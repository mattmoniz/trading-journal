# Hard rules — full incident detail

Full incident narratives for the Hard Rules in `CLAUDE.md` that carry a real dated incident (bugs found, numbers, root causes, fixes). A handful of rules in CLAUDE.md are already short and rule-only with no incident — those aren't duplicated here. `CLAUDE.md` keeps the condensed rule + a pointer into this file; read this before assuming you understand why a rule exists, not just what it says.

## No dead ends — the four-part checklist

- **Anything that drives or anticipates a decision — a data point, a computed signal, a classifier, a backtest finding, not just a "script" — must be built so the system keeps learning from it and can revisit it. No dead ends.** Added 2026-07-18 per explicit user directive ("its not just scripts it[s] data or datapoints anything that drives or anticipates in decision making must be help the system keep learning and growing. No dead ends") after a session spent the day building exactly this pattern piecemeal (persisting `VOL_REGIME_HIST`, then `GARCH_VOL_SCALE`, recording `RESEARCH_CLAIM` rows for every tested finding) without it ever being named as a governing rule new work is held to. Concretely, before considering anything of this kind done, check all four:
  1. **Persisted somewhere queryable** (`performance_audit` or a real table) — not trapped in a script-local variable, a one-off `scratch/*.json` file, or a hardcoded literal in the serving code. A hardcoded snapshot of a once-real number is the textbook failure case here — see the hand-typed-stat rule below, 7 confirmed instances, most recently `keyLevels.js`'s `tierStats` object (2026-07-18): a real calibration got computed once, dropped into a literal, and then just sat there while the real number underneath it drifted 3-6x away, including a full sign flip, with nothing to ever notice.
  2. **Has a recheck/recalibration path** — a scheduled script (`run_weekly_backtests.sh`), a `RESEARCH_CLAIM` 30-day cycle, or at minimum a documented manual recheck trigger. Not compute-once-and-forget.
  3. **Actually wired to a consumer, or explicitly flagged if not yet wired.** A signal nobody reads is a dead end whether or not it's persisted — either it feeds a live decision (sizing, suppression, a displayed card) or it's tracked as a `flag_decision.mjs` `OPEN_DECISION` so someone has to actively decide to wire it in or drop it, never just silently sitting there unreferenced.
  4. **Discoverable** — has an entry in `ARCHITECTURE.md`'s inventory or this file's "Where to look" section, not an orphan only findable by grepping around and hoping.
  This names the connective principle behind several mechanisms that already exist as separate conventions — `RESEARCH_CLAIM` (item 2), `OPEN_DECISION` (item 3), "export the real function, never reimplement" (item 1, applied to code), the no-static-thresholds rule below (item 1, applied to a threshold specifically) — treat this as the reason those exist, not a fifth new mechanism to build. When starting something new that computes or anticipates anything, ask which of the four it's missing before calling it done.

## RTH + Globex both required

- **Any new setup, signal, or calibration finding must be evaluated for BOTH the RTH window (9:30am-4pm ET) and the Globex/overnight window (6PM-8:30AM ET) before being considered complete — never default to RTH-only and call it done.** User directive 2026-07-22, given directly after the confluence-pair proximity calibration was built and backtested RTH-only (`scripts/backtest_confluence.js`'s `getRTHBars()`) without the question of overnight applicability ever being raised. This codebase already has two parallel, structurally different detection engines — the full RTH level-fade engine (`acd.js` ~3830-4430, `sizeMultiplier` IIFE, `keepLevelsAll`, confluence-aware) and the much simpler `detectGlobexSetup()` (~line 594, single-level touches only, no `sizeMultiplier` stack, no confluence tracking at all as of 2026-07-22) — and it is easy for a new finding built/tested against one to simply never get asked about the other. Concretely, before calling any new setup-discovery or calibration thread done: (1) test it against Globex/overnight data too, not just RTH, even if the result is negative or thin — a tested-and-recorded "doesn't apply overnight" is fine, an untested gap is not; (2) if the live wiring mechanisms differ between the two engines (e.g. RTH has a `sizeMultiplier` stack to hook a bonus into, Globex currently doesn't), wire into whichever supports it and explicitly flag (`OPEN_DECISION`) whichever doesn't rather than silently leaving it RTH-only with no record of the gap. See `confluence_pair_globex_backtest` `RESEARCH_CLAIM` for the first applied instance of this rule.

## CumPL diff P&L method

- **P&L must use the CumPL diff method**, not `SUM(pnl)` or `SUM(FlatToFlat)` — both overcount. See the SQL pattern in [ARCHITECTURE.md](ARCHITECTURE.md#pnl-calculation-cumpl-diff--critical-dont-regress-this). `/api/daily-logs` and `/api/stats/daily` both implement this — keep them in sync if you touch either. **A raw, account-type-unscoped CumPL-diff is a DIFFERENT and WORSE bug than the `SUM(pnl)` it replaces — always scope to `custom_fields->>'account' LIKE '%-PRO%'`, matching `stats.js`'s `/stats/capture-ratio` (the established correct reference).** Found 2026-07-19 fixing `server/services/patternMemoryUpdate.js`'s `session_pnl` (`OPEN_DECISION` `pattern_memory_update_session_pnl_needs_cumpl_audit`): a naive `LAG(cum_pl) OVER (PARTITION BY account ORDER BY log_date)` interprets a practice/sim account's periodic balance reset as a single-day loss in the tens of thousands — confirmed live, `PRACTICEDec108855775`'s `cum_pl` dropped from $13,000.00 (2024-12-16 close) to resetting near zero the next day, which an unscoped diff reads as a **-$12,155 loss that never happened**. Caught only because the "fix" was audited against real numbers before trusting it — Gemini's first pass reported the CumPL-diff and `SUM(pnl)` "matching almost perfectly," which was wrong (its query used a flawed `COALESCE(LAG(...), cum_pl)` fallback that silently zeroed out exactly the rows that would have exposed the reset); a from-scratch re-implementation of the canonical pattern surfaced the $13K-scale discrepancy immediately. `-PRO%` accounts don't get balance-reset mid-history the way practice ones do — this is why `stats.js` already scoped this way; `patternMemoryUpdate.js` didn't, until this fix. When there's no PRO-account CumPL data for a given day (only ~48 of 358 historical trading days have any), fall back to raw `SUM(pnl)` for that day only — imprecise but not corrupted, same documented-exception convention as `dll.js`'s own fallback.

## MNQ commission constant

- **This journal trades MNQ (Micro E-mini Nasdaq): $2/point, $2 round-trip commission ($1 per side)** — ground truth lives in `server/config/instruments.js`'s `LIVE_INSTRUMENT.commissionPerRoundTrip` (imported by `server/routes/acd.js` and `scripts/update_optimal_stops.mjs`), mirrored in `src/constants/contract.js` for the frontend. **Corrected 2026-08-11**: this was `$1` round-trip (documented here as "independently verified against a broker statement") until a direct user correction — it's actually $1/transaction/contract, so $2 for a full round trip on 1 MNQ. Every historical EV/calibration number computed before this fix undercounts commission by $1/trade. **Never copy a `$/pt` or commission constant from another script without checking it matches this** — and don't trust an in-code "verified" comment either, see the standing rule on that below. Found 2026-07-14: `scripts/archive/backfill_level_fades.js` used `PT=5, COMM=5` (matching neither MNQ's real $2 nor standard NQ's real $20) — an uncaught error present since that script's creation, silently copied into 6 new `repair_*.mjs` scripts written earlier the same session before being caught. Overstated every affected setup_type's dollar-EV by ~2.5x (correct sign, wrong magnitude) until fixed via `scripts/repair_dollars_per_point.mjs`. If you're about to write a `$/pt` or commission constant in a new script, check it against `acd.js`'s live values first — don't trust an existing script's constant just because it's already there.

## active_setups backfill vs origin_status

- **~80% of `active_setups` is synthetic backfill data, not live-fired trades — check `origin_status` before treating any figure derived from this table as realized/historical performance.** Found 2026-07-17 (Opus Audit #3, `docs/OPEN_THREADS.md`): `resolution_method` breakdown is `BACKFILL` 6,375 + `EARLY_TOUCH_BACKFILL` 4 (inserted retroactively by old backfill/repair scripts, **never fired through the live system at all**) vs. `PRICE_CLEAN` 231 (genuinely live-resolved) out of 7,988 total rows. `active_setups.origin_status` (immutable at insert, never touched by any resolution UPDATE — unlike `status`, which gets overwritten to `RESOLVED`/`EXPIRED`) now distinguishes `ACTIVE` (real, live-visible)/`SHADOW` (suppressed, background-only)/`BACKFILL` (synthetic)/`UNKNOWN` (pre-2026-07-09, unrecoverable — no `SETUP_STATUS` snapshot history reaches back that far). **A `SUM(actual_pnl)` or backtest built from `active_setups` without filtering by `origin_status` is a strategy simulation, not an account record** — this bit an entire session's worth of walk-forward-backtest/DLL-sweep/weekly-P&L work before the gap was found. Before presenting any `active_setups`-derived dollar figure as "what happened," check what fraction of its population is `BACKFILL`.

## Never hand-type a WR%/N/$ literal

- **Never hand-type a WR%/N/$ literal into a live-rendered card, label, or description string.** Found 2026-07-13: 6 separate instances across `mine_session_bias.mjs`, `antigravityEdges.js` (IB re-test cards, gap-fill card, V-pattern card, `SETUP_CONTEXT` adjustment table), and `acd.js` (`levelMap.bestCtx`) — all presented a specific hand-typed number as if freshly computed, several silently drifted to the point of being *directionally wrong* (e.g. `acd.js` claimed IB_LOW was an "88% WR" edge; the real, live number was 66% WR at **negative** EV). **7th instance found 2026-07-18**: `server/routes/keyLevels.js`'s `/api/confluence/today-zones` `tierStats` object — hand-typed despite its own comment claiming it was "latest weekly rigor-checked calibration," found while consolidating an unrelated GARCH backtest and comparing its touch-detection constants against the live confluence system. Every tier was off 3-6x vs. the real latest `performance_audit` `CONFLUENCE_AUDIT` row, `SINGLE` wrong-signed (+$6.91 hardcoded vs. real **-$3.02**). Fixed the same way as the other 6: query `performance_audit` live (12h cache, `server/lib/cache.js`). Full writeup: [docs/OPEN_THREADS.md](docs/OPEN_THREADS.md). Either derive the text from a `row` field already fetched from `performance_audit` in the same function, or write a dedicated `scripts/backtest_<name>.mjs` that populates one — never hand-type the number, even as a placeholder "for now." **This pattern keeps recurring (7 instances now) — when touching ANY file that renders a WR%/N/$ figure for any reason, even in passing, check whether that figure is a live query result or a literal before moving on, don't wait to stumble into it.**

## Volume-profile spreading (POC/VAH/VAL)

- **Volume-profile computations (POC/VAH/VAL) must spread each bar's volume across its own high-low tick range, never bucket 100% of it at one price.** `server/services/developingValueService.js`'s `computeProfile(bars)` is the single correct reference implementation (spreads volume evenly across each bar's H-L range, then extends VAH/VAL alternately toward whichever side has more volume next until 70% total is enclosed) — for any period-range VA (week/month/quarter/2-day), call its exported `computeVolumeProfileForRange(queryFn, { startDate, endDate, ... })` wrapper rather than writing a new SQL aggregation. Found 2026-07-17: a `ROUND(low/0.25)*0.25 ... GROUP BY` bucket-by-low pattern (plus a non-standard fixed 35%-up/35%-down value-area split instead of the correct alternating-to-70% method) had been hand-duplicated across `scripts/compute_levels.js` (PW/PM/3M_VAH/VAL/POC — the values written to `level_prices`, feeding every backtest/live level-fade candidate for those levels), `server/routes/acd.js` (6 occurrences: the live 2-day-composite POC, 2 prior-month VA computations, 2 prior-day VA fallbacks), and `server/routes/weekly.js` (3 endpoints, all confirmed dead/no frontend caller). Because a bar that trades through a 5-point range in one minute got 100% of its volume counted at the bottom tick, every affected VAH/VAL/POC was dragged toward the low of the session/period — drift confirmed real and often large (many periods showed 100+ point differences once corrected) once independently spot-checked directly (not just via Gemini's own estimate, which had at least one confirmed replication error against the actual live SQL — audited per the standing Gemini-output-audit rule). Fixed by centralizing on `computeProfile`/`computeVolumeProfileForRange`, backing up and recomputing the full `level_prices` history for the affected level_names, and re-tagging every trade in `trades.level_proximity` (whose nearest-level ranking could have been skewed by a wrong VA value even when the final tag wasn't itself a VA level) against the corrected data. Full writeup and backup-table names: docs/OPEN_THREADS.md / docs/DB_BACKUP_CATALOG.md.

## Export the real function, never reimplement

- **Export the real function, never reimplement live-derived classification logic inline in a backtest script.** If a backtest/mining script needs a value that a live service already computes (a regime, a day-type, a level, any derived classifier — not a raw DB column), it must `import`/reuse that service's real exported function, or read a persisted canonical table populated by it, never re-code the math by hand. Found 2026-07-16: two independent Gemini attempts at a Markov-vs-volatility-regime comparison each had to hand-reimplement `classifyRegime()` from scratch (`volatilityRegimeService.js` had no persisted history to check against), and the two reimplementations disagreed with each other and with the live tool's own prior validation — a real, silent drift bug, not a hypothetical. Fixed at the root by exporting `fiveMinBars`/`stdevLogReturns`/`getPercentile`/`classifyRegime`/`getMorningVolBaseline` from `volatilityRegimeService.js` and building `scripts/backfill_volatility_regime_history.mjs`, which imports them directly and persists one row/day to `performance_audit` (`signal_type='VOL_REGIME_HIST'`) as the now-canonical source every future comparison should join against. When adding a new derived/live classifier, export its core function(s) at creation time rather than waiting for a second script to need it and reimplement instead.

## Every tested claim gets recorded via record_claim.mjs

- **Every tested research/exploratory claim — not just setup-calibration ones — gets recorded via `scripts/record_claim.mjs`, positive or negative.** A hypothesis that gets tested, produces a real N/WR/EV number, and only lives as prose in `docs/OPEN_THREADS.md` or a `scratch/*.json` file has no lifecycle: nothing re-checks it, and the next session re-derives it from scratch (sometimes differently — see the rule above). `recordClaim({slug, claimText, sourceFile, sourceDate, sampleSize, winRate, evPerTrade, rigorStatus, status})` writes/updates a `signal_type='RESEARCH_CLAIM'` row in `performance_audit` with a 30-day `next_recheck_due`; `node scripts/record_claim.mjs --list` shows every claim and flags overdue ones. `status` is `CONFIRMED` (independently re-verified), `PROVISIONAL` (real but thin/unstable/unchecked-for-rigor), or `STALE` (needs a fresh recheck, generally by age). This is separate from the existing setup-calibration tables (`SETUP_STATUS`/`OPTIMAL_STOP`/`DAY_TYPE_ALPHA`/etc.) — those already have their own lifecycle; `RESEARCH_CLAIM` is for everything else. Built 2026-07-16 per an Opus consultation on making this codebase's research findings durable instead of evaporating each session; seeded with 7 audited claims from this session (one caught a real Gemini-fabricated set of numbers before it entered the ledger — see docs/OPEN_THREADS.md). **Found 2026-07-20 (new session): two scripts (`test_extension_vs_garch_vol.mjs`, `test_extension_vs_next_level_distance.mjs`) hand-rolled their own `performance_audit` INSERT instead of calling `recordClaim()` — and set `next_recheck_due` to the SAME DAY the claim was written, not +30 days, so the session-start hook flagged both as overdue the very next day.** Fixed both to call the canonical helper. **When writing any new script that persists a `RESEARCH_CLAIM` row, always import and call `recordClaim()` — never hand-write the INSERT, even if it looks like a one-off** — this is the same "shared module, don't reimplement" principle applied to a persistence helper instead of a computation function.

## RESEARCH_CLAIM recheck flag vs recurring cron

- **A `next_recheck_due` on a `RESEARCH_CLAIM` row is a FLAG, not an auto-rerun — if the finding is still open (not a settled/rejected/confirmed one-time study), wire its source script into a recurring cron too, or it never actually recomputes itself.** This is the direct answer to "why doesn't this work like `SETUP_STATUS`, which already auto-promotes any setup_type the moment it crosses real N≥20" — `backtest_setup_status.mjs` can do that for free because it's a single generic `GROUP BY setup_type` scan with no hardcoded list, so every live setup_type rides the same daily/weekly cron automatically. A `RESEARCH_CLAIM` has no equivalent generic scanner — each is backed by a bespoke one-off script — so the *only* way it keeps re-checking itself against fresh data is if that specific script is added to `run_weekly_backtests.sh` or `run_daily_calibration.sh`, same as any calibration script (`calibrate_delta_confirmation.mjs`, `scan_regime_combinations.mjs`, `backtest_pd2_2dpoc_complete.mjs`, `backtest_vwap_reclaim_hold_phase1.mjs`/`_globex_phase1.mjs` all do this) — the promotion/wiring decision still stays a human call (see `scan_regime_combinations.mjs`'s `flagDecision()`-on-clean-cell pattern), only the *recompute* becomes automatic. **`test_invariants.mjs` check `[10]`** (added 2026-08-04, direct user question) verifies every `RESEARCH_CLAIM` source script's filename appears in one of those two cron files — WARN-only and deliberately quiet in the routine alert stream (one aggregate count, not one line per claim: as of 2026-08-04, 149 of 161 historical claims are unscheduled, and that's mostly *expected*, since most of this codebase's `RESEARCH_CLAIM` backlog is settled/rejected one-time studies that don't need a standing recheck) — full per-claim detail is written to `scratch/research_claim_unscheduled.txt` for triage, not spammed into `scratch/gemini_alerts.txt`. Read that file when deciding whether a specific open finding deserves to be wired in; don't treat the aggregate WARN count as something to drive toward zero.

## Resolve every isolation worktree dispatch

- **Resolve every `isolation: worktree` Agent dispatch before the spawning session ends — never leave one for a future session to discover by accident.** The harness only auto-deletes an isolated worktree if the agent made *no* changes; if it made any, the path/branch are handed back and a human/session must explicitly commit+merge it or deliberately discard it (`git worktree remove` + delete the branch). Found 2026-07-16: a 2026-07-01 `isolation: worktree` dispatch (24hr Globex VWAP feature) left ~3,100 uncommitted lines across 31 files sitting untouched for two weeks — nothing in this repo's workflow surfaces an orphaned worktree, so it was only found by accident during an unrelated dead-code grep. `.claude/hooks/session-start.sh` now flags any worktree besides the main checkout at the start of every session (see its `STRAY_WORKTREES` check) as a backstop, but the real fix is not leaving one dangling in the first place.

## Use Gemini for mining, Claude for implementation

- **Use Gemini for mining/analysis, Claude for implementation.** When a task is combinatorial exploration or pattern-mining over `performance_audit`/trade data — "which pairs are best under condition X," "what does the data show about Y across N setup types," multi-scenario simulations — dispatch it to Gemini via the `scratch/claude_request.md` protocol rather than grinding through it directly. Gemini has read-only DB access and doesn't burn Claude's context on large query output; only the findings should come back into context, not raw rows. Claude's job is building the systems (scripts, endpoints, hooks) and interpreting/applying what Gemini finds — not re-deriving the mining work itself. Reserve doing it directly for small, deterministic, single-query aggregations (e.g. one bucketed backtest over one table) where dispatching would cost more round-trip time than it saves, and for anything Gemini has already gotten wrong twice on this task (see the 2-strikes rule below). This does not relax **Audit all Gemini output before acting on it** below — mining work still gets verified before anything is promoted to live.

## Three-phase Gemini workflow for higher-stakes work

- **For higher-stakes work — anything that could end up gating/sizing a live trade, or any live-wiring change to production code — use a 3-phase Gemini workflow, not just the mine-and-run above.** (0) Before writing any code, send Gemini the intended approach/design (not code) and ask it to critique the plan itself. (1) Full AUTONOMOUS mine-and-run for the actual analysis, same as the rule above. (2) A separate review-only pass on the resulting code (explicit "do not execute, do not edit" header) before trusting any number or shipping any live change. Adopted 2026-07-29 after Claude shipped a live-wired signal (`hivol_lopace_at_detection`) the same day it was validated, with neither a design critique nor a code review first — a real off-by-one bug (the live volume-window calculation excluded the entry bar the backtest included) reached production undetected until the user directly asked "did gemini review your code?" Once adopted, phase 0 caught a real design gap in a risk-management gate backtest (marginal utility against the existing suppression stack was the single most important thing to check and hadn't been planned for), and phase 2 caught the resulting script's level-name mapping was broken/incomplete before any promotion decision was made on it. User directive: persist this, and use it specifically for anything touching risk management or live execution behavior, not just entry-signal research.

## Every pending decision gets recorded via flag_decision.mjs

- **Every pending product/architecture decision — "wire this in or delete it," "merge this branch," "change this cadence" — gets recorded via `scripts/flag_decision.mjs`, not left as prose in `docs/OPEN_THREADS.md`.** Deliberately a sibling mechanism to `RESEARCH_CLAIM` above, not the same rows with a different label: a decision has no statistical content and doesn't go "stale" the way a research finding does — it just sits `PENDING` until a human actually decides, then `RESOLVED`. `flagDecision({slug, decisionText, sourceFile, sourceDate})` writes a `signal_type='OPEN_DECISION'` row in `performance_audit`; `decisionText` must include real context — what's being decided, why it matters, what resolving it looks like (a bare fact like "5 cards aren't rendered" isn't enough; write the why and what's-at-stake alongside it, the same way this file's own entries do). `node scripts/flag_decision.mjs --list` shows every pending decision; `--resolve <slug> '<resolution text>'` closes one out. **Every pending decision prints unconditionally at the start of every session** (`.claude/hooks/session-start.sh`'s `OPEN_DECISIONS` section, sorted oldest-first with age since first flagged) — this is the actual fix, not the table: nothing here depends on a future session remembering to re-read prose in `OPEN_THREADS.md`. Built 2026-07-17 per explicit user request ("anything that needs to be reevaluated should [be] flagged with something and actively monitored. Nothing can be buried") after the session-start hook was found to have zero mechanism for resurfacing this category — `RESEARCH_CLAIM`'s 30-day recheck only covers statistical findings, not decisions; seeded with 10 real pending items pulled from this session and the prior day's SSOT/dead-end audit.

## A verified code comment is not itself verification

- **A code comment claiming a number was "verified" or "cross-checked" is not itself verification — this is a distinct, more dangerous risk than a one-off wrong Gemini response, because it sits trusted in committed production code instead of a scratch file someone might still double-check.** Found 2026-07-17: `scripts/update_optimal_stops.mjs` hardcoded `DEFAULT_DPP=5` (a dollars-per-point fallback), defended by a comment claiming "real $/pt is cleanly bimodal (~$5 for the level-fade family)... independently verified via Gemini mining pass, cross-checked by Claude against direct SQL before trusting." That claim was false — every setup_type with N≥20 STOP_HIT trades (54 checked) resolves to $2.01-$2.06/pt, no exceptions, no bimodal split (the 4th occurrence of the wrong-$/pt-constant bug class documented in `server/config/instruments.js`'s header). 25 live setup_types had `OPTIMAL_STOP` rows calibrated with the wrong 2.5x-inflated fallback before this was caught — not by anyone re-reading the comment skeptically, but by someone happening to re-run the check from scratch months later. Treat "verified" language in an existing comment as a claim to re-check when you're about to depend on the value it's attached to, not as a substitute for checking it yourself.

## Derived-value field drift when a smarter computation is added

- **When a script both computes a derived value (a sweep, a classifier, an optimizer) and separately stores/prints a number labeled as describing it, that pairing needs a standing check — a feature added on top of an existing field can silently break the field's own meaning without anyone touching the field's line.** Found 2026-07-17: `scripts/update_optimal_stops.mjs`'s `ev_per_trade` column was `ROUND(AVG(actual_pnl))` — a raw historical average using whatever stop/target each trade actually fired with — from the file's original commit (`a04b2fd`, 2026-07-05), back when `optimal_stop`/`optimal_target` were themselves just plain percentiles (`p75_mae`/`p50_mfe`), so the raw average was a defensible, honest, standalone stat at the time. The real EV-optimizing sweep (`sweepOptimalTarget`) was added 4 days later (`de3e407`, "EV-sweep targets") to make `optimal_stop`/`optimal_target` genuinely EV-optimal — but `ev_per_trade`'s write path (`console.log`, the INSERT param) was never rewired to report the sweep's own `swept.ev`. From that commit on, `ev_per_trade` silently stopped describing the stop/target it sat next to, for every setup_type, every run — reproduced live: `CAM_R1_FADE_LONG` showed `stop=23/target=40/EV=-$14`, but re-running the exact formula at that exact stop/target gave **+$13.92**, a sign-flipping $28 discrepancy. Survived 4 more commits touching the same file (including one earlier the same day this was caught) because none of them had a reason to look at that specific line — a normal code review or diff read catches "does this line look right," not "does this field's original meaning still hold after a later feature was bolted on three commits ago." **Fixed** by writing `swept.ev` (falling back to the raw average only in the documented thin-tail-gate case), and — the actual prevention, not just the one-off patch — `scripts/test_invariants.mjs` check `[5]` now re-derives every `OPTIMAL_STOP` row's expected stop/target/EV via the real, imported `sweepOptimalStopAndTarget()` (not a hand-copied formula — a second copy would itself be the same bug class) and fails if the stored row doesn't match either the fresh sweep result or the documented fallback exactly. Verified the check actually catches this specific bug (not just passes trivially) by deliberately reintroducing the old raw-average line, confirming 65 failures, then restoring the fix and confirming a clean pass. **General lesson: when you add a smarter computation on top of a value a field already claims to describe, either rewire that field in the same commit or explicitly rename/re-scope it — and if the value is trusted enough to sort/display/gate anything, add an invariant check that re-derives it via the real function, not a plausibility check that a bug could trivially satisfy** (the first version of check `[5]` had exactly this flaw — it accepted "matches the raw average" as always-valid, which a bug that *always* writes the raw average would pass 100% of the time; fixed by requiring an exact match against the real sweep function's actual output). Full writeup: `docs/OPEN_THREADS.md`.

## Baseline must be computed the same way as the candidate

- **Auditing a backtest's simulation logic is not the same as auditing where its baseline comes from — a comparison is only as trustworthy as its least-audited side.** Found 2026-07-19: `scripts/backtest_scaleout_runner.mjs` (Gemini-authored, Claude-audited) had its chronological bar-by-bar simulation logic checked carefully and found sound — but its "baseline EV" was read directly from the live `OPTIMAL_STOP.ev_per_trade` column instead of being resimulated the same way as everything else it compared against. That stored value is computed by the OLD order-blind `sweepOptimalTarget()` against `mae_points`/`mfe_points` captured under whatever stop/target was live when each trade historically fired — for `VALUE_AREA_RESPONSIVE_SHORT`, historical stop distances actually used ranged 15-28pt+ while the CURRENT live stop is 10pt, so the stored baseline (-$1.99) was silently comparing today's tight stop against MAE data that was never bounded to it. A properly self-consistent chronological resimulation of the identical 100%-at-T1 baseline gave +$15.22/trade — not a loser at all — which **reversed** the finding: the scale-out config that looked like a clear winner (+$17.76 vs the wrong -$1.99 baseline) actually loses out-of-sample against the true baseline. Already promoted to an `OPEN_DECISION` and a `RESEARCH_CLAIM` before being caught — both had to be retracted (with a full account, not silently deleted) once a sibling script (`backtest_target_sweep_v2.mjs`, built the same day, which computed its baseline via the same resimulation as its candidates from the start) exposed the discrepancy on a side-by-side check of the same setup_type. **Fixed** by always resimulating the baseline in the same pass as everything else being compared (never reading a stored EV column as ground truth for a fresh comparison), and tightening the promotion gate to require beating baseline both full-sample AND out-of-sample. The real replacement finding (`CAM_R4_FADE_SHORT`) is actually stronger than the retracted one. **When building or auditing any script that claims "config X beats baseline Y," verify baseline Y was computed by the exact same method as X — a stored/precomputed number read from elsewhere, even one that looks authoritative because it's "the live value," needs the same scrutiny as the thing being tested against it.**

## Structural advantage control in comparison backtests

- **A backtest comparing two conditions against a shared, unchanging exit needs to rule out a structural/algebraic advantage before crediting the "smarter" condition with the win.** Found 2026-07-21: a test of whether a candle-pattern-confirmed re-entry (after price overshoots a level fade past its own historical median adverse excursion) beats blind first-touch entry, both walked to the SAME original stop/target, came back from a Gemini corpus-wide run looking dramatic — pooled paired EV improved from -$85.77 to -$5.67, in 62 of 64 setup_types with zero exceptions. That zero-exception uniformity was the tell (same "too clean" signal as every other incident in this section) — a dedicated control script (`scripts/pilot_overshoot_control_check.mjs`) proved nearly all of the improvement was mechanical: entering LATER against a FIXED stop/target is algebraically favorable regardless of any pattern (a winner pays more from a cheaper entry, a loser costs less from a closer one) — confirmed directly, the win/loss OUTCOME matched between a pattern-free "enter blind at the overshoot point" control and the pattern-confirmed entry in 92-100% of trades per setup_type. Corrected: `ORIG` EV=-$82.56 → blind-overshoot-entry EV=-$8.99 → pattern-confirmed EV=-$2.96 — the pattern's real marginal contribution was ~$6/trade, not the ~$77/trade the uncontrolled comparison implied. **When a new backtest's two arms differ in WHEN they enter but share the same exit levels, add an entry-price-only control arm (no "smart" filter, just the later/different entry) before trusting that a filter/pattern/signal explains an EV gap — the gap may be entirely explained by the entry price itself.** Same family as the baseline-mismatch rule above, applied to entry timing instead of a stored baseline column. Full account: docs/OPEN_THREADS.md.

## Delete stale rows when guardrails tighten

- **When a backtest script's overfitting guardrails get tightened and re-run, anything that no longer survives needs its OLD `performance_audit` row explicitly deleted, not just left unrefreshed by the new run.** Hit twice in one day, 2026-07-19: `backtest_scaleout_runner.mjs`'s first run persisted 3 survivors; the corrected rewrite (fixed promotion gate) only found the same 3 slots worth updating naturally, but a broader case bit `backtest_target_sweep_v2.mjs` harder — its first (broken, spike-picking) run persisted a row for all 103 tested setup_types unconditionally, then the corrected rewrite only inserted/updated the 18 that survived the new guardrails, leaving the other 85 setups' original spike-picked rows (e.g. `PD_LOW_FADE_SHORT`'s absurd 719.8pt pick off a single trade) sitting in the table with the SAME `run_date` as the fresh ones — a naive `DISTINCT ON (signal_name) ORDER BY run_date DESC` query can't tell them apart, since "most recent run" doesn't distinguish "recomputed this run" from "untouched leftover from a run that happened on the same day." Caught both times only by noticing a downstream consumer's own count looked wrong (a walk-forward script logging "103 setup_types" when 18 was expected) — not by anything in either backtest script itself. **When re-running a script with stricter/different guardrails, explicitly query which prior rows for that `signal_type` are NOT in this run's fresh output and delete them** (or diff on a marker field the new version writes that the old one didn't, like `rigor`/`oosEv` in this case) — don't assume `ON CONFLICT DO UPDATE` alone keeps the table consistent, since it only touches rows the new run actually produces.

## Backtest candidate grid floor from data resolution

- **A backtest candidate grid needs a floor derived from the underlying DATA'S OWN RESOLUTION, not just statistical overfitting guardrails (thin-tail/plateau/OOS/rigor) — those catch overfitting to a few trades, not overfitting to a precision the data cannot actually resolve.** Found 2026-07-19: widening `backtest_scaleout_runner.mjs`'s trailing-stop candidate grid (for thoroughness, per user request) surfaced 32/96 setup "survivors" — but 31 of them picked a trailing-stop width of just 3-6.8pt, passing every existing guardrail cleanly. Checked directly: the median 1-minute NQ bar range is 6.25pt, the 25th percentile is 3.25pt — a trail that tight sits *within normal single-bar noise*. OHLC bar data only records a bar's high/low, not the intra-bar price path, so the backtest literally cannot determine whether such a tight trail would have actually triggered in real execution — the near-universal "survival" was a data-resolution artifact, not a real edge, and every one of this codebase's existing guardrails (all statistical, checking sample size/stability/out-of-sample performance) passed it cleanly because none of them check whether the candidate itself is finer than the data can support. **Fixed** by adding a minimum trail-width floor derived from the same live data (median 1-min NQ bar range, queried fresh — not a hardcoded number, matching the no-static-thresholds rule) — survivors dropped from 32 to 18, and even those cluster suspiciously close to the floor, suggesting a genuinely different (smaller, execution-risk-heavier) phenomenon than the original, wider-trail finding it was meant to generalize. **General lesson: before trusting ANY backtest whose candidates are themselves a distance/time/price granularity (a trail width, a tick-level threshold, a sub-bar timing window), check that granularity against the data's own real resolution — a candidate finer than what the underlying data can distinguish will pass statistical guardrails by construction, since the "noise" it's exploiting is measurement noise, not market behavior.**

Also check `scratch/gemini_alerts.txt` / `scratch/server_errors.jsonl` for `[CLIENT_ERROR]` entries — `trading-journal-watcher.service` (`scratch/gemini_error_watcher.mjs`) logs live browser errors there, and a real one can sit unnoticed for days if nothing checks it. Does NOT replace the full `npm run build` + browser-check gate above (single-file lint can't see cross-file import/export breaks or interaction bugs) — it's the fast, real-time layer underneath, not a substitute.

## Verify data-fetching performance, not just no-errors

- **Whenever a change touches data-fetching — a new component with its own `fetch`/poll, a new or modified API endpoint, or edits to an existing one on a hot path (Morning Prep, Trades/Calendar) — verify actual loading performance before calling it done, not just that it renders without errors.** "No console errors" and "actually fast" are different claims; this codebase has repeatedly shipped the former while being badly wrong on the latter (a 51MB unbounded `/api/trades` response, an N+1 firing ~18 redundant queries per setup, a shared-poll hook that silently multiplied requests 16x instead of deduping them — all invisible to lint/build/error-log checks, all found only by measuring). Concretely, using Playwright (already available in this environment — see the `/tmp` node_modules-symlink trick used 2026-07-15 if `playwright` isn't a direct project dependency):
  1. **Count and list actual network requests** a real page load/interaction fires (`page.on('request', ...)`, filter to `/api/`) — group by endpoint and flag anything firing more than once per load. A component fetching the same URL another component already polls is almost always a bug, not a coincidence (`grep` the exact URL string across `src/` before adding a new fetch of something that sounds "already available elsewhere").
  2. **Time the actual settle point**, not just first paint — watch for whatever loading indicator the page uses (this codebase's convention: `page.locator('text=Loading…').locator('visible=true').count()` polled every ~500ms-1s) until it hits zero, not just `domcontentloaded`.
  3. **For any new/modified endpoint, `curl` it standalone** (`-w "%{time_total}s size=%{size_download}\n"`) and compare against its cost *inside a real concurrent page load* — a large gap between the two means connection contention or a pile-up, not a slow query, and points to request-coalescing/caching (see below) rather than query optimization.
  4. **If a response is unexpectedly large, check the query is actually bounded** — this codebase has repeatedly found genuinely unbounded historical queries (`SELECT ... FROM trades` with no date/limit, `price_bars_primary` lookbacks missing an upper or lower bound defeating partition pruning) hiding behind code that looked bounded at a glance.
  Don't run this full checklist for every one-line change — but any change that adds a fetch, adds a component that will live on Morning Prep or Trades, or touches an endpoint already known to be hot (`setup-detection`, `confluence/today`, `live-session-context`, `edges-context`, `trades`) gets it. Added 2026-07-15 after a multi-pass session where "components take forever to load" kept resurfacing despite each individual fix passing lint/build/no-errors — the actual causes were only found by measuring request counts and response timing directly, and each one clean-checked (no error, no warning) right up until it was.

## Validating a classifier is not the same as validating its split

- **Verifying a statistical split is real is not the same as verifying the classifier that produced the split is valid.** A backtest that conditions setup EV on some newly-invented regime/classification (not an existing, already-computed field — a fresh z-score/percentile scheme built for the occasion) can pass every rigor check this codebase uses (N≥20, chi-square-ish significance, chronological stability, day-clustering) while the classifier itself is still an arbitrary construction: window lengths and cutoffs picked semi-informally rather than derived from a principled search, never sensitivity-tested (does the finding survive a 25-day window instead of 30?), never checked for whether the label predicts anything on its own independent of whichever setup it's being used to condition, and never adjusted for the multiple-comparisons surface of testing several regime schemes against dozens of setup_types at once. A plausible-sounding economic narrative for why a split makes sense ("don't fade a fresh trend") is not validation either — that kind of story can be told for almost any split after the fact. Found 2026-07-18: three regime-conditioning metrics built and rigor-checked in one session (directional-trend z-score, price-stretch z-score, trend-persistence tercile) had every downstream EV split verified, but the classifiers themselves never were — flagged by the user, recorded as `OPEN_DECISION` `regime_detection_methodology_needs_validation`. Before trusting a *newly-built* classifier's conditioning effects (as opposed to conditioning on an existing field like `day_type` or `prior_day_profile`, which only needs the split itself checked), validate the classifier's own parameter robustness and independent predictive power first. **Follow-up, same day: the validation was actually run, and this specific classifier failed it.** A non-overlapping-window re-test, a placebo/permutation test, and an independent PELT-changepoint ground truth on raw price data (not the classifier's own input) all came back negative — full account in `docs/REGIME_DETECTION_SPEC.md` §7.1/§8.1. This is the concrete, worked example of why this rule exists: the EV splits all passed rigor checks; the classifiers themselves were still arbitrary.

## A PENDING OPEN_DECISION can be stale

- **A `PENDING` `OPEN_DECISION` describes the state of the codebase *as of whenever it was last checked*, not necessarily now — verify its underlying claim before relying on it if you're doing related work, especially anything touching a file it names.** The mechanism guarantees a decision won't be silently forgotten; it does not guarantee the decision's factual claim is still accurate, and nothing currently re-checks a decision's claim automatically. Found 2026-07-18: `unrendered_dashboard_cards_5` was flagged pending on 2026-07-17, describing 5 specific dashboard components as still-unrendered dead code — they had actually already been deleted a day earlier (2026-07-16, commit `9fb677b`), almost certainly because the flagging check ran against stale `main` instead of the active feature branch (the exact risk `main_branch_55_commits_behind` had already warned about in the abstract — this is the confirmed real instance of it). Only caught because a routine main-merge diligence pass happened to touch the same files. Concretely: before citing a pending decision's claim as current fact (not just before resolving it), a cheap `grep`/direct check costs little and prevents compounding a stale finding into new work.

## Pre-compaction claims are not evidence

- **A prior "confirmed empirically" claim — including Claude's own, including from earlier in the same session — is not evidence once it has crossed a context-compaction boundary; the actual verification script/query is gone and only the conclusion survives.** This is the same trust-boundary problem the standing Gemini-output-audit rule solves for Gemini, but it applies just as much to a summarized version of Claude's own prior work: a compaction summary preserves *what was concluded*, not *how it was checked*, and a wrong methodology (e.g. a verification query that didn't scope to the right `signal_type`/table/column) survives the summary just as confidently-worded as a correct one. Found 2026-07-18: `keepLevels_ls_base_key_mismatch_selection_bug` was flagged PENDING with language claiming a standalone script had "confirmed empirically" that `ls()` always returned null in production — carried across a context-compaction boundary as settled fact, then acted on (a code fix was written and committed) before its own `GUNNING FOR` text ("re-verify... live afterward, not just code review") was actually carried out. When that follow-up verification was finally done from scratch — querying `UNIFIED_BACKTEST` directly and checking `backtest_unified.js`'s own naming convention via `git log -S` — it flatly contradicted the original claim: the table's signal names had never had the shape the original diagnosis assumed, for any of the 64 real candidate levels checked, since the file was first written on 2026-07-01. The one-line "fix" already committed was a harmless no-op against real data, not a fix of anything real; both the code comment and an `ARCHITECTURE.md` entry that had already picked up the false claim needed correcting in a follow-up commit, and the `OPEN_DECISION` had to be resolved with a corrected account instead of a triumphant one. **General lesson**: before resolving an `OPEN_DECISION`, or otherwise treating any pre-compaction "confirmed via a standalone script" claim as load-bearing, redo the actual check against current live data rather than trusting the conclusion — a session summary is not a re-runnable artifact, and skepticism that's already standard practice for Gemini's output needs to apply to a compacted version of Claude's own prior claims too.

## Market-behavior hypotheses go through bar history first

- **A hypothesis about market behavior gets tested against raw bar/price history first; only route a hypothesis through `active_setups` trade-level N when the question is specifically about how this system's OWN setups perform.** Named 2026-08-04 (external Opus review) after noticing a repeating pattern: `diagnose_chronological_stop_target_bias.mjs` (0 of 9 live types pass a bar-walk-based check), the structural-breakout Phase 0 retest test (0 of 8 gated cells, `docs/STRUCTURAL_BREAKOUT_RETEST_SPEC.md`), and the BIGMOVE "riding-with-trend" runner-extension idea (0 real triggers ever, `docs/BIGMOVE_SIGNAL_RUNNER_EXTENSION_SPEC.md`'s Resolution section) all independently landed on a real zero — and all three were structurally forced toward zero by routing a *market-behavior* question ("does a big trend day predictably follow a compression period," "does retesting a level beat the first touch," "does the day's trend confirm mid-trade") through `active_setups`, whose real (non-`BACKFILL`) population is thin, recent (`origin_status` tracking only started 2026-07-17), and gated by whether one of this system's specific setups happened to fire — not by whether the underlying market condition happened. `price_bars_primary` has the full multi-year NQ bar history and isn't gated by any of that. Concretely: if the question is "does market condition X predict market outcome Y" (a claim about NQ price behavior in general), build it as a bar-level scan over `price_bars_primary` first — cheap, dense, and not selection-biased by which setups fired. Only route through `active_setups`/real trade N once the question becomes "does this system's OWN setup capture that edge" (a claim about execution, not about the market). Getting a real zero from a trade-level test doesn't mean the market phenomenon doesn't exist — it may just mean the question was asked through too thin a lens.
