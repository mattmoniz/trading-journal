# Pre-registration: overnight high/low and prior-week level distances as ML inputs — 2026-10-21

Written and committed BEFORE the features are exported or any arm is run. Origin: user (2026-10-21): "overnight high short and overnight low longs are classic setups… they should be included in ml, same with prior week value high and lows." The ML model's level inputs are prior-day only (`pd_distTo*` for PD high/low/close/POC/VAH/VAL) plus developing-level distances; it has no overnight or prior-week level. The ONH/ONL fade setups are already in the training population (`ONH_FADE_SHORT`, `ONL_FADE_LONG` etc.); what is missing is the model knowing where those levels are. Research only, offline; nothing live or in the nightly training changes unless a later, separate step wires a kept feature.

## Features (one signed distance per level, in ATR20 units: (entry minus level) / ATR20, positive = entry above the level; ATR20 = mean RTH range of the previous 20 sessions as of the row's trade date)
- **ONH / ONL:** RTH-hours fires (09:30-18:00): high/low of the calendar day's bars before 09:30 (exactly the live StopSweep definition); Globex-hours fires: the overnight high/low SO FAR (from the most recent 18:00 ET up to the fire minute, at least 10 bars) so nothing after the fire is used.
- **PW_VAH, PW_VAL, PW_HIGH, PW_LOW:** the prior week's value-area high/low and range high/low from `level_prices` (known at the start of the week; a row's trade_date lookup).
- Missing level = missing value (LightGBM handles it); no imputation.

## Arms (identical machinery to `docs/ML_INPUT_ABLATION_PREREG_20261020.md`: same 7,300 rows, 27-input research baseline, expanding 7-day folds, 3-day purge, same hyperparameters, weights, 75th-percentile approval per session, policy P&L per trade, fold-averaged AUC)
- **M0** baseline. **L1** M0 + ONH, ONL (2 columns). **L2** M0 + PW_VAH, PW_VAL, PW_HIGH, PW_LOW (4 columns). **L3** M0 + all six.
- **Controls:** random normal columns with exactly each candidate column's own blank pattern, added in the same numbers (2, 4, 6) so a feature must beat a same-shaped noise column set, not just the baseline (the 2026-10-20 ablation showed missing-value patterns alone move AUC by up to +0.01). Noise band: 8 baseline-plus-one-random-column arms (SD of AUC and of policy P&L).
- **Rule (frozen, same as the earlier B arms):** a level set ADDS VALUE only if its fold-averaged AUC exceeds its matching control's by more than 2 null SD AND the 99 percent day-blocked interval of (arm minus control) policy P&L per trade is above zero AND both halves of the folds are positive. Otherwise research-only. 3 comparisons. Context: every earlier candidate set (day type, normalised flow, rotation gate, setup family, pace) and the dollar-trained target came out not shown, so no gain is expected; a null is informative and is reported as what could not be shown.
- **If something is kept** the next step is a separate decision: add the feature to `dataset.py`, `mlFeatureSnapshot.js` (live capture at fire time), `build_feature_dict()` and the scorer, retrain, and let the weekly checkpoint-promotion gate and the unseen-trade scorecard judge it. Nothing here wires anything.

## Known limits
The model currently adds no measurable value on unseen trades (`ml_checkpoint_unseen_trades_no_value_20261021`), so even a kept feature does not make the gate worth trusting by itself; ONH/ONL for Globex fires are developing values and noisier than the RTH ones; prior-week levels change only once a week, so within a week they are partly a proxy for the week; the simulated pnl is a bar walk.
