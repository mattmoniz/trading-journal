# Pre-registration: which ML inputs help, and do the new candidates add anything — 2026-10-20

Written and committed BEFORE any arm is run. Origin: the user said the ML gate "is not improving, so I'm not seeing that our current inputs are helping or good" and asked to (1) test removing inputs one at a time and (2) test the new ideas (day type, order flow normalised against the same time of day, the rotation gate as an input). Research only, offline, nothing wired, the live model and its nightly training are untouched.

## Data and machinery (identical to the existing validation)
- Rows: the same real, fully-featured training population `scripts/ml_meta_labeling/dataset.py::fetch_training_dataframe()` builds, with the production 2.5x label. Validation: the expanding-window walk-forward of `scripts/ml_meta_labeling/walkforward.py` (7-day folds, 3-day purge, minimum training size, LightGBM with the hyperparameters from `ML_HYPERPARAMS` or the defaults, sample weights that split a confluence cluster, approval threshold = the 75th percentile of the fold's own training-set scores computed separately for RTH and Globex, exactly the live mechanism). Only the feature list and the random seed change between arms.
- Seeds: every arm is run with seeds 42, 7 and 99 and the results averaged; the baseline additionally with seeds 1 and 2 so the seed-to-seed standard deviation of the fold-averaged AUC and of the policy P&L per trade is measured, not assumed.

## Arms
- A0 baseline: the current feature list (`dataset.py::feature_cols()`).
- A1-A10 leave-one-group-out, each removing one group of columns: A1 prior-day level distances (the six `pd_distTo*`), A2 prior-day structure (`pd_pdRange`, `pd_pocDeltaVsPrior`, `pd_vaOverlapPctVsPrior`), A3 value migration (the three `pd_migration_*`), A4 developing-level distances (`intraday_distToDevPoc/Vah/Val/Vwap`), A5 session cumulative delta (`intraday_sessionCumulativeDelta`), A6 recent 15-bar delta in both forms (`intraday_recentDelta15Bars`, `drv_recentDeltaAligned15Bars`), A7 time in session (`intraday_barsInSessionSoFar`, `minutes_from_open`), A8 `nl30_at_detection`, A9 `confluence_score_at_detection`, A10 trade direction (`drv_is_long`).
- B-arms add candidate columns to the baseline, computed point-in-time at the decision bar (the last completed 1-minute bar before the fire minute) and exported by `scripts/export_ml_candidate_features_20261020.mjs`: B1 day type = developing-range rank (range from the RTH open / ATR20, ranked against the previous 60 sessions at the same clock bar, the R4 definition, plus the raw range / ATR20); B2 order flow vs normal = adverse-imbalance rank over 15 and over 30 one-minute bars (the R5 definition, aligned to the trade direction, ranked against the previous 60 sessions at the same clock bar); B3 rotation = the 65pt gate AGREE flag, bars since the current rotation leg began, and the number of 65pt rotations since the 18:00 session start; B4 = B1 + B2 + B3 together. These exist for RTH fire times 09:35-15:59 only; Globex rows carry missing values (LightGBM handles them natively).
- Not tested here: the tick-based candidates (tape pace, big-order features) because they cannot be scored live without a tick feed, which the user has paused.

## Metrics
- Fold-averaged AUC (threshold-free signal check) and the number of folds.
- Policy P&L per trade: over EVERY test-fold trade, the P&L of a trade if the arm says TAKE and 0 if VETO, divided by all trades. This accounts for an arm approving more or fewer trades. Also the approved-trade count, approved P&L and the mean per approved trade (descriptive).
- Comparison to baseline: the paired difference (baseline minus arm for the A arms, arm minus baseline for the B arms) of policy P&L per trade, by trading day (seed-averaged), day-blocked bootstrap 99 percent interval (14 comparisons are made: ten removals and four additions), the difference in fold-averaged AUC in units of the baseline's seed standard deviation, and the sign in the first and second half of the folds.

## Decision rules (frozen)
- A group MATTERS if removing it lowers the fold-averaged AUC by more than 2 baseline seed standard deviations AND the 99 percent interval of the policy-P&L difference (baseline minus arm) lies above zero. It is NOT HELPING if the AUC change is within 2 seed standard deviations and the interval includes zero (a candidate to trim, but only a candidate). It HURTS if removing it raises the AUC by more than 2 seed standard deviations or the interval lies below zero.
- A candidate feature set ADDS VALUE if adding it raises the fold-averaged AUC by more than 2 seed standard deviations AND the 99 percent interval of the policy-P&L difference (arm minus baseline) lies above zero, with the same sign in both halves of the folds. Otherwise it stays research-only, which is the expected outcome (the earlier direction-aligned flow feature did not survive correction for the number of things tried).
- Any result is recorded as a RESEARCH_CLAIM; nothing here changes the live model, its features or its nightly training. If a candidate adds value, the next step is the roadmap decision `ml_feature_candidates_after_forward_r4_r5_20261020` (forward confirmation as a plain rule first, a DeepSeek review, then a pre-registered feature addition), not an immediate change.

## Known limits (stated in advance)
The roster changed a lot during the validation window (the roster-churn confound) so a pooled result is not a clean read of "now"; the model's whole real population is a few thousand trades; LightGBM results have seed noise, which the baseline seeds measure; this test uses the replay-free real live rows only. The scripts are not DeepSeek-reviewed.

## Addendum A (written after the FIRST run showed two defects, before any corrected result is read)
The first run (`scratch/ml_ablation_20261020.txt`) is discarded as a test and kept only as a regression check: its baseline reproduced `walkforward.py` exactly (fold AUCs identical; 1,100 approved of 6,630, approved P&L +3,408, which matches the recorded walk-forward claim). Two defects were found, both visible in that output, and the raw AUC deltas of that run were seen by the author before this addendum was written (so this is a correction made with partial knowledge of the results, stated openly):
1. LightGBM with these hyperparameters has no random sampling, so every seed gives the identical model and the "seed noise band" is exactly zero. The noise band is therefore replaced by NULL-COLUMN arms: the baseline plus one column of pure noise (eight different random columns); the standard deviation of the fold-averaged AUC and of the policy P&L per trade across the eight null arms is the noise band used in every rule above (replacing "baseline seed standard deviation"). All runs use seed 42.
2. Policy P&L divided by all trades came out NaN because some rows have no `actual_pnl`; those rows count as 0 in the policy P&L (the same way the recorded totals skip them).
3. The four B arms all raised AUC by about the same amount (+0.013) although their contents differ, which points to the missing-value pattern (the candidate columns are blank on Globex rows, so any such column tells the model "this is an RTH trade", a flag the baseline deliberately does not have). Control arms are added: C1 = the baseline plus an RTH flag only; C2 = two random columns with exactly the candidates' blank pattern; C3 = seven random columns with that pattern. A B arm must beat its matching control, not just the baseline: B1-B3 are compared with C2 and B4 with C3. "ADDS VALUE" now needs the AUC gain over the control above 2 null standard deviations and the 99 percent policy-P&L interval of (arm minus control) above zero with both halves positive.
All other rules, arms and metrics are unchanged.

## Addendum B (written after the corrected run's results were read, before the pruned arms are run): pruned models
The corrected run (claim `ml_input_ablation_and_candidates_20261020`) found session cumulative delta and nl30 do nothing, time-in-session and the recent 15-bar delta carry the AUC, and removing prior-day structure, trade direction or the confluence score raised AUC but not dollars. These pruned arms were chosen after seeing that, so they are a forking-path follow-up: three more comparisons are added to the 14 already made (17 in all; 99 percent intervals kept). Same population, folds, hyperparameters, noise band (null-column SD from the same script run) and policy metric as above.
- P1: baseline minus the do-nothing groups: session cumulative delta (A5) and nl30 (A8).
- P2: P1 and also minus the groups whose removal raised AUC: prior-day structure (A2), confluence score (A9), trade direction (A10).
- P3: only the two groups that carried AUC: time in session (A7) and recent 15-bar delta raw and aligned (A6).
Rules: a pruned model is SIMPLER AND NOT DISTINGUISHABLE if its fold-averaged AUC is within 2 null SD of the baseline (above or below) and the 99 percent interval of the policy-P&L difference (baseline minus arm) includes zero; it is BETTER if its AUC exceeds the baseline by more than 2 null SD and the interval of (arm minus baseline) lies above zero with both halves positive; it is WORSE if its AUC falls more than 2 null SD below the baseline or the interval of (baseline minus arm) lies above zero. These intervals are wide (about +-1 dollar per trade), so "not distinguishable" is not evidence of equality; it only means the data cannot tell the models apart. Nothing is changed in the live model whatever the result.
