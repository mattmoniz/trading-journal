## 1. Entry freshness gate (G0 item 2, narrowed after reading the code)
Fact: the shared price helper `getLatestBars()` / `getCurrentPrice()` (`server/services/priceRetrieval.js`) already returns nothing when the freshest NQ bar in `price_bars_primary` is older than `FRESHNESS_MINUTES = 15` (a static plumbing parameter, documented as slack over the ~60 s ingestion poll), so every DETECTION call site fails safe on a stale feed. The live-flags banner (`server/routes/setups.js`) uses its own `PRICE_BARS_STALE_MINUTES = 10`. The gap: `sweepEntries()` (`server/services/sierraChart/orderSweep.js`, called at the start and end of each detection pass) places an ENTRY order for an ALREADY-EXISTING `active_setups` row without checking feed freshness (MARKET entries in `MARKET_ENTRY_PREFIXES` are the sharpest case: the order is sent at market on information that may be minutes old). The only existing fail-closed staleness check is in the escalate-unfilled-entry-to-market path (`orderSweep.js` about line 347).
Proposal: once per sweep, before any entry is placed, read the age of the latest NQ bar (one cheap query, cached for the sweep). If the feed is stale, or the query fails (fail closed), skip every entry candidate this sweep through the existing `recordEntrySkip(row, reason)` with a readable reason such as `price feed stale: latest NQ bar N min old` (so it lands in `gated_candidates` and the per-row `broker_note`, the same visible-reason convention as the other gates), and never touch exits, stops or reconciliation (exits must never be blocked by a data problem). A resting LIMIT already working is not canceled by this gate; only NEW placement is gated. Closure windows (`isGlobexWeekClosed`, the 17:00-18:00 maintenance gap) need no special case because nothing is eligible then anyway.
Open design questions: (a) the threshold. Options: the existing 15 minutes (consistent with the helper), the banner's 10, or derived from the data (for example a multiple of the recent median inter-bar gap, with a floor) to follow the repo's no-static-threshold rule; thin overnight Globex can have legitimately sparse 1-minute bars, so a tight rule risks blocking real entries. (b) whether MARKET entries need a tighter bound than resting LIMIT entries. (c) where the check sits in the chain relative to `isOrderEligible`, the daily-loss gate and `checkEntryGates` (order matters for which reason is recorded; repo history shows a later override silently winning). (d) alert path: reuse `priceBarsStale` plus a nightly count of FEED_STALE skips in `live_attestations`.
Verification plan: a unit test with injected bar ages (fresh, stale, query error), a rolled-back real-schema dry run of the skip insert, a check that exits are never gated, `test_invariants.mjs` unchanged, then a live restart and a read of the skip rows.

## 2. Boot self-test of the kill switch and daily-loss gate (G0 item 5)
Fact: `killSwitch.forceHaltOnBoot()` runs unconditionally at startup (`connectionManager.js`), the daily-loss gate has unit tests (`scripts/test_dll_gate.mjs`), sim profiles auto-rearm after a clean reconciliation. Gap: nothing asserts after EVERY restart that the system really came up disarmed and refusing.
Proposal: after boot (before any auto-rearm), run a side-effect-free self-test: (1) `killSwitch` state is disarmed with a halted reason; (2) `isOrderEligible()` for a synthetic setup returns not eligible with a reason; (3) the daily-loss gate returns blocked with a visible reason for a synthetic account with unknown P&L, and for an unset limit; (4) `sweepRealOrders()` with a MOCK dtc client submits zero orders while disarmed. Record the result in `live_attestations` (check name `boot_selftest`, trade date today) and, on failure, alert and SUPPRESS the auto-rearm for that boot (a failed self-test must not be undone by the auto-rearm path). Open questions: where exactly to hook (before or after the DTC logon), how to avoid any real order path being exercised, whether the self-test itself can deadlock a boot, and what else is worth asserting.

## 3. Failure rehearsal (G0 item 10)
A scripted, repeatable rehearsal run against the SIMULATED account and offline mocks, never a real-money profile: restart mid-position, DTC disconnect mid-order, a stale price feed with a resting entry, an exit rejected then retried against a different position, sleep/wake (process alive, DTC dropped), a duplicate server process, a tick file missing at the session start. For each: expected state, what must be visible (banner, `gated_candidates`, `live_attestations`), and the pass/fail check. Open questions: which scenarios can be automated safely, which need a manual step on the sim, and a sensible order.

## 5. DeepSeek review outcome (run 2026-11-01 23:10-23:13 EST, off-peak; full text `scratch/deepseek_response_g0_design_20261102.md`, ANSI trace stripped copy not kept; audited by Claude against the code 2026-11-02)
Verified against the files (accepted):
- `getLatestBars()` returns `[]` on a stale feed and discards the age in that case (it attaches `ageMinutes` only to FRESH rows, `priceRetrieval.js` 50-68), so "N min old" needs a raw age read (use `etNaiveTimestampToMs`, as the helper and banner do).
- Three divergent staleness numbers exist: helper 15 min with no closure guard, banner 10 min with `isGlobexWeekClosed` (`setups.js` 39, 106), and the proposed gate. Unify them or the operator sees the banner say fresh while entries are blocked.
- `wantsMarketEntry()` splits MARKET from resting-LIMIT entries; `AMT_TELL_` is a MARKET prefix, so the only live flow is covered by a MARKET-only gate. The escalate path already fails closed (`orderSweep.js` 344-354).
- Self-test assertion (3) in section 2 is WRONG as written: `dllGateDecision` returns `blocked:false` for unknown P&L when a worst case is computable (`dllGate.js` 29-35, the 2026-10-18 change); it blocks only with no computable worst case or at the limit. Unset limit: the wired `evaluateDailyLossLimit` blocks (84-86) while the pure `dllGateDecision` does not (line 24). Assert the two behaviours separately.
- `maybeAutoRearmAfterReconcile()` (`connectionManager.js` 138-150) consults only `DTC_AUTO_REARM_SAFE`, armed state, the last clean report and the invariant check; nothing reads a self-test result, so "suppress auto-rearm on failure" needs a NEW gate there plus a defined order against the first post-LOGON reconcile.
- `sweepRealOrders` returns early unless `dtcClient.isLive()`, and `sweepExits` does not consult the kill switch (the only `isOrderEligible` use is in the entry path), so a mock that fakes `isLive()` against the live DB could write or submit exit rows. Do not run the full sweep in the self-test.
Not verified / overstated:
- "hr-003 explicitly exempts infra thresholds" is NOT in the stored rule (`docs/CLAUDE_MD_ARCHIVE/hard_rules.md` hr-003 has no exemption). 15 minutes is a documented static plumbing parameter; deriving the gate threshold from the recent median inter-bar gap with a floor stays an open design choice, to be recorded as a deliberate deviation if a static number is kept (hr-035: take the diagnosis, apply the house convention).
- That the self-test would race the first LOGON reconcile is plausible from `connectionManager.js` (`forceHaltOnBoot` at line 109, `maybeAutoRearmAfterReconcile` called at 188) but the exact boot ordering was not traced; trace it before coding.
Decisions for the build (not yet implemented, nothing live changed): (1) gate MARKET entries only, one shared staleness helper and closure guard for banner, helper and gate; (2) self-test = three gates as pure units (kill switch state, `isOrderEligible`, `evaluateDailyLossLimit` plus the blocked/unblocked unknown-P&L cases) plus a rolled-back insert, never the full sweep, run to completion with a timeout before the first reconcile, its result a required input to `maybeAutoRearmAfterReconcile`; byte-diff state and DB before/after; (3) rehearsal automated-first (duplicate process, missing tick file, stale feed injection as the gate's acceptance test, DTC disconnect on an offline mock), then manual on the sim account with a written checklist; the script hard-refuses unless the profile is `DTC_AUTO_REARM_SAFE=true` and sim, and never calls `arm()`/`halt()`; the gate sits outside the per-row try/catch but inside `sweepEntries`.

## 6. Build and code review outcome (2026-11-02; DEPLOYED 06:39 EST the same morning, scenario 1 of the rehearsal passed)
Built per section 5: `server/services/feedFreshness.js` (shared age definition, `FEED_BLOCK_MINUTES = 15`, `FEED_WARN_MINUTES = 10`, `entryFeedGate()`), the MARKET-only gate in `sweepEntries` (after `isOrderEligible` and the daily-loss gate), `server/services/sierraChart/bootSelfTest.js` (6 checks, runs between `forceHaltOnBoot` and `connectOnce`, result in `live_attestations` check `boot_selftest`, gates `maybeAutoRearmAfterReconcile`), banner field `bootSelfTest` in `/api/setups/live-flags` plus a quick-check line, `scripts/test_g0_safety.mjs` (mutation-tested), invariant [27], `docs/G0_FAILURE_REHEARSAL_CHECKLIST_20261102.md`. DeepSeek code review: `scratch/deepseek_response_g0_code_review_20261102.md`. Audited and acted on:
- ACCEPTED, fixed: a crashed or unfinished self-test was invisible (banner silent on null); now `markBootSelfTestCrashed()` records a failure, suppresses auto-rearm and shows the banner. A late-finishing check could mutate the result after the timeout; now closed and snapshotted. The env-variable removal could outlive a hung check; now raced against its own 5 s timeout with the restore in a `finally`. DLL and DB-probe checks are injectable and mutation-tested. Comments corrected ("side-effect free" and "touches no live state" were imprecise). The DTC `getClient` name collision is avoided by importing the DB one as `getDbClient`.
- REFUTED by data: "15 minutes will false-block thin Globex". Across 60,479 NQ 1-minute bars since 2026-09-01 the only gap over 5 minutes outside the 16:55-18:05 maintenance window is the 2026-09-07 holiday early close (301 min); bars are continuous overnight, so the static 15-minute limit stays (infrastructure alarm, recorded deviation from hr-003).
- FOUND BY THE REVIEW-DRIVEN DST TEST, fixed: `etNaiveStringToUtcIso` (`server/parsers/sierraParser.js`, used by `etNaiveTimestampToMs`) was off by up to one hour for a few hours on the six DST-change dates in 2024-26 (single-pass correction); added a second pass. Verified on 200,000 timestamps: outputs differ only on those six dates, and the round trip is exact except the non-existent 02:xx hour on spring-forward days. Practical impact was nil for live data (the affected hours are Sunday early morning, market closed).
- NOT DONE, noted: no end-to-end test runs `sweepEntries` against a stale feed (only unit and wiring tests); the escalate-to-market path has no freshness re-check between cancel-confirm and resubmit (it fails closed at cancel time only; pre-existing); manual `POST /sierra-chart/start` is deliberately not gated by the self-test (human override, banner is the protection).
