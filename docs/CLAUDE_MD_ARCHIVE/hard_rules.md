<a id="hr-001"></a>

- **Anything that drives or anticipates a decision — a data point, a computed signal, a classifier, a backtest finding, not just a "script" — must be built so the system keeps learning from it and can revisit it. No dead ends.** Before considering anything of this kind done, check all four:
  1. **Persisted somewhere queryable** (`performance_audit` or a real table) — not a script-local variable, a one-off `scratch/*.json` file, or a hardcoded literal in the serving code.
  2. **Has a recheck/recalibration path** — a scheduled script (`run_weekly_backtests.sh`), a `RESEARCH_CLAIM` 30-day cycle, or at minimum a documented manual recheck trigger. Not compute-once-and-forget.
  3. **Actually wired to a consumer, or explicitly flagged if not** via a `flag_decision.mjs` `OPEN_DECISION` — a signal nobody reads is a dead end whether or not it's persisted.
  4. **Discoverable** — an entry in `ARCHITECTURE.md`'s inventory or this file's "Where to look" section, not an orphan only findable by grepping and hoping.
  This is the reason `RESEARCH_CLAIM`, `OPEN_DECISION`, "export the real function," and the no-static-thresholds rule below already exist — treat it as the reason those mechanisms exist, not a fifth one to build. See [docs/HARD_RULES_DETAIL.md#no-dead-ends-the-four-part-checklist](../../docs/HARD_RULES_DETAIL.md#no-dead-ends-the-four-part-checklist) for the incident that prompted this and the recurring hand-typed-stat failure case.


<a id="hr-002"></a>

- **Any new setup, signal, or calibration finding must be evaluated for BOTH the RTH window (9:30am-4pm ET) and the Globex/overnight window (6PM-8:30AM ET) before being considered complete — never default to RTH-only and call it done.** A tested-and-recorded "doesn't apply overnight" is fine; an untested gap is not. The RTH level-fade engine (`acd.js` ~3830-4430) and `detectGlobexSetup()` are structurally different — if their live-wiring mechanisms differ (e.g. only one has a `sizeMultiplier` stack), wire into whichever supports it and flag (`OPEN_DECISION`) whichever doesn't, rather than silently leaving a finding RTH-only. See [docs/HARD_RULES_DETAIL.md#rth-globex-both-required](../../docs/HARD_RULES_DETAIL.md#rth-globex-both-required).


<a id="hr-003"></a>

- **No static thresholds.** Every threshold in this codebase must be derived from a rolling distribution (σ from a rolling mean/std), never a hardcoded number. This applies to entries, stops, targets, signal triggers — everything. If you're about to write a literal number as a cutoff, stop and compute it from historical data instead. **This rule stops new hardcoded numbers — it does not, by itself, catch existing ones that already slipped through and have since decayed.** Found 2026-09-07: `sizeMultiplier`'s NL30/loss-streak/win-streak/overnight-alignment branches were each calibrated once from a real backtest (dated 2026-07-05 to 2026-07-08 in their own code comments) and never rechecked — over the following ~2 months, multiple branches decayed to near-zero edge or fully inverted (a boost landing on what's now a negative-EV bucket, a penalty landing on the wrong bucket entirely), invisible because nothing ever re-validated the comment against current data. **A hardcoded WR/EV/z-score backtest comment justifying a live branch, with no corresponding scheduled recalibration script, is a standing audit target, not a one-time-verified fact** — when investigating "is this signal still good" (prompted by the user or found incidentally), grep the relevant IIFE/function for dated backtest comments lacking a scheduled recalibration path and re-verify each against current real data before trusting it, the same way `sizemultiplier_loss_win_streak_overnight_stale_20260907`/`nl30_regime_conditioning_stale_boost_inverted_20260907` did.


<a id="hr-004"></a>

- **P&L must use the CumPL diff method**, not `SUM(pnl)` or `SUM(FlatToFlat)` — both overcount. See the SQL pattern in [ARCHITECTURE.md](../../ARCHITECTURE.md#pnl-calculation-cumpl-diff--critical-dont-regress-this). `/api/daily-logs` and `/api/stats/daily` both implement this — keep them in sync if you touch either. **A raw, account-type-unscoped CumPL-diff is a DIFFERENT and WORSE bug than the `SUM(pnl)` it replaces — always scope to `custom_fields->>'account' LIKE '%-PRO%'`**, matching `stats.js`'s `/stats/capture-ratio`. When there's no PRO-account CumPL data for a given day, fall back to raw `SUM(pnl)` for that day only — imprecise but not corrupted. See [docs/HARD_RULES_DETAIL.md#cumpl-diff-pl-method](../../docs/HARD_RULES_DETAIL.md#cumpl-diff-pl-method) for the practice-account balance-reset incident this guards against.

<a id="hr-006"></a>

- **~80% of `active_setups` is synthetic backfill data, not live-fired trades — check `origin_status` before treating any figure derived from this table as realized/historical performance.** `active_setups.origin_status` (immutable at insert) distinguishes `ACTIVE` (real, live-visible) / `SHADOW` (suppressed, background-only) / `BACKFILL` (synthetic) / `UNKNOWN` (pre-2026-07-09, unrecoverable). **A `SUM(actual_pnl)` or backtest built from `active_setups` without filtering by `origin_status` is a strategy simulation, not an account record.** Before presenting any `active_setups`-derived dollar figure as "what happened," check what fraction of its population is `BACKFILL`. See [docs/HARD_RULES_DETAIL.md#activesetups-backfill-vs-originstatus](../../docs/HARD_RULES_DETAIL.md#activesetups-backfill-vs-originstatus).


<a id="hr-007"></a>

- **`active_setups.is_cluster_primary` (added 2026-09-07, cluster touch credit Phase 2) is a SECOND, independent filter every real-N/EV aggregation needs, on top of `origin_status` — a query that filters `origin_status` correctly but not this will still overcount.** A confluence-cluster touch now writes one primary row (the winning candidate) plus `is_cluster_primary=false` sibling rows for the other cluster members (`suppression_reason IN ('CLUSTER_SIBLING_TOUCH_CREDIT','CLUSTER_SIBLING_TOUCH_CREDIT_BACKFILL')`) so the losing siblings get real N credit for setup-level stats — but a naive `COUNT(*)`/`SUM(actual_pnl)` grouped by `setup_type` without `AND (is_cluster_primary IS NULL OR is_cluster_primary = true)` double-counts the same touch event once per cluster member. Caught 2026-09-07 via self-audit: an ad hoc verification query missing this filter overcounted real decisive N by ~43% (3,803 vs. the correct 2,653) — DeepSeek's own independently-run query had it right, Claude's didn't. `is_cluster_primary` defaults `true` (rows predating the column, and any non-clustered touch, are correctly primary) — the risk is a *new* aggregation query written without the exclusion, not existing calibration scripts (`backtest_setup_status.mjs` and the pooled/real trade filters already apply it). See `scripts/backtest_setup_status.mjs`'s `REAL_TRADE_FILTER`/`POOLED_TRADE_FILTER` for the canonical filter pair to reuse rather than hand-rolling a new one. **This risk is NOT backend-only** — found live 2026-09-08: `server/public/quick-check.html`'s own displayed Net P&L (`computeRangeStats()`/`renderEquityCurve()`) summed `actual_pnl` with no `is_cluster_primary` filter at all, inflating a real -$1,908 into a displayed +$738 in one day. **There are 4 real insert sites that can produce a cluster-tagged row, not 3** — the 4th, `EARLY_TOUCH_BACKFILL` (a level already touched by the time the poller catches up, commonly right at the RTH open), had zero cluster-tagging until fixed the same day; see the "Cluster touch credit" entry below for the full incident and both fixes.


<a id="hr-008"></a>

- **Never fabricate a stat.** Any win-rate/hit-rate claim needs N≥20 in the sample before it's reported as decisive (see `engineReadHitRates.js` convention). Below that, say so explicitly rather than rounding to a confident-sounding number.


<a id="hr-009"></a>

- **Any new query against `performance_audit` filtered by `signal_type` (± `signal_name`/`window_days`) needs `DISTINCT ON (the grouping columns) ... ORDER BY ..., run_date DESC` — a bare filter with no dedup silently returns EVERY historical calibration run's row, not just the latest, once more than one run has accumulated for that key.** This table is append-only (one new row per weekly/nightly recalibration), so any query without this pattern degrades over time as history accumulates — it can look correct for weeks after being written, then start returning garbage once a second calibration run lands. Two distinct failure shapes depending on how the JS consumes the rows: (1) consumed via `.map()`/pushed into an array with no dedup → duplicate entries, one per historical run, not one per real row (found 2026-09-20: `performance-audit/unified`'s `pairsBaseQ` inflated 778 real distinct confluence pairs into 9,267 displayed array entries — a straight 1:1 map over every un-deduped row); (2) consumed via an object-key assignment in a `forEach` (`someMap[key] = row`) → non-deterministic, since whichever row Postgres happens to return last for a tied `ORDER BY` sort key silently wins, changing between requests with zero code change (found the same day: `pairsWinQ`'s `wr20`/`wr6m`/`wr1y` etc. — 7,853 of 9,267 pairs differed between two back-to-back calls to identical code, only diagnosed as a data bug and not "the refactor broke something" via the verification technique below). Already known for `OPTIMAL_STOP` (see that entry under "Where to look") — this is the same pattern confirmed to recur in a completely different `signal_type` (`CONTEXT_ANALYSIS`) in the same file, meaning it's a standing footgun for any NEW query against this table, not a one-off already fully patched. When wrapping in a subquery to keep an independent outer `ORDER BY` (e.g. by `ev_per_trade DESC` for display ranking, separate from the `DISTINCT ON` dedup columns), that's expected and fine — see `server/services/unifiedSignalTable.js`'s pairs queries for the pattern. **Two more failure shapes in this same family, found 2026-09-25:** (3) `ORDER BY run_date DESC` alone has no secondary tiebreak — `run_date` is a plain `DATE` (no time component), and a `signal_name` with multiple same-day runs (confirmed live: 68 historical rows for one signal_name, clearly more than one run per day on average) makes `DISTINCT ON`'s tie-break non-deterministic between calls. Add `, id DESC` (or another monotonic column) after `run_date DESC`. (4) **A `WHERE recommendation = 'X'` filter applied BEFORE the `DISTINCT ON` dedup is a different, worse bug than either of the above** — it returns the latest row *among only the rows that were ever `X`*, not the type's true current state, so a setup_type that was `X` at some point in its history but has since changed shows up as `X` even when its actual latest row says something else entirely. Confirmed live: `IB_HIGH_FADE_SHORT` (currently `ACTIVE`) appeared in a "current `SUPPRESS` list" built this way. Always get the true latest row per key FIRST (`DISTINCT ON (signal_name) ... ORDER BY signal_name, run_date DESC, id DESC`, no `WHERE` on the value you're checking), and filter to the value you want only after that.


<a id="hr-010"></a>

- **When byte-diffing a refactor's before/after output and the two don't match, call the SAME (post-refactor) code twice in a row before concluding the refactor introduced the diff.** A live endpoint reading real, continuously-updating data (price, resolving trades, recalibration runs) will show real differences between two fetches minutes apart even with zero code change — that's expected drift, not evidence of a bug. But if two back-to-back calls to the *identical, unchanged* code also disagree, the endpoint has a real, pre-existing non-determinism bug, independent of whatever you're verifying — this is what surfaced the `performance_audit` dedup bug above during the 2026-09-20 acd.js file-size-reduction work (a pure, verified-behavior-identical extraction), not something the extraction caused. This is a cheap, decisive test — always run it before attributing a byte-diff mismatch to your own change.


<a id="hr-011"></a>

- **A "backtest reference" calibration script must never write to `signal_type='SETUP_STATUS'`/`'OPTIMAL_STOP'` under the same `signal_name` the real pipeline (`backtest_setup_status.mjs`, grouped from real `active_setups` rows) uses — give it its own distinct `signal_type` instead.** Every consumer that reads "the current row" does `DISTINCT ON (signal_name) ... ORDER BY run_date DESC`, so if two different scripts both write under the same `(signal_type, signal_name)` key on different schedules, the value silently alternates between real and simulated depending on which one ran most recently — with no marker visible anywhere except `notes.source`, which nothing checks by default. Found 2026-09-14 (user-caught live: "I never see `RTH_FLUSH` fire"): `scripts/backtest_flush_patterns.mjs` wrote backtest-simulated numbers into `SETUP_STATUS` under `RTH_FLUSH_LONG`'s own real signal_name — confirmed live, the same signal_name showed `recommendation=ACTIVE`/N=167/EV=+$9.13 right after the backtest script ran, then `THIN_N`/N=5/EV=-$104.20 two days later once the real pipeline ran again. This fooled the session itself, not just a hypothetical future reader — a backtest number was reported as real live performance before the collision was found and fixed (renamed to `FLUSH_BACKTEST_REFERENCE`, 29 stale collision rows backed up and deleted, see `docs/DB_BACKUP_CATALOG.md`'s `performance_audit_flush_setup_status_collision_backup_20260914` entry). **The file's own header comment cited this exact pattern as "matching `MOMENTUM_60m_60m_TREND`'s precedent"** (`scripts/backtest_momentum60_daytype.mjs`) — meaning it was a deliberately reused anti-pattern, not a one-off, and that script has not yet been checked for the same live collision. Before trusting any `SETUP_STATUS`/`OPTIMAL_STOP` row for a setup_type that also has a dedicated calibration/backtest script of its own, check `notes.source` across its recent history for more than one distinct writer — if two scripts both write there, this bug class is present until one of them gets its own signal_type.


<a id="hr-012"></a>

- **`backtest_setup_status.mjs`'s `REAL_TRADE_FILTER` excludes `resolution_method IN ('MARK_TO_MARKET','RECOVERY_MTM')` uniformly — correct for a setup whose MTM means "stale, force-closed position," but wrong for a setup whose DESIGNED exit mechanism is itself a time-based mark-to-market (no price target to hit, e.g. `POC_ROTATION_JOIN_LONG/SHORT`'s documented "Time60_Stop20": 20pt stop, else mark-to-market at 60min).** For that shape of setup, the filter strips out every real WIN and counts only stop-outs as "real" — pinning `real_n` under 20 and forcing permanent `THIN_N` no matter how much real, genuinely positive-EV data exists. Found 2026-09-14 (user asked "why is the N smelling bad," turned into a real bug hunt): `POC_ROTATION_JOIN_LONG/SHORT` had 27 real trades each (8-10 real MTM wins averaging +$111-$147, 19-17 real stop-outs at exactly -$42), but the filter's own real_n read only 17-19 — `backtest_setup_status.mjs`'s own THIN_N log line literally says "blended N clears the floor, real N doesn't." System-wide scan found 9 setup_types with zero `TARGET_HIT` resolutions but real MTM wins, all subject to the same undercount — `FAILED_SWEEP_REVERSAL_LONG/SHORT` (117 real trades combined, currently SHADOW) is the biggest population affected; the "zero real fires yet" note this codebase previously carried about it is stale. Not yet fixed — `OPEN_DECISION real_trade_filter_mtm_exclusion_undercounts_20260914` scopes the real fix (distinguish "MTM because stale" from "MTM because that's the real exit," not another hardcoded setup-type list). Before trusting a `THIN_N`/`SUPPRESS` verdict for any timeout-exit-style setup, check its real resolution_method breakdown directly rather than trusting the pipeline's own real_n at face value.


<a id="hr-013"></a>

- **A "own poller, stateless by design" detector's in-memory poll-skip cache (the pattern used by `pocRotationJoinDetector.js`, `globexFlushDetector.js`, `rthFlushDetector.js`, `minuteBarSignalDetector.js`, `majorPivotDefendedBreakDetector.js`, `stallDefendedLevelDetector.js`) can insert a real signal hours (even 10+) after it actually fired, correctly timestamped but freshly inserted — whenever a server restart wipes that cache mid-session.** This isn't a data-corruption bug (`fired_at`/P&L are computed correctly from real historical bars) — it's a genuine detection-latency gap: the row simply didn't exist in the database until the next successful poll after restart, so a live viewer checking in the gap between the real fire and the restart would correctly see nothing. Found 2026-09-14/15 (user: "I only saw 3 trades by 9:30, why do I see more now") — two real examples landed exactly at a restart timestamp, one 11 hours late, one 6.7 hours late. Fixed the visibility side: `GET /api/setups/today` now returns `late_backfill_min` (`created_at - fired_at` in minutes, computed in SQL since both are the same naive-timestamp column type) and `quick-check.html` shows a `⏱ Nh late` badge inline whenever it exceeds 5 minutes, so a late-arriving row never silently masquerades as a live one. **Not fixed structurally** — `OPEN_DECISION poller_late_backfill_display_gap_20260914` tracks the real fix (persist each poller's watermark to the DB instead of memory) if it's ever worth doing; the display fix resolves the user-facing confusion regardless.

- **A WSL2→Windows-host TCP connection to the host's real LAN IP can silently reset the instant data flows, even though the bare TCP handshake succeeds — use the WSL2 NAT gateway IP (`ip route show | grep default`, e.g. `172.27.192.1`) instead.** Found 2026-09-28 building the Sierra Chart DTC client: `192.168.4.178:11099` (the Windows host's real LAN IP) completed the TCP handshake cleanly every time but reset (`ECONNRESET`) the instant the first protocol bytes were written — a classic hairpin-NAT signature (traffic leaves via the LAN adapter and loops back in, and Windows Firewall's stateful inspection loses track of the session once real payload flows). Switching to WSL2's own default-route gateway IP (`172.27.192.1` in this case) fixed it immediately, zero code changes. This is a standing WSL2 networking gotcha, not specific to DTC/Sierra Chart — check this before assuming a "handshake succeeds, then resets on data" failure is a protocol bug when the target is a service running on the Windows host itself.


<a id="hr-016"></a>

- **This host is WSL2 on a machine that sleeps — a machine sleep/power-off is a FULL outage of the entire Linux environment, not just this one Node process, and it can last hours with zero warning in any app-level log.** Confirmed 2026-09-15 (`dmesg -T` showed the kernel itself only booted ~07:12 that morning, `uptime` showed the whole VM alive <1hr, journal reported "corrupted or uncleanly shut down") — an ~8 hour stretch (≈23:00-07:07 ET) where literally nothing was running: no polling, no detection, no health-monitor, nothing. `journalctl --user -u trading-journal-server.service` alone won't show this — its last entries before the gap look like an ordinary shutdown-adjacent silence, not an outage; the tell is a `Started` line with NO preceding `Stopped` line (the previous instance never got the chance to run its own shutdown), cross-checked against `dmesg -T`/`uptime` for the actual host-level boot time. Since this system is built around continuous overnight Globex monitoring, treat "the machine might sleep overnight" as a standing, real operational gap — not fixable in code (Windows power-settings / always-on hosting is the actual fix), but worth knowing before assuming any overnight silence in the logs means "nothing happened" rather than "nothing COULD happen."

- **A `./restart.sh` or `./start.sh` invoked via a backgrounded Bash tool call that hits ITS OWN tool-level timeout can leave a real, live duplicate dev-mode server process running — even though the harness reports the call as "moved to background," not "failed."** Found 2026-10-11: a `./restart.sh` call exceeded the Bash tool's 120s foreground cap and got silently detached into the background — but the script had already run far enough to spawn its own full dev-mode chain (`start.sh` → `npm run server` → `scripts/dev-server-guard.sh` → `nodemon` → `node server/index.js`) before stalling. <a id="hr-036"></a>

See [docs/HARD_RULES_DETAIL.md#every-pending-decision-gets-recorded-via-flagdecisionmjs](../../docs/HARD_RULES_DETAIL.md#every-pending-decision-gets-recorded-via-flagdecisionmjs). **A slug's name can go stale even while its content stays accurate — when re-flagging an existing decision with `flagDecision()` grows its scope well past what the slug originally named** (found 2026-09-07: `nl30_regime_conditioning_needs_recalibration_20260907` was updated 3 times as more stale sizeMultiplier factors were found, until the slug — still NL30-specific — was actively misleading about a thread that had grown to cover 9 unrelated factors; NL30 itself had been done for hours by the time this was caught, only because the user said "I thought nl30 was done"), **resolve the old slug with a note explaining the rename and flag a fresh one that names the current scope**, rather than let an accumulated decision keep growing under its original narrow name. Caught by noticing the mismatch between the prose and the mechanism, not by trusting either alone. **When triaging the open-decision backlog, read a candidate's `notes.status` field directly (or check whether it appears in `--list`'s PENDING-only output) — don't take a decision's own narrative tone as proof of its mechanical state.** A related risk found the same pass: that decision's own text also named a real, still-unfinished follow-up thread (a DeepSeek dispatch with no response file anywhere) — resolving the parent without splitting that out first would have silently lost it. Split it to its own fresh slug before resolving the parent.


<a id="hr-037"></a>

See [docs/HARD_RULES_DETAIL.md#a-verified-code-comment-is-not-itself-verification](../../docs/HARD_RULES_DETAIL.md#a-verified-code-comment-is-not-itself-verification) for the `DEFAULT_DPP=5` incident (25 setup_types calibrated wrong before it was caught) and a 2nd confirmed instance (`momentum_against_fade_shadow`'s own header comment claiming Globex validation that didn't hold up on re-check).


<a id="hr-038"></a>

- **`computeRigor()`'s 3-way chronological "stable" check can mislead on thin, day-correlated real-trade populations — a third's own mean can be carried by 1-2 unusual days, which the separate `top5DayPct`/`clustered` check does NOT catch (that measures concentration across the whole population, not within one third).** Prefer `dayBlockedBootstrapCI()` (day-blocked resampling) over the tercile check when a finding actually matters enough to act on — it directly tests whether the CI on the quantity of interest excludes zero, which "stable across 3 thirds" doesn't. See [docs/CONVENTIONS_DETAIL.md#computerigors-tercile-stable-check-can-mislead-on-thin-day-correlated-data](../../docs/CONVENTIONS_DETAIL.md#computerigors-tercile-stable-check-can-mislead-on-thin-day-correlated-data) for the incident (a "stable" Globex finding that a proper bootstrap showed was pure noise) and `OPEN_DECISION computerigor_tercile_stability_check_methodology_flaw_20260916` for the still-open fix.


<a id="hr-039"></a>

- **On this roster, any "momentum/order-flow/price-position running against a fade's own direction" signal validated in RTH should be assumed to REVERSE, not just weaken, when tested in Globex** — confirmed independently 5+ separate ways in one session (VWAP position, VWAP slope, single-bar order-flow at 4 window sizes, volume-z-scored order-flow, and momentum-against-fade's own re-derivation). Real structural difference behind it: Globex runs ~15% of RTH's per-bar volume but is *more* net-directional on average (higher trendiness ratio), not just quieter. Don't adapt an RTH-validated directional-pressure signal to Globex by loosening numbers or narrowing the time window — test it in Globex from scratch and expect a real chance it points the opposite way. See [docs/CONVENTIONS_DETAIL.md#globex-reverses-against-the-trade-directional-pressure-signals-for-this-roster](../../docs/CONVENTIONS_DETAIL.md#globex-reverses-against-the-trade-directional-pressure-signals-for-this-roster).


<a id="hr-040"></a>

- **When a script both computes a derived value (a sweep, a classifier, an optimizer) and separately stores/prints a number labeled as describing it, that pairing needs a standing check** — a feature added on top of an existing field can silently break the field's own meaning without anyone touching the field's line. When you add a smarter computation on top of a value a field already claims to describe, either rewire that field in the same commit or explicitly rename/re-scope it — and if the value is trusted enough to sort/display/gate anything, add an invariant check that re-derives it via the real function, not a plausibility check a bug could trivially satisfy. See [docs/HARD_RULES_DETAIL.md#derived-value-field-drift-when-a-smarter-computation-is-added](../../docs/HARD_RULES_DETAIL.md#derived-value-field-drift-when-a-smarter-computation-is-added) for the `ev_per_trade` incident this names.


<a id="hr-041"></a>

- **Auditing a backtest's simulation logic is not the same as auditing where its baseline comes from — a comparison is only as trustworthy as its least-audited side.** When building or auditing any script that claims "config X beats baseline Y," verify baseline Y was computed by the exact same method as X in the same pass — a stored/precomputed number read from elsewhere, even one that looks authoritative because it's "the live value," needs the same scrutiny as the thing being tested against it. See [docs/HARD_RULES_DETAIL.md#baseline-must-be-computed-the-same-way-as-the-candidate](../../docs/HARD_RULES_DETAIL.md#baseline-must-be-computed-the-same-way-as-the-candidate) for the incident this reversed a finding on.


<a id="hr-042"></a>

- **A backtest comparing two conditions against a shared, unchanging exit needs to rule out a structural/algebraic advantage before crediting the "smarter" condition with the win.** When a new backtest's two arms differ in WHEN they enter but share the same exit levels, add an entry-price-only control arm (no "smart" filter, just the later/different entry) before trusting that a filter/pattern/signal explains an EV gap — the gap may be entirely explained by the entry price itself. See [docs/HARD_RULES_DETAIL.md#structural-advantage-control-in-comparison-backtests](../../docs/HARD_RULES_DETAIL.md#structural-advantage-control-in-comparison-backtests) for the overshoot-entry incident (~$77/trade of an apparent edge was actually ~$6).


<a id="hr-043"></a>

- **When a backtest script's overfitting guardrails get tightened and re-run, anything that no longer survives needs its OLD `performance_audit` row explicitly deleted, not just left unrefreshed by the new run.** When re-running a script with stricter/different guardrails, explicitly query which prior rows for that `signal_type` are NOT in this run's fresh output and delete them (or diff on a marker field the new version writes that the old one didn't) — don't assume `ON CONFLICT DO UPDATE` alone keeps the table consistent, since it only touches rows the new run actually produces. See [docs/HARD_RULES_DETAIL.md#delete-stale-rows-when-guardrails-tighten](../../docs/HARD_RULES_DETAIL.md#delete-stale-rows-when-guardrails-tighten).


<a id="hr-044"></a>

- **A backtest candidate grid needs a floor derived from the underlying DATA'S OWN RESOLUTION, not just statistical overfitting guardrails** (thin-tail/plateau/OOS/rigor) — those catch overfitting to a few trades, not overfitting to a precision the data cannot actually resolve. Before trusting ANY backtest whose candidates are themselves a distance/time/price granularity (a trail width, a tick-level threshold, a sub-bar timing window), check that granularity against the data's own real resolution — a candidate finer than what the underlying data can distinguish will pass statistical guardrails by construction, since the "noise" it's exploiting is measurement noise, not market behavior. See [docs/HARD_RULES_DETAIL.md#backtest-candidate-grid-floor-from-data-resolution](../../docs/HARD_RULES_DETAIL.md#backtest-candidate-grid-floor-from-data-resolution) for the sub-bar-noise trailing-stop incident.


<a id="hr-045"></a>

- **The cell a grid search picks as "best" needs its OWN day-clustering/mean-median/chronological-split check, at its exact population and its exact real-dollar simulation — checks run on the raw forward-return population, a different threshold/population, or only one dimension of a multi-dimension grid do NOT transfer.** Found 2026-09-10 (DeepSeek design review): a "35/35 cells beat placebo" climactic-acceleration-reversal result looked decisive, but the winning cell (picked from a 7-hold x 5-target grid) had never itself been day-clustering-checked or chronologically half-split — only the raw Phase 1 forward-return population had been. Applying the same lens retroactively to `STALL_DEFENDED_LEVEL` (shipped live the same session) found the identical gap: after a mid-session threshold correction changed the population, only the WINNING hold value (210min) was re-swept against targets — the full hold grid was never re-run on the corrected population, so there's no way to tell if 210min is a smooth, robust choice or a lucky spike in a jagged neighborhood (the majors' own threshold-sensitivity sweep is the model to match — a 5-point sweep across the parameter, not a single re-verified point). **A related trap in the same family**: an EV that resolves mostly via stop-out or time-exit (not the target) means the "target" in "target/hold grid" is barely being tested at all — check the stop%/target%/time% breakdown at the winning cell before treating the target choice as validated.


<a id="hr-046"></a>

- **A "catch rate" / "capture rate" claim built on a loose time-window match (a signal counts as catching an event if it fired anywhere in a wide window before or after) can be a matching artifact, not a real capture, whenever the underlying strategy has a high stop-out rate or resolves faster than that window.** Found 2026-09-10: a "climactic acceleration reversal caught 53.6% of real Globex 300+pt moves" claim used a 24h-before/1h-after match window, but the strategy itself stops out 67-89% of the time and resolves in 120-960min — so a signal could count as "catching" a move while the position it would have opened had already been stopped out hours before the move even started. The real question ("was a position still open, correctly-directioned, and alive when the event happened") was never asked. Before trusting any X%-catch-rate number, check whether the match window is wide enough relative to the strategy's own resolution time that a stopped-out or already-closed signal could still count as a "catch."


<a id="hr-047"></a>

- **A pooled before/after comparison across a fix's deploy timestamp does not tell you whether the fix actually engaged — split by which code branch the fix's own guard condition took, not just aggregate P&L, before calling it fixed.** Found 2026-09-22: `sortedCandidates`' EV-ranking fix (commit `fc0e37b`, 2026-09-20) added a `real_n>=20` conditional — prefer real SETUP_STATUS EV when a candidate's setup_type has enough real trades of its own, else silently fall back to the old, already-known-unreliable `UNIFIED_BACKTEST` source that caused the original problem. `OPEN_DECISION rth_cluster_primary_underperforms_siblings_20260922` was marked resolved same-session based on a 2-day pooled post-fix average that looked better (primary flipped from -$4.64/trade to +$7.40/trade) — **premature, and wrong**. The user pushed back ("even today is a stark difference"); splitting that SAME post-fix day by whether the picked candidate's setup_type actually cleared the `real_n>=20` bar showed the fix only engaged for a minority of touches (this roster has 180+ largely-thin setup_type variants, e.g. the OR5/10/15/30×HIGH/LOW/MID family alone is 18 near-duplicates) — candidates that cleared the bar were roughly break-even (primary $1.55 vs sibling $19.88), candidates that didn't were nearly as bad as pre-fix (primary -$30.76 vs sibling +$50.77). The pooled post-fix average looked better purely because it mixed a genuinely-fixed minority with an as-bad-as-ever majority — a classic Simpson's-paradox-shaped trap specific to "prefer new/real source when available, else fall back to old/synthetic source" fixes, which this codebase builds constantly (`OPTIMAL_STOP`'s real-vs-synthetic fallback, `DAY_TYPE_ALPHA`'s real_n gating, GARCH's roll-week pause, dozens of `getCached()`-style real-vs-fallback reads). **Whenever verifying a fix of this shape, check outcomes split by which branch actually executed in each case, not just a pooled before/after average** — a fallback branch that's still the common case can hide behind a pooled improvement contributed entirely by the minority that cleared the bar. See `docs/OPEN_THREADS.md`'s 2026-09-22 entry for the full incident.


<a id="hr-048"></a>

- **A `curl localhost:3002/...` check only verifies a fix if the live server process has actually restarted since the edit — check process uptime (`ps -p <pid> -o etime`) before trusting a "verified live" claim, don't assume nodemon picked up the change.** Found 2026-09-14: the live dev server had not actually restarted in hours despite many committed edits that session — nodemon wasn't picking up file changes as expected, for reasons not root-caused (not a `.nodemonignore` scoping issue that was checked). Discovered by accident (checking uptime for an unrelated reason), which means any earlier same-session claim that something was "verified live" via a localhost curl check — before that discovery — may have been silently testing stale, pre-fix code in the actual running poller, not the fix at all. Fixed by running `./restart.sh` (never kill/restart processes by hand — see the single-instance server-lifecycle rule above) to force a real restart before trusting the next check. **Before treating any `curl localhost:3002`-based check as confirmation a fix is live, confirm the server process's own start time postdates the edit** — a passing curl check proves the server responded, not that it's running the code you just wrote. **Corollary, found 2026-09-16: when a bug lives in code a live background poller calls on a schedule (every ~15s), restart the server BEFORE cleaning up any data the bug corrupted, never after.** Cleaning up first left a window where the still-running OLD process (unaware of the fix, still polling every 15s) immediately re-corrupted ~200 fresh rows before the restart could take effect — caught only by re-checking the contamination count after the "fix," not assumed clean. The correct order for this shape of fix is: patch the code → restart → verify the process postdates the edit → *then* run the data cleanup/backfill, so nothing still-running can re-dirty what you just cleaned.


<a id="hr-049"></a>

- **Check for frontend render errors before calling any frontend change done.** Run `npm run lint:frontend` (ESLint `no-undef`, catches missing-import/undefined-variable `ReferenceError`s) and `npm run build` (catches broken import/export paths and esbuild-level errors lint won't). Also check `scratch/gemini_alerts.txt` / `scratch/server_errors.jsonl` for `[CLIENT_ERROR]` entries. If real browser/Playwright tooling isn't available, say so explicitly rather than claiming an interactive check was done — static checks confirm nothing throws on load, not that a specific interaction behaves correctly. `.claude/hooks/post-edit-lint.sh` runs single-file lint on every touched file as a fast real-time layer underneath this — it does NOT replace the full `npm run build` + browser-check gate (single-file lint can't see cross-file import/export breaks or interaction bugs). See [docs/HARD_RULES_DETAIL.md#check-for-frontend-render-errors-before-calling-a-change-done](../../docs/HARD_RULES_DETAIL.md#check-for-frontend-render-errors-before-calling-a-change-done).


<a id="hr-050"></a>

- **When auditing or fixing a frontend component for accuracy/efficacy, confirm the component (or the specific branch/section within it) is actually reachable in the live app BEFORE trusting that fixing it matters — a real, correctly-fixed bug in unreachable code fools both an external reviewer and the person applying the fix.** Found 2026-09-28 (main-dashboard statistics audit, DeepSeek Batch 1b): `SessionForecastPanel.jsx`'s "Session Volatility"/"Setup Anticipation" Intel section had 3 real HIGH/MEDIUM findings (hand-typed WR% literals, N-floor below the decisive rule, hardcoded fallbacks) — all genuinely fixed and verified clean — but the component is only ever mounted once in the live app (`ACDView.jsx`, `section="scripts"`), which structurally skips the exact `section !== 'scripts'` branch that content lives in. Neither DeepSeek's review nor Claude's own first pass caught this; it only surfaced because a live Playwright render check came up empty for that section's own text, prompting a `grep` for every JSX mount site. **Before or while auditing a component's accuracy, `grep` for every place it's actually rendered with `<ComponentName` (not just imported) and trace any prop-gated branch (a `section`/`variant`/`mode` prop) to whichever value real call sites actually pass — a component that exists, compiles, and fetches real data can still be dead weight if nothing ever mounts the branch containing it.** This is a standing risk for the rest of this same audit initiative (Batch 1c, Batch 2, and retroactively Batch 1a) — check it for each, don't assume "it's imported somewhere" is sufficient.


<a id="hr-051"></a>

- **Whenever a change touches data-fetching — a new component with its own `fetch`/poll, a new or modified API endpoint, or edits to an existing one on a hot path — verify actual loading performance before calling it done, not just that it renders without errors.** "No console errors" and "actually fast" are different claims this codebase has repeatedly conflated. Using Playwright:
  1. **Count and list actual network requests** (`page.on('request', ...)`, filter to `/api/`) — group by endpoint and flag anything firing more than once per load. `grep` the exact URL string across `src/` before adding a new fetch of something that sounds "already available elsewhere."
  2. **Time the actual settle point**, not just first paint — watch the page's loading indicator until it hits zero, not just `domcontentloaded`.
  3. **For any new/modified endpoint, `curl` it standalone** (`-w "%{time_total}s size=%{size_download}\n"`) and compare against its cost *inside a real concurrent page load* — a large gap means connection contention or a pile-up, not a slow query.
  4. **If a response is unexpectedly large, check the query is actually bounded** — this codebase has repeatedly found genuinely unbounded historical queries hiding behind code that looked bounded at a glance.
  Don't run this full checklist for every one-line change, but any change adding a fetch, a component on Morning Prep/Trades, or touching a known-hot endpoint gets it. See [docs/HARD_RULES_DETAIL.md#verify-data-fetching-performance-not-just-no-errors](../../docs/HARD_RULES_DETAIL.md#verify-data-fetching-performance-not-just-no-errors) for the concrete incidents (51MB unbounded response, N+1 firing 18x, a 16x request multiplication) this checklist was built from.

- **Verifying a statistical split is real is not the same as verifying the classifier that produced the split is valid.** A backtest that conditions setup EV on a newly-invented regime/classification (not an existing, already-computed field) can pass every rigor check this codebase uses while the classifier itself is still an arbitrary construction — window lengths/cutoffs picked semi-informally, never sensitivity-tested, never checked for independent predictive power, never adjusted for the multiple-comparisons surface of testing several regime schemes against dozens of setup_types at once. A plausible economic narrative for why a split makes sense is not validation either. Before trusting a *newly-built* classifier's conditioning effects, validate the classifier's own parameter robustness and independent predictive power first. <a id="hr-059"></a>

- **A frontend exclusion filter shaped `row.field !== someLiteral` silently becomes a no-op the instant a backend query's `SELECT` stops returning `field` — `undefined !== someLiteral` is always `true` in JS, so the filter passes every row through with zero error, zero warning.** Found 2026-09-22: `getDecidedRows()` (`quick-check.html`) correctly checks `s.is_cluster_primary !== false` to exclude confluence-cluster-sibling rows from the Performance card's account-level Net/N/Max-DD, exactly per the standing `is_cluster_primary` hard rule below — but `GET /api/setups/range-summary` (`server/routes/acd.js`) never selected `s.is_cluster_primary` in its SQL, so every row the frontend received had that field permanently `undefined`, and the exclusion silently stopped excluding anything. This reintroduced the EXACT double-counting bug the 2026-09-08 fix closed — displayed Net swung from a real -$68 to a displayed +$286 (N=21 vs N=33) before being caught. Distinct from the existing `is_cluster_primary` rule below (that one is about a *new query forgetting to write the filter logic at all*) — this is about an *existing, correctly-written filter* silently breaking because the backend's column contract quietly changed out from under it, which is a more general JS footgun: any frontend `!== `/`===` exclusion check against a backend-sourced field is only as safe as the backend's guarantee that the field is always present. When touching any endpoint's `SELECT`/column list for any reason, grep the frontend consumer(s) for every field-equality check against that endpoint's response shape before considering the edit safe.


<a id="hr-060"></a>

- **A script using the `main().then(() => process.exit(0))` idiom needs every async call inside `main()` explicitly `await`ed — an un-awaited call races the process exit and can silently drop its own work with zero error, while the script's own console output falsely confirms success.** Found 2026-09-22 (user asked "weren't we recalibrating daily now?", which is what prompted checking whether the write was actually landing): `recalibrate_ml_walkforward.mjs` called `recordClaim({...})` without `await` — `main()`'s own returned promise resolved immediately after the synchronous `console.log('Claim recorded.')` right below it, and `main().then(() => process.exit(0))` then killed the process while the `INSERT` was still in flight. This is a **race, not a guaranteed failure** — the one prior manual run happened to land (the DB round-trip won the race that time), which is what made the script look correct until a slower run exposed it: a re-run printed fresh N=263/tighter-CI numbers to the console, but a direct query of `performance_audit` immediately after showed the stale N=113 row, completely unchanged. Fixed by adding the missing `await`; checked the 3 sibling `recalibrate_ml_*.mjs` scripts and all 3 already awaited their own `recordClaim()` calls correctly, so this was isolated to one file, not systemic — but the idiom itself (`main().then(() => process.exit(0))`) is used by many one-shot scripts in this codebase, and every one of them is a candidate for this exact silent-drop bug if a future edit adds a new async call inside `main()` without awaiting it. When writing or reviewing any script with this shape, grep every call inside `main()` for a missing `await` before trusting a "success" console line — the log message and the actual DB state are two different claims, and only one of them is authoritative.

<a id="hr-062"></a>

- **A `dayBlockedCI()`-shaped function's own point estimate (average of each day's own mean, every day weighted equally) is a DAY-WEIGHTED mean, not sum(pnl)/N — using it as "$/trade" to compare two SPLIT subgroups with different trades-per-day distributions silently inflates (or deflates, or even sign-flips) the apparent effect.** Found 2026-10-12 (DeepSeek design review): a same-night POC_ROTATION_JOIN stochastic-filter test reported EXTENDED mean=$27.04 vs NOT-EXTENDED mean=$72.62, delta=-$45.58/trade, holding in both chronological halves — looked like a real, rigorous finding. DeepSeek independently recomputed from the saved row data and found the REAL per-trade numbers were EXTENDED $16.43 vs NOT-EXTENDED $27.72, delta=**-$11.29**, CI=[-$35.00,+$9.17] (crosses zero) — and the "holds in both halves" claim reversed too: per-trade delta was -$25.39 in the first half, **+$2.73** in the second (sign flip). Root cause: this population has a steep real gradient (quiet 1-trade days average +$204.8/trade, busy 6+-trade days average ~$1/trade), and NOT-EXTENDED happened to cluster on the quiet, high-pnl days — day-weighting (treating each day as one vote regardless of trade count) handed that arm's mean a boost that sum(pnl)/N never would have. **This is NOT a bug in `dayBlockedCI()`/`dayBlockedBootstrapCI()` itself** — day-weighting is the CORRECT, deliberate choice for a single population's own CI (it's this codebase's standing convention, used everywhere, specifically to stop one correlated day from dominating a trade-weighted average) — the bug is specifically in using that SAME function's point estimate as the headline "$/trade" number when COMPARING two arms of a split that don't have matched day-count distributions. A PAIRED comparison (same events, same days, two different rules simulated on each — e.g. the already-shipped `poc_rotation_breakeven_hold_100pt_stop_20261008` validation) is NOT subject to this, since both arms share identical day composition by construction; a SPLIT comparison (two different subsets of events, classified by some filter) is exactly where this bites. **Before reporting a split-comparison's headline number as "$/trade," report sum(pnl)/N (the real per-trade mean) for each arm, and use day-blocking only for the delta's confidence interval (resample days, pool trades from resampled days per arm, compute the per-trade mean difference) — never for the point estimate itself.** This pattern (the `dayBlockedCI()` shape, copied from `poc_rotation_breakeven_hold_20261008.mjs`'s own scaffolding) was reused in at least 2 other scripts the same night (the EMA-alignment test, the stochastic test) — any future split-comparison script copying this scaffolding needs the per-trade-mean fix applied, not just the day-weighted CI.

The user independently spotted the same confound from a completely different angle — `quick-check.html`'s Declustered 30-day chart showed a steep early drawdown fully masking a real +$10,197.80 recovery since 2026-09-01, which a single pooled 30-day number (-$894) obscured entirely. This is a distinct risk from the already-documented "pooled verdict hides opposite-signed subgroups" convention (that one is about a market/structural variable like day-type or session; this one is about **the detector/roster mix itself not being the same thing at the start and end of the window**) — this codebase ships new setup_types and recalibrates/suppresses existing ones on a near-weekly cadence (see the extensive "Where to look" history above), so any future multi-week pooled read is a real, standing candidate for this exact confound. Before trusting a pooled backtest/validation number as representative of "how things are now," check whether the setup_type roster (or any other live mechanism the number depends on) materially changed within the window — a quick `GROUP BY date_trunc('week', fired_at), COUNT(DISTINCT setup_type)` is enough to catch it. See `docs/OPEN_THREADS.md`'s 2026-09-22 entry and `RESEARCH_CLAIM ml_walkforward_roster_churn_confound_20260922` for the full numbers. **The same confound recurs at same-day timescale, not just multi-week** — found 2026-09-28, while `SUPPRESS_ALL_DISABLED` was actively promoting an unusually large batch of normally-suppressed setup_types into real N-credit: a user question about OFP's (`touch_orderflow_pressure_shadow`) daily accuracy came back looking bad (following its `wouldSkip` calls that day would have cost $318 vs. letting every trade ride) — but that day's trade population itself was anomalous (most real fires traced directly to the flag, not the normal roster), so the bad-looking accuracy number says more about the unusual population than about OFP's own calibration. Same root shape as the roster-churn confound above, just triggered by an active override flag instead of weeks of organic roster growth. **Any same-day live-metric check (a shadow-tag's daily hit rate, a Collapsed-vs-Declustered comparison, a Live-vs-All split) computed while a broad live-eligibility override (`SUPPRESS_ALL_DISABLED`, `ALL_LEVELS_LIVE`, or any future one) is active needs the same caveat a multi-week pooled backtest does — check whether the override materially changed that day's population before trusting the number as representative,** not just when explicitly asked about the override itself.

- **A later unconditional force-SHADOW/pause override in a live-eligibility chain silently wins over every earlier check — including a future, broader override that hasn't been written yet.** `detectGlobexSetup()`'s candidate loop (and the RTH main path, and `shadowCandidates`) chains multiple sequential overrides (`crossDirectionCooldownMin`, `isPostWinOppositeFamilyBlocked`, `isOppositeDirectionOpen`, `isSameSetupRefireBlocked`, and — until 2026-09-28 — a `GLOBEX_PAUSED` block) that each conditionally force `SHADOW`. **Found 2026-09-28**: `GLOBEX_PAUSED`, added 2026-09-16 as a discretionary pause (explicitly NOT based on a proven negative-EV finding — the real numbers at the time were flat/positive for Globex), sat as the LAST check in that chain and unconditionally overrode anything earlier, including `SUPPRESS_ALL_DISABLED` (added 2026-09-25, "move everything to live for the time being") — so that flag going live never actually reached Globex at all, for 3 days, invisibly (confirmed live: 100% of a real overnight session's 15 Globex fires were still force-`SHADOW`, 8 explicitly tagged `GLOBEX_PAUSED`). It was never logged in this file either, unlike almost every other override in this codebase, which is part of why the interaction went unnoticed. **Before adding a new global pause/override to any live-eligibility chain, grep every OTHER override already in that same function/chain and check the ORDER they're applied in — a later one always wins regardless of stated intent, and this needs re-checking again every time a NEW broad override (like `SUPPRESS_ALL_DISABLED`) is added elsewhere, not just when the override chain itself is edited.** A companion override existed for the same reason in `globexFlushDetector.js`'s separate `GLOBEX_FLUSH_*` insert path (added by DeepSeek review the same day as the original pause) — both removed together once found; see `docs/OPEN_THREADS.md`'s 2026-09-28 entry for the full incident.


<a id="hr-065"></a>

- **A broad override's own already-written documentation states its exclusions for a reason — a "promote regardless of X" simplification must be cross-checked against that documentation before shipping, not assumed safe because the user approved simplifying "the scope" in general.** `SUPPRESS_ALL_DISABLED`'s own header comment (and the CLAUDE.md "Where to look" entry) already explicitly stated it does NOT bypass "any risk-discipline gate ... same-type refire ... opposite-direction conflict" — but a same-night fix wiring it into `acd.js`'s "suppressed near-level audit" branch (a location with SEVERAL different suppression reasons landing in one place, not just one) promoted a candidate regardless of WHICH reason applied, including `SAME_TYPE_REFIRE_COOLDOWN` and `CLUSTER_ALREADY_FIRED` — both exactly the family of gate the flag's own docs already excluded. **Found live 2026-09-28, ~50 minutes after shipping**: `FLOOR_S3_FADE_LONG` fired `ACTIVE` 9 times in 6 minutes as price drifted slowly through the level, each fire a real, avoidable refire-cooldown violation (no dollar harm this time — no real order-placement is wired to `origin_status` yet, all 9 resolved `INVALIDATED` — but a real false-live-signal window on the user-facing dashboard). The mistake wasn't re-litigating an already-settled call — an earlier exchange in the same session ("Its fake capital"/"Simulation") had genuinely established the STAKES were low enough not to hand-pick individual `SETUP_STATUS`-driven suppression reasons one at a time — but that conversation was about SETUP_STATUS-style reasons specifically, and got silently generalized to EVERY reason variable in scope at that insert site, including ones with a completely different provenance (real-time dedup discipline, not a calibration verdict) that the flag's own documentation had already, separately, explicitly carved out. **Before writing a "uniform"/"regardless of reason" version of any override-consuming logic, re-read that override's own already-written scope/exclusion list first and partition the reasons in scope at THIS call site against it explicitly** — a multi-reason call site (several different `suppressReason`/gate-name values funneling into one check) is exactly where a "simplify by promoting regardless of which one" shortcut silently reintroduces something the override's author already thought through and excluded elsewhere. Fixed via a `PROMOTABLE_SUPPRESS_REASONS` allowlist (only the 2 genuinely `SETUP_STATUS`/`SETUP_STATUS_DOW`-driven reasons) at that one call site — see `docs/OPEN_THREADS.md`'s 2026-09-28 entry (bug #6) for the full incident and which reasons ended up on which side of the line. **A deeper, more subtle version of the SAME class of bug was caught the same night by an independent DeepSeek code review of that very fix, before it caused live harm**: the allowlist gated on `suppressReason`, a single COLLAPSED string from a precedence ternary (`clusterAlreadyFired -> sameTypeRecentlyFired -> _suppressedSetups -> _dowSuppressToday -> isS2DoubleCounter -> isTrendCounterFade -> SUPPRESSED_OTHER`) — a candidate that was simultaneously `SETUP_STATUS`-suppressed (or DOW-suppressed) AND `S2_DOUBLE_COUNTER`/`TREND_COUNTER_FADE` collapsed to `'SUPPRESSED_FADE'`/`'DOW_SUPPRESSED'` (on the allowlist), silently promoting it past a directional risk gate the ternary never even reached for that candidate — the exact same "promote past a risk-discipline gate" failure shape, just hiding one layer deeper, behind a precedence-ordered string instead of an unscoped allowlist. **A collapsed multi-reason classification string (a `suppressReason`/`skipReason`/`gateName`-style variable built from an if/else-if precedence chain) is NOT safe to gate a promotion/bypass decision on, even with a correctly-scoped allowlist of its possible VALUES — always gate on the underlying independent boolean flags directly when they're available**, since the string can only ever report the FIRST reason that matched, silently hiding every other reason that would also have applied to the same candidate. Fixed by adding the independent `s2Double`/`trendCounterFadeFlag` booleans (already computed once per poll) to the promotion check directly, on top of the string allowlist. See `docs/OPEN_THREADS.md`'s 2026-09-28 entry for the full DeepSeek review writeup.

- **A broker/exchange-level aggregate resource (account position, balance) is never attributable to a specific strategy/setup once more than one logical position can share the same real account+instrument — never use it as an attribution or decision oracle, only as a fail-closed cross-check that halts on disagreement.** Found 2026-09-29 (the first night the Sierra Chart DTC order-placement system traded for real): `placeExitOrder()`'s fallback asked the broker for the account's aggregate position on `MNQZ6.CME` (every setup this app trades shares that one instrument) whenever its own fill record read a possibly-stale zero, and attributed the result to whichever setup was being checked. DTC's `POSITION_UPDATE` is keyed by (symbol, account) with zero concept of "which strategy" — confirmed via DTCProtocol.h, no protocol feature exists to change that. Real, confirmed consequences: a BUY exit submitted for a BUY/long entry (doubling the position instead of closing it), and a flatten for "quantity=2" attributed to a setup whose own entry never filled — misattributing a completely different setup's real position. The fix, DeepSeek-reviewed: per-order fill tracking (matched by a setup-scoped ClientOrderID) is the only legitimate attribution source; a real DB-enforced singleton "one position open, account-wide, at a time" invariant (a unique index on a constant expression, the standard Postgres one-row idiom) makes the aggregate safe to use for exactly one remaining purpose — a fail-closed cross-check that halts and flags loudly the moment the broker's real aggregate disagrees with what the app's own per-order records expect, never guessing or acting on it directly. **Any future system where multiple independent logical units (strategies, sub-accounts, algos) submit orders against a shared real account/instrument must apply this same discipline** — the aggregate tells you something is wrong, never which unit it belongs to.


<a id="hr-067"></a>

- **Never apply the latest-arriving async status update to a persisted record on a simple last-write-wins basis — a terminal/absorbing state must never be overwritten by a later out-of-order or confusing message.** Found in the same 2026-09-29 incident: `handleOrderUpdate()` applied whatever `ORDER_UPDATE` arrived last with no ordering or terminal-state protection. A real entry order's own final stored state showed `CANCELED` with `InfoText="Order cancellation failed | The order is no longer working and cannot be canceled"` — Sierra Chart's own message implies the order had already filled, but nothing protected a genuine `FILLED` confirmation (if one had briefly landed) from being overwritten by this confusing follow-up cancel-rejection message. Fix: a terminal-state lattice, not a timestamp comparison alone — `FILLED` is absorbing (nothing can move a row away from it, regardless of arrival order or timestamp); a `CANCELED`/`REJECTED` terminal state may only be *corrected* by a later real `FILLED` (never the reverse); a monotonic field like `filled_quantity` may only increase, never decrease, independent of status. A message's own timestamp (matched only against another timestamp of the same kind, never wall-clock time) is a secondary guard for genuinely non-terminal transitions only. **Any code applying an async status update from an external system (a webhook, a broker/exchange callback, a message queue with at-least-once/out-of-order delivery) needs this same lattice discipline** — `COALESCE`-style "apply whatever's non-null" or blind field-overwrite is not sufficient once a terminal state exists.


<a id="hr-068"></a>

- **Also from the same incident: a column that only ever stores the SINGLE LATEST message of an external event stream (not a sequence) makes forensic repair of a later-discovered bug impossible.** `order_placements.raw_last_order_update` was overwritten on every update; once the misattribution bug above was found, there was no way to reconstruct the true sequence of what had actually happened to the corrupted rows, because the intermediate messages were never kept. Fixed by adding a genuine append-only log table (one row per real message received) alongside the "latest snapshot" column. **Any new table that stores "the current state of X, derived from an external event stream" should default to also keeping (or being able to reconstruct) the full event history from day one** — a single overwritten "last known state" column is a standing forensic dead end the first time something needs debugging after the fact, and this is exactly the kind of thing that's cheap to add up front and expensive to retrofit after real data has already been lost.

- **A strict, fail-closed reconciliation halt on "any broker order unknown to this app" is only usable if the real broker account is kept free of unrelated resting orders — it does not distinguish "a real problem" from "old manual clutter."** Found live 2026-09-29, the first time `runReconciliation()`'s `unknownToApp` halt (`server/services/sierraChart/reconciliation.js`, "Item 1") ever ran against Sim1: 8 real, long-standing bracket orders on already-CME-expired contracts (`MNQU5.CME`/`MNQH6.CME`, `FreeFormText: "2TargetsWithCommonStop.twconfig"`) — clearly leftover manual/ATM activity on the sim account predating this app, not anything the app placed — immediately tripped the halt.
