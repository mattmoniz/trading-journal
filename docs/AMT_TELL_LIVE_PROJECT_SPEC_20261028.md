- "I'm not in front of the screen all day ... a forward tracker would be difficult. But what I can try is reviewing your trades if you fire this off in live, and I can see them in Sierra chart getting fired." Approved: **go ahead, use the DTC live account** (= the account currently logged on, `DTC_TRADE_ACCOUNT=DTC-Live-Simulator`, port 11199, the simulated Trading Evaluator account; VERIFY with `GET /api/sierra-chart/status` at the start, never assume). ## 2. Research state (all EXPLORE data, 2023-03..2025-05-16; hold-out after 2025-05-16 NOT extracted; every number is a hypothesis)

- Trade test (`PREREG_TRADE.md`, `run_trade.py`, `run_trade_output.txt`): V1 (stop behind n2's LVN, tell-fade exit after break) N=1,760, +1.93 per trade, CI -3.44..+7.62, beats the random-entry placebo p95 (+2.68 vs +1.97) and the moving-only control (+0.51); V2 (stop at the first LVN) -0.20; V3 (hold to the 15:55 flatten after the break) +7.29, CI -2.19..+17.30, total +10,158 over the explore period. V3 was chosen after seeing the results (selection caveat). The money is in the 18-22 percent that break the range (+120 to +130 per trade); the rest lose about -24 to -27. Stop distance median 26 pts, p90 80, max 338 pts (so up to about 676 dollars on 1 MNQ in the tail). Not a lead under the frozen reading.

## 3. The frozen rule to implement (parity with research code is the acceptance test)
Research code is the specification: `scripts/amt_vbars/vbars.py` (profile, nodes, ladder, flow, decision points), `trade.py` (tell evaluation every bar, LVN stop, management, stripped geometry), `PREREG.md` + Amendment 1 + `PREREG_TRADE.md` (definitions). Summary:
- **Bars:** 500-contract bars from ticks, exactly 500 with a trade that overflows SPLIT into the next bar (pro rata bid/ask), first bar of the session starts at the 18:00 ET open, bars run continuously to 17:00; last bar partial. Day profile = volume at price (0.25 bins) from 18:00 through the last completed bar.
- **Node:** Sierra-style peak (volume above each of the 3 bins either side, session extremes excluded) extended to the first bin at or below the profile's median volume of non-empty bins; nodes under 3 bins dropped, overlaps merged; node time = volume-weighted median bar index. **Left behind (d=+1):** node upper edge below the current close. **Ladder L** = longest chain of left-behind nodes (price order) with strictly increasing node times; L >= 2.
- **Tell (all five):** L >= 2; ACTIVITY A >= 1 (baseline mean seconds-per-bar of the same clock hour over the 20 prior sessions / mean of the last 10 bars); Q >= 0.4444 (share of the 9 consecutive bar-delta pairs flipping sign, last 10 bars); R >= 4 (reversals in the last 10 close-to-close changes); STRIDES (net progress last 20 bars positive and larger than the 20 before). Cutoffs 0.4444 and 4 are frozen from the explore screen.
- **When:** every completed bar ending 10:00-14:30 ET while flat; price still inside the combined range (no RTH bar closed beyond max(ONH, IBH) / min(ONL, IBL), IB included only after 10:30); one direction qualifying; one position at a time; re-arm after a bar with the tell false.
- **Entry** next bar open (+1 tick). **Stop** (user's rule): nearest-first left-behind nodes n1, n2...; LVN behind n2 = lowest-volume occupied bin between n2's far edge and n3's near edge (no n3: down to the day's extreme bin, extreme excluded); stop 1 tick beyond it; fixed at entry. **Management V3 (run live):** hold through the break, no tell-based exit, 120-minute time exit if there is still no break, flatten at the 15:55 open. **Also log the V1 outcome** (tell-fade exit after the break: ncomp <= 2) so the two stay comparable. 1 contract MNQ.

## 4. Proposed architecture (to be critiqued, `scratch/claude_request_deepseek.md`, response preserved as `scratch/deepseek_response_amt_tell_live_20261028.md`)
1. **Tick source:** tail the live Sierra `NQZ26.scid` in `/mnt/c/SierraChart-DTC/Data` (2-digit-year naming, prices stored at 1/100, validated layout handling in `scripts/tick_microstructure/extract_cells_20261020.py` and `scid_reader.py`; the contract per date comes from the contract calendar; roll weeks need handling). The app has NO live tick feed today (CLAUDE.md, 2026-10-20), so this is new infrastructure. Alternative: a DTC market-data subscription (untested here).
2. **Evaluator:** reuse the real research functions (rule "export the real function"): a Python sidecar process (pattern: `server/services/mlScoringServiceManager.js` with its stale-process reaper and the fail-closed banner) that imports `vbars.py`/`trade.py` logic, rebuilt from the raw file on every start (stateless, idempotent inserts) so a restart never loses or late-inserts a signal (see the CLAUDE.md "poll-skip cache can insert a signal hours late" rule: here the file is replayed, so fired_at is exact).
3. **Persistence:** own table `amt_tell_events` (every armed tell bar, decision bar index and time, direction, node list, stop price and its fallback flag, components met, entry, V1 and V3 simulated outcomes; append-only history), plus, for Stage 2, an `active_setups` row so the existing order pipeline (`sweepRealOrders` / `sweepExits`, the ONE place real orders are submitted) acts on it; never write new order-submission code.
4. **Display:** quick-check tag + a small endpoint; any new endpoint called from a `server/public` page needs the `~/.cloudflared/config.yml` ingress rule (check with the 302 test); the setup types need SETUP_DISPLAY_LABELS and direction inference (checklist item 6).
5. **Detector placement:** its own service file, never inline in `acd.js`; it must replicate the live-eligibility checks a standalone poller needs (`detectorLiveGates.checkStandardLiveGates`, checklist item 7) and sit in the dead-zone map (its 10:00-14:30 window avoids both dead zones).

## 5. Stages
- **Stage 1 (watch only, no orders):** build builder + evaluator + table + display; SHADOW rows only; the user compares the logged tells to their Sierra chart and reports whether "node" and "back-and-forth" match what they see. This IS the forward tracker, unattended. Exit criteria set by the review, not by feel; the floor for any judgement is the pre-registered 150 trades / 60 dates or the user's call to stop earlier for review.
- **Stage 2 (orders on DTC-Live-Simulator, only on the user's explicit go-ahead):** needs a user decision to exempt the setup from the `LIVE_ROSTER` gate (it fails closed for anything not demonstrated; this is not demonstrated) — flag it with `flag_decision.mjs`, do not exempt unilaterally; arming the kill switch is the user's call (the classifier also blocks arming), `DTC_AUTO_REARM_SAFE` is true on the simulated profiles so a restart re-arms on its own there, verify with `/api/sierra-chart/summary`; the risk question in §6 first.

## 6. Open questions the design review must answer, and what I would verify
1. **Tick source and bar builder correctness:** scid tail vs DTC market data; the 17:00-18:00 maintenance gap, session reset, contract roll mid-week, restart recovery, clock/timezone traps (CLAUDE.md lists five failure modes of naive timestamps), the legacy 1/100 price scaling, files that are not true ticks (28 of 564 explore dates were skipped for that reason).
2. **Parity test (acceptance):** replay a handful of historical days (including a roll week and a sparse day) through the live code path and byte-diff the tells, stops and V1/V3 outcomes against `run_trade.py`'s `trades_V1_explore.csv`; also compare live-built 500-bars with Sierra's own bars on the same day (the user can export or screenshot a chart) to measure the overflow-split assumption (how many bars differ, what it does to the tell count).
3. **Lifecycle modelling in the order pipeline:** how a fixed stop at an LVN, NO target, a 120-minute no-break time exit and a 15:55 flatten map onto `active_setups` + `sweepEntries/sweepExits` without new order code (`DESIGNED_TIMEOUT_EXIT_PREFIXES`, `setupExpiry.js` grace, `REAL_TRADE_FILTER`'s MTM exclusion, the `resolveSetupsByPrice` 1-minute bar walk, the fill-gate for resting orders); whether a far protective target must exist.
4. **Risk:** stop distance up to 338 pts (about 676 dollars on 1 MNQ); the account daily-loss gate (`dllGate.js`, `DTC_DLL_LIMIT_USD`), whether to cap stop distance (user gave no cap; a data-derived cap would be a new choice), one-position invariant, V3 selection-after-seeing-results, what to log so the V1/V3 choice can be re-judged.
5. **Look-ahead in the live build:** every feature must use only completed bars (node time and profile include the decision bar's own volume; the entry is the NEXT bar's open; a bar completes on the tick that fills 500 so the live entry is the first tick of the next bar, within ticks of the simulated open).

## 8. DeepSeek design critique, audited (2026-10-28; full text `scratch/deepseek_response_amt_tell_live_20261028.md`, also `scratch/deepseek_response.md` which has the thinking trace first and the four answers from line 246)
Rule applied: take each diagnosis, check it against the code, apply the house convention where its remedy runs softer or different. Changes to the plan, in order:
1. **Overflow-split assumption becomes a Stage-0 GATE, before any live tell is logged.** Accepted. Do it offline first: build the day's bars from the same ticks both ways (split vs whole trade) for explore days and measure how many bars differ and how the tell count and V1/V3 outcomes move; if the effect is negligible the question is moot, else ask the user to export one day of their 500-volume chart bars from Sierra and compare. Do NOT guess how Sierra treats an oversized trade.
2. **Replay must be bar-by-bar with each decision frozen at its own bar.** Accepted (matches the research code, which builds the profile only through bar i). Acceptance test = two-layer byte-diff: bar sequence first (times, OHLC, cumulative volume, per-bar 500 check), then decision tuples (session, bar index/time, direction, node list, stop LVN + price + fallback flag, the five component values, entry, V1 and V3 outcomes), 20-40 edge-chosen days (roll week, half-session, 17:00-18:00 touch, DST day, window edges, re-arm sequences, a day with an oversized trade). Snapshot the file offset, replay to it, then tail. Hash completed bars per session; alarm on file shrink or compaction, on a bar whose tick count is not 500 (except the last), and on host-clock vs newest-tick-time drift; use tick timestamps, all windows in ET.
3. **Entry mismatch:** research enters at the next bar's open = the first tick after the completing tick; live must read that first tick (not a completed-bar close) and log entry lag and price difference vs the simulated open.
4. **A baseline** (same-hour seconds-per-bar over the prior 20 sessions) needs those 20 sessions replayed or a persisted per-session hour table; absent it, A is undefined for the first sessions: persist it.
5. **Python sidecar importing the research functions (literal import, research commit hash pinned), not a Node port.** Accepted; the reaper must not kill a mid-replay process; handoff lossless.
6. **Tick source:** tail the `.scid`; the DTC feed is only a "file stopped growing" alarm. Accepted.
7. **Lifecycle:** the detector marking rows resolved races the pipeline's designed-timeout backstop: add the new setup-type prefix to `DESIGNED_TIMEOUT_EXIT_PREFIXES` (verified: `server/config/setupTypes.js:729`, currently 3 prefixes; `setupExpiry.js` gives them a grace window) and use an existing `resolution_method` value (VARCHAR(20)); the real reason goes in `amt_tell_events`. Stage-1 rows stay SHADOW (never ACTIVE, or the sweep would order them) and are excluded from any unfilled accounting. A no-target position: read `orderSweep.js` lines ~262-290 first (the OCO bracket needs both `stop_level` and `t1_level` and is behind `SIERRA_USE_OCO_BRACKET`; how a stop is placed without a target was NOT verified); prefer an existing no-target representation over a far target (a far resting target can fill in a spike).
8. **Stop cap:** DeepSeek's DLL-derived cap (`DTC_DLL_LIMIT_USD/2`) does not bind here (limit is 1000, so 500 pts, above the 338-pt maximum): not a real guard. Plan: no cap in Stage 1; log the uncapped outcome always; a Stage 2 distance guard (skip, never override the stop, so the traded rule stays the researched one) is a USER decision.
9. **V1 vs V3:** DeepSeek says run V1 live and promote V3 only on forward evidence (V3 was picked after seeing results). Accepted for the plan: Stage 1 logs BOTH outcomes for every tell; the Stage 2 exit choice is fixed by a pre-registered rule BEFORE Stage 2 starts (written down in this file and as a decision), not by looking at who is ahead at the time. (My earlier draft said run V3.)
10. **Evidence floor:** a fixed floor, not "the user's call to stop earlier": the user may stop reviewing whenever they like, but nothing counts as evidence of an edge below the pre-registered 150 tells / 60 dates, and DeepSeek's point stands that this is only a lower bound. **Be honest with the user about power:** per-trade SD is about 170 dollars, tells arrive about 3.4 per session, so one year (about 850 tells) gives a standard error of about 6 dollars per trade, against an explore mean of +2 (V1) to +7 (V3): forward confirmation of the EDGE takes about a year or more; the chart review confirms FIDELITY (the detector sees what the user sees) much sooner. Treat the chart review as a sanity check on definitions, never as evidence of edge.
11. **Order of work now:** (0) Stage-0 gates 1-2 above (overflow sensitivity, then byte-parity replay harness built against the research CSVs), (1) build the sidecar + builder + `amt_tell_events` + display, (2) DeepSeek code review (the two-reviewers rule), (3) Stage 1 live SHADOW, (4) user review vs chart, (5) Stage 2 only on the user's go-ahead with the open user decisions: LIVE_ROSTER exemption, stop-distance guard, kill-switch arming, V1 vs V3 rule.

## 9. User authorisations and the targets question (2026-10-28, after the critique)
- "Yes its exempt": the tell family is exempt from the LIVE_ROSTER gate for Stage 2 on the simulated DTC-Live-Simulator account (explicit carve-out, sim-only, documented in code; not a silent bypass).
- "I need to see this fire longs shorts": both directions must fire and be shown (explore: 897 long / 863 short V1 trades).

- **Targets / wide stops (`scripts/amt_vbars/descriptive_targets_output.txt`, claim `amt_tell_targets_and_stop_cap_descriptive_20261028`):** the researched rule has no profit target; a fixed R-multiple target lowers the average at every multiple (caps the winners), and the whole V1 profit sits in the 88 trades with stops over 100 pts (+49.95 each); a cap at 100 pts would leave -0.60 per trade. So the user's instinct (a wide stop must come with a bigger payoff) is met by the data through the open-ended hold, not through a fixed target. Stage 1 must log, per tell, the full excursion path (max favorable/adverse by bar) so any target or cap rule can be evaluated forward without peeking. Open: whether Stage 2 runs the researched rule uncapped on the simulated account (my recommendation: yes, it is simulated money and the tail is where the edge is) or applies a guard.
