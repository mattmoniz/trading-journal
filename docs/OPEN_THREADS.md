## 🔶 2026-08-10: Uncensored MAE candidate grid + volatility-anchored risk ceiling — the last named structural defect in the measurement layer, Gemini/DeepSeek-reviewed

Final item in the "measurement layer" block, direct continuation of the `backtest_setup_status.mjs`/MTM-exclusion fixes above. User's own framing: "the one that breaks the self-referential loop... the last structural defect in the measurement layer."

**The bug**: `realMaeCandidates()` (the stop-side candidate-value generator) built its percentile grid from `active_setups.mae_points` — but `resolveSetupsByPrice()`'s bar walk STOPS the moment a trade's ORIGINAL stop or target is hit, so `mae_points` is right-censored by whatever stop was already live when that trade fired. A trade that stopped out at 26pt has `mae_points≈26pt` regardless of what a 40pt candidate would actually have seen — the data to tell the difference was never recorded. This creates a feedback loop: the stop that was live when trades fired determines how far the candidate grid can even see, anchoring every future calibration near wherever the stop already sits.

**The fix**: `uncensoredMaeCandidates()` reuses `precomputeCrossovers()`'s own bar walk (same `WALK_WINDOW_BARS`=390 window already used for target calibration) with EMPTY candidate lists, so it walks the full window purely to report each trade's true, uncensored max adverse excursion — independent of when/whether the original stop or target actually fired. Required a small fix to `precomputeCrossovers()`'s own early-break condition (was vacuously true with empty candidate arrays, breaking after 1 bar instead of walking the full window). Wired into `computeStopTargetForType()`'s chronological-sweep branch only — the order-blind fallback keeps using the old censored grid, since its own EV computation is still censored-column-based and an uncensored candidate grid would be internally inconsistent with how it scores each one.

**The problem found before shipping** (caught by direct testing, not assumed): on real `IB_BEARISH` data (132 real trades), the uncensored grid produced candidates of **172.5pt to 398.25pt** — vs the old censored grid's 24.75pt to 61.75pt. **First proposed fix rejected by DeepSeek design review** (`scratch/deepseek_response.md`): capping the uncensored grid at a multiple of the OLD censored p75 was rejected — it re-introduces the exact self-referential censoring loop the fix was built to escape, just through a different door, and the multiplier itself would be an arbitrary, ungrounded threshold (violating the standing no-static-thresholds rule). ## 🔶 2026-08-03: "Grind Detector" dynamic exit mechanism — designed, then caught 3 real bugs via audit/debate before any code was written

Follow-up to the risk-management/R:R threads above. User asked for a genuinely dynamic (not binary snap-between-two-states) exit mechanism, framed explicitly: "much like picking entries should be a dynamic process, a trailing stop or breakeven should be dynamic too based on price action/volatility/volume" — and that it's fine to accept more risk if the EV is there, not a mandate to minimize risk for its own sake.

**Design process**: Gemini and DeepSeek independently brainstormed dynamic exit mechanism shapes (no leading suggestion beyond Claude's own bar6-checkpoint-extension hypothesis, which both independently rejected — extending `bar6_checkpoint` into a continuous sliding window loses its fixed-reference-to-entry property and risks becoming a disguised trailing stop, per both models' reasoning). Both converged independently on the same core idea from different angles: tighten the stop when TIME passes without proportional PROGRESS toward target ("grinding"), rather than reacting to price reversal (a trail) or an external confirmation signal. DeepSeek's version ("Grind Detector": `grindScore = timeElapsed - targetCovered`) is more refined than Gemini's simpler linear time-decay ("Stagnation Cut") because it doesn't punish a slow-but-genuinely-progressing trade the same as a truly stalled one.

**Target**: `IB_BEARISH_TURBULENT` (N=39 real trades, current fixed stop=25pt/target=50pt — already a favorable 1:2 R:R by the usual metric, yet real avg P&L=-$8.19/trade, implied WR≈28%). 3. **Lookahead data leak in the fallback median** (found by Gemini only — DeepSeek's self-audit explicitly signed off on this exact value as "Correct," checking only the primary path): the documented fallback ("if calibration has <3 winners, use full-sample median") uses data that includes the held-out set, contaminating a value later used to evaluate that same held-out set's simulated outcomes.
