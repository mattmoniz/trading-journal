# Conventions — full incident detail

Full incident narratives for the Conventions in `CLAUDE.md` that carry a real dated incident or extended mechanism writeup. A handful of short, incident-free operational notes (the sizeMultiplier IIFE location, the level fade detection gate, the unified suppression pipeline, etc.) stay in `CLAUDE.md` untouched and aren't duplicated here.

## localStorage drag-reorder must be merged, not filtered

- **A `localStorage`-persisted drag-to-reorder column order must be MERGED against the current column set at load time, never just filtered against it.** The obvious-looking pattern (`(savedOrder || defaultKeys).map(k => COLS.find(c => c.key === k)).filter(Boolean)`) only ever drops a key that's no longer valid — it can never re-add a key that's new since the user's last drag, because that key simply isn't in the saved array to begin with. Found 2026-07-28, independently in two places (`SetupReferenceView.jsx`, `SetupHistoryView.jsx`) — both had this exact bug, and it silently deleted the brand-new `misc` column for any user with an already-saved order, surfaced only via a user screenshot that was missing the column entirely (looked like "the column reset," but was actually "the column never had a chance to appear"). Fixed by reconciling any `DEFAULT_COLS`/`SETUP_LOG_COLS` key absent from the saved order back in (appended at the end) in the `useState` initializer itself — synchronous, no render flicker, and the existing "persist on change" effect writes the corrected order straight back to `localStorage`. Any future table with this drag-reorder-plus-persist pattern needs the same reconciliation, not the filter-only version.

## price_bars_primary needs an explicit upper bound too

- **Any new script querying `price_bars_primary` with a lower-bound-only `ts >= X` filter must add an explicit upper bound.** `price_bars_primary` is a VIEW (join + `GROUP BY` aggregation over `price_bars` + `price_bars_contract_calendar`, confirmed via `information_schema.tables.table_type='VIEW'`) — it can never have an index, so an unbounded query forces the aggregation across everything from `X` through the present before it can sort/`LIMIT`. Found 2026-07-27: a new backtest script's per-trade bar lookup took ~900ms-1.2s/call (2.5+ hours projected for ~11,000 rows) until a tight upper bound (`ts < X + interval`) was added, dropping it to 62ms (15-20x). Full writeup and the broader structural fix (materialize historical bars into a real indexed table): ARCHITECTURE.md's `price_bars_primary` section, `OPEN_DECISION`s `price_bars_primary_unbounded_query_audit`/`price_bars_primary_materialize_historical_bars`.

## Floor timestamps to the minute before matching bars to fired_at

- **Never look up a bar by an exact epoch/timestamp match against a real trade's `fired_at` — real trades carry genuine sub-minute precision (recorded live via `NOW()`), but bars are always exactly on the minute, so an exact match silently fails and the trade gets dropped, not flagged.** Floor the timestamp to the minute before the lookup. Found 2026-07-27: a backtest script's `Map`-based exact-epoch lookup discarded 31 real trades into a "skipped, no bar found" bucket — one of them (id=67604) was a genuine occurrence of the exact condition being tested, silently erased, producing a false "zero occurrences ever" finding. The bug was masked because the one row used to "verify" the lookup method earlier happened to have `fired_at` exactly on the minute (an unrepresentative pick) — pick a normal, live-recorded row (non-zero seconds) when spot-checking any timestamp-matching logic, not whichever row `LIMIT 1` happens to return.

## A number computed twice by the same script isn't verified

- **A number that survives being computed twice by the same script is not verified — it only proves the script is consistent, bugs included.** Independent re-derivation (by hand with a different method, or dispatched to Gemini without showing it the original methodology) is what actually catches a deterministic bug a repeated run cannot. Found 2026-07-27, twice in one session: a bar-6 exit-rule figure and a "zero real occurrences" claim were both wrong, both reproduced identically on a second run of the same buggy code, and both only corrected once an independent second derivation disagreed and the disagreement was chased down rather than dismissed. Applies even when the independent check itself contains an unrelated error (Gemini's own re-derivation had a wrong `$/pt` constant on one check the same session) — audit a disagreement in both directions instead of assuming whichever answer already existed is correct.

## Confound checklist for comparison-style backtests

- **Confound checklist for any new comparison-style backtest (two arms compared against each other).** Built 2026-07-21 per Opus Audit #4 after the same failure shape recurred 5+ times across ~5 sessions, always looking like a real win first, twice reaching `RESEARCH_CLAIM`/`OPEN_DECISION` before being retracted (most recently the same day: `volume_confirmed_candle_pattern_low_vol_trap`, selected the 6 largest-effect setup_types from a 48-setup sweep, reversed under held-out replication). Before recording or promoting any "config/condition A beats B" finding, check all four:
  1. **Do the two compared arms differ ONLY in the hypothesis variable**, or does one arm have a structural/algebraic edge (a later entry against the same fixed exit, a smaller remaining risk distance, anything mechanical)? If unsure, ask whether the "smarter" arm would still win with the intelligence stripped out and only the structural difference left.
  2. **Is the baseline computed by the exact same method/window as the thing being compared** — resimulated in the same pass, never read from a stored column computed under different historical conditions (the `backtest_scaleout_runner.mjs` baseline-mismatch incident, 2026-07-19).
  3. **Does the signal select a sub-population** (overshot / made-a-new-extreme / pattern-present / any filter)? If so, is there a same-selection-minus-the-signal-condition control bucket — the 3-way template in `scripts/pilot_cvd_divergence.mjs` (`SIGNAL` / `SAME_SELECTION_NO_SIGNAL` / `NEVER_SELECTED`) is the pattern to reuse, not reinvent.
  4. **Was this the largest of K effects pulled from a sweep** (top-N setup_types, best candidate in a grid, etc.)? If so, run `computeReplication()` (`server/services/rigorDiagnostics.js`) — a held-out/permutation check that pools the selected subset against everything NOT selected and reports whether the direction and magnitude survive. This is the one sub-family that's cheaply automatable; item 1-3 are domain-specific each time and need manual reasoning, not a generic detector (deliberately not built — would create false confidence).
  Items 1-3 are a documented checklist, not code — the actual bugs they catch are different every time. Item 4 has a real, reusable function now; use it before recording any `RESEARCH_CLAIM` that came from a "pick the biggest movers, then check them" process.

## Benchmarking bundle size across worktrees

- **Benchmarking bundle size across commits (git worktrees):** never symlink `node_modules` between a worktree and the main repo — Vite's dependency-optimizer cache (`node_modules/.vite`) is shared through the symlink and can silently contaminate build output from a different commit's module graph, even after deleting `node_modules/.vite` between runs. Give each worktree its own real `npm install`. Also build each commit in its own fully separate Bash/tool call — chaining `cd worktreeA && npm run build` followed by a second build command in the *same* call risks the shell's cwd silently carrying over to the second build too. Found 2026-07-13: a self-audit of a lazy-loading change reported a "52% bundle regression" that was entirely a benchmarking artifact from these two bugs stacked together; an independent review with a clean `node_modules` install got the correct (and much better) numbers.
- Backtest scripts live in `scripts/`, named `backtest_<hypothesis>.js`, run manually via `node`, and typically write findings to the `performance_audit` table. They are not imported by the running app.

## Frontend API calls go directly to 3002, never through api proxy

- **Frontend API calls fetch the backend directly (`:3002`), never the relative `/api` path (2026-07-15).** `src/constants/api.js` exports the one `API_URL` constant every view/component imports — never redeclare `const API_URL = '/api'` locally. Reason: routing API traffic through Vite's `/api` proxy put it on the same origin (`:3000`) as the app's own module-serving, and Chrome's HTTP/1.1 6-connections-per-origin cap meant Morning Prep's own background polling could starve a newly-navigated-to view's module fetch indefinitely (root-caused via a `curl` to the stuck URL succeeding instantly from a separate process — the server was never hung, the browser's per-origin connection queue was). Splitting API traffic onto its own origin (`:3002`) gives it a separate connection budget. Backend already has permissive CORS and no cookie/session auth, so this needed no backend change. Full writeup: docs/OPEN_THREADS.md.

## Cache day-stable backend queries

- **Day-stable backend queries (bounded strictly `< date`, or otherwise fixed for a whole trading day) should be cached on `server/lib/cache.js`'s `cacheGet`/`cacheSet`, not recomputed on every poll.** Already used by `acd.js`/`auctionRead.js`/`keyLevels.js`/`weekly.js`/`stats.js`/`morningBrief.js`/`sessionForecastService.js` — check this file before hand-rolling a new module-level cache object; `cacheSet` returns its `val`, so `return cacheSet(key, result, ttl)` works inline. Use a shorter TTL (minutes, not hours) for anything that reads the *target date's own same-day* data (e.g. today's still-accumulating premarket bars) — see `sessionForecastService.js`'s `getSessionForecast` (5min) vs. `morningBrief.js`'s strictly-prior-day `getTrailing*` helpers (12h) for the two conventions side by side.

## useSharedPollData dedup gaps

- **`useSharedPollData` (`src/utils/useSharedPollData.js`) dedupes the recurring poll interval automatically, but NOT independently-added consumers of a new URL, and NOT (before 2026-07-15) the very first load.** Before wiring a new component to an existing polled endpoint, `grep` for the exact URL string first — it's cheap, and this hook has already silently gained duplicate non-shared fetchers of the same endpoint multiple times (edges-context, live-session-context, morning-brief/forecast all had 2-6 independent fetchers found in one pass 2026-07-15, including ones that predated the hook's own creation). The hook itself also had a real bug fixed the same day: any subscriber mounting before the first fetch resolved saw `entry.data` still `null` and called `load()` again itself — with N real subscribers × React StrictMode's 2x dev-mode effect invocation, that was measured as 16 requests for one URL on a single page load. Fixed with an in-flight guard inside `load()`; no call-site changes were needed, so no other consumer should need touching for this specific bug again.

## Request-coalescing lock for expensive polled endpoints

- **A genuinely expensive endpoint that's also polled frequently or fetched by several components on mount needs a request-coalescing lock, not just a data cache.** If a response takes longer than its own poll interval (or several components independently fetch it at once on page load), concurrent/overlapping requests pile up and compete for the same DB connections, making every one of them progressively slower — a self-inflicted DoS against your own database. Found 2026-07-15: `/api/acd/setup-detection` (polled every 15s, ~8-10s per call) and `/api/confluence/today` (fetched by 3+ components on mount, ~5-6s per call) were both measuring 13-24s+ under normal use for exactly this reason — the per-call cost alone never explained the total. Pattern (see `acd.js`'s `setupDetectionInFlight` / `confluence.js`'s `confluenceTodayInFlight`): a module-level in-flight promise; the first caller runs the real handler against a minimal fake `res` (capturing just `.status()`/`.json()` — verify no other `res` methods are used in the handler first), concurrent callers `await` that same promise and get the identical result. This doesn't make the underlying query faster — it only stops concurrent callers from multiplying the cost. Don't add this reflexively to every route; only where polling frequency or multi-component fan-out can realistically overlap with the endpoint's own response time.
- Sierra Chart TAL data is stored as JSONB under `custom_fields->'sierra_data'` rather than typed columns — this lets new TAL columns appear without a migration and lets old Activity Log format rows coexist.
- Account filter state is lifted to `App.jsx` and shared between Calendar and Dashboard — don't duplicate it locally in a component.

## Views stay mounted across tab switches

- **Views stay mounted across tab switches (2026-07-15) — never add a new top-level view back to the old conditional-unmount pattern.** `App.jsx` tracks a `visitedViews` Set and CSS-hides (`display:none`) inactive views instead of removing them from the tree, so switching tabs doesn't re-run every view's fetches from zero. Consequence: any `setInterval`/polling effect in a view now keeps running while hidden unless it's gated. New polling code inside a view must read `useViewActive()` (`src/utils/useViewActive.js`) and add it to the effect's dependency array with an early `if (!isViewActive) return;` — see `ACDView.jsx`/`MarketPulseBar.jsx`/`PermSlipAndStackBar.jsx`/`LivePlaybookCard.jsx` for the pattern. Bounded, user-triggered job-status polls (e.g. `ACDBacktestRunner`, `PhaseChangeBacktestPanel`) are the deliberate exception — those should keep running while the user is on another tab. Full writeup, including a separate pre-existing Chrome-connection-limit bug found while shipping this: docs/OPEN_THREADS.md.

## Dont keep adding to App.jsx

- **Don't keep adding to `App.jsx`.** It was 20K+ lines before the 2026-07-13 code-split (`git log` commit `7c9b22a`) moved most view-layer code out into `src/views/`; it's now ~1.8K lines, but the split isn't an excuse to reverse it by piling new code back in. When a change needs new UI, extract it into its own file (`src/components/dashboard/` or `src/views/`) instead of inlining it. If a constant or helper needs to be shared across view files, put it in `src/constants/` or `src/utils/` — don't leave it as an unexported local `const`/`function` in App.jsx. That exact mistake (`SETUP_DISPLAY_LABELS`, `SETUP_RESOLUTION_TEXT`, `CAL_SETUP_SHORT_LABELS`, `LR_SLATE`, `getSetupConviction` all defined locally in App.jsx pre-split) caused several `ReferenceError`s in `ACDView.jsx`/`CalendarView.jsx` after the split, since they referenced App.jsx-local bindings across a file boundary. User directive, restated 2026-07-13.

## Monolith file size nudge is statistical not a fixed limit

- **Unnecessary monolith files get an automatic, non-blocking nudge — not a fixed line-count limit.** User request 2026-07-18: "I want the system to decide when the file is too big... unless they need to be." `.claude/hooks/post-edit-filesize.sh` (`PostToolUse`, `Write|Edit`) compares a touched file's line count against its own cohort (sibling files in the same directory, same extension) using median + MAD (median absolute deviation, robust to an already-known legitimate outlier like `acd.js` — confirmed by direct measurement: `server/routes/`'s cohort median is ~255 lines, and `acd.js` at ~7980 would blow out a plain mean/stdev threshold for every other file in the directory). Fires only when the file is BOTH a statistical outlier for its cohort (modified z-score > 3.5, the standard Iglewicz–Hoaglin robust-outlier cutoff) AND grew by at least a cohort-median's-worth of lines since the last commit — this is what keeps it quiet on routine small edits to `acd.js` itself, only firing on genuinely new sprawl. `acd.js`'s size is a known, deliberate exception (its own "largest route file" note in this doc); the hook doesn't special-case it by name, the growth-gate does that naturally since small edits never trip it. Advisory only (`additionalContext`, informs the judgment call, doesn't block) — splitting isn't always right, cohesion sometimes matters more than line count.

## No-new-entries dead zone 4-6PM ET

- **No-new-entries dead zone (4:00-6:00 PM ET):** `runSetupDetection()` (`server/routes/acd.js`, `inNewEntryDeadZone` computed near the top from `etMin`) forces any new RTH candidate that would otherwise fire `ACTIVE` in this window to `SHADOW` instead (`suppression_reason='POST_RTH_DEAD_ZONE'`), via the same `forceShadow` choke point that already handles trail-mechanism variants and standard suppression. User directive 2026-07-31 ("seems to be noise and bad trades"). Does NOT force-close already-open positions — those still resolve normally via `resolveSetupsByPrice()`/`expireStaleSetups()`, which run unconditionally every poll regardless of window; only NEW entries are blocked. Overlaps with, but is broader than, the pre-existing 5-6PM ET hard-close gap (which force-closes anything still open at 5PM) — the two are independent mechanisms, not a duplicate. Still shadow-tracked (never a dead end): setups still fire/resolve as SHADOW in this window, so real N keeps accumulating for whenever this rule is revisited.

## Server-autonomous detection schedule

- **Server-autonomous detection:** `server/index.js` runs a `setInterval` every 15s calling `GET /api/acd/setup-detection`, across the full CME Globex week (Sun 6PM–Fri 5PM ET, with the daily 5–6PM ET maintenance gap excluded) — not just RTH. This is intentional — it makes level fade detection independent of browser clients. Do not remove it. The INSERT in `acd.js` is `ON CONFLICT DO NOTHING` so concurrent client polls don't double-write. **This entry was stale from 2026-06-01 until 2026-07-19** (described a `GET /api/acd/today`, 60s, RTH-only poller that no longer exists under that name/schedule — the endpoint was consolidated and the schedule extended to full Globex hours on 2026-07-16, but this bullet was never updated to match). The same staleness had propagated into two frontend display strings (`AlphaEngineOverview.jsx`'s "Server Poll Cadence" card, `PlaybookView.jsx`'s scanning FAQ) — both said "60s, 9:30–4:00 PM ET" and both were fixed the same session, found while investigating a user report that several dashboard cards showed "Market Closed" during an actually-open Sunday-evening Globex session (`DayOfWeekPlaybookCard.jsx`'s weekend branch checked `getDay()` with no time-of-day check at all, and `App.jsx`'s `inGlobex`/`inRTH` sidebar logic had no day-of-week boundary, so it misread Saturday RTH-hours as "open"). **General lesson: a hard rule describing a poller's schedule/endpoint is exactly the kind of fact that silently drifts when the poller itself changes — if you touch the setup-detection poller's schedule or endpoint again, grep for "9:30" / "RTH" / "market hours" across `CLAUDE.md`, `src/components/dashboard/`, and `src/views/` in the same session, not just the code.**

## DAY_TYPE_MANAGED bucket breakdown re-read

- **DAY_TYPE_MANAGED types need their bucket breakdown re-read, not just their headline recommendation.** A `DAY_TYPE_CONDITIONAL` type (currently `IB_BULLISH`/`IB_BEARISH`) staying off `SUPPRESS` can mean "genuinely strong on its good day-type" or "one thin/borderline bucket happens to clear the -$5 bar this week" — the recommendation string alone doesn't distinguish these, and the IB_BULLISH regression (found 2026-07-16, docs/OPEN_THREADS.md) happened because nobody re-checked the bucket numbers for two days after a fix. `.claude/hooks/session-start.sh`'s `DAY_TYPE_MANAGED WATCH` section now prints every such type's full bucket breakdown at the start of every session and flags (⚠️) any bucket that's the *sole* reason a type isn't `SUPPRESS`ed while sitting within $10 of the bar or under N=50 — read it, don't skip past it as boilerplate.

## active.sizeMultiplier overwrite footgun

- **`active.sizeMultiplier` overwrite footgun:** the level-fade IIFE above sets a real, ~20-factor `sizeMultiplier` (0.10-1.5x) on `levelScalpSetup`. Later in the same `/api/acd/setup-detection` handler, the "Build full trade brief" block (`acd.js` ~line 5855, shared by every candidate in the `candidates` array — both `levelScalpSetup` and `ibSetup`) sets `active.sizeMultiplier` again for a completely different reason (post-loss "Death Sequence" protection). Found 2026-07-16: this second assignment used to unconditionally *replace* the first, silently discarding the entire elaborate factor stack down to a crude binary 0.5/1.0 — confirmed live via 100% of persisted `active_setups.size_multiplier` rows being exactly 0.500/1.000, zero variety. Fixed to apply the post-loss rule as an additional ceiling (`Math.min(existing, 0.5)` when `hasLossToday`) instead of a replacement. **Any future code that sets `active.sizeMultiplier` (or any other field a candidate object already sets in its own construction) after candidate selection must merge/cap, never blindly overwrite** — check what the candidate already computed first. **Follow-up found 2026-07-27 (`unify_sizemultiplier_into_validated_score` audit): the 2026-07-16 fix above corrected the overwrite-vs-ceiling bug, but `hasLossToday` itself (and two other context queries feeding the same IIFE — `lfConsecWins`/`lfConsecLosses` win/loss-streak sizing, and the stacking-count/level-recency factors) had never been scoped by `origin_status` (they all predate that column, added 2026-07-17). Confirmed live: on 6 of the last 23 days, `hasLossToday` fired true with zero real (`ACTIVE`-origin) losses, purely from `BACKFILL`-origin rows sharing that `trade_date` — meaning the 0.5x ceiling was still engaging far more often than the "a real prior loss today" concept intends, even after the overwrite fix, which is why real `size_multiplier` was still 0.500 on 56 of 57 rows checked. Fixed: `hasLossToday`/streaks scoped to `origin_status='ACTIVE'` (a personal-day concept — `SHADOW` setups were never shown to the user, so a `SHADOW` "loss" isn't one they experienced); stacking-count/level-recency scoped to `origin_status IN ('ACTIVE','SHADOW')` (a market-structure concept — a `SHADOW` touch is still a real, live-price-triggered event). Full writeup: `docs/OPEN_THREADS.md`.

## New setup type checklist anti-hardcode gate

- **New setup type checklist (anti-hardcode gate) — also the checklist for auditing *existing* live setups, not just gating new ones.** Items 5-10 below were each found by retroactively checking an *already-live* setup, not by reviewing a new one before launch — if you're doing a broad audit pass over existing setup_types (see docs/OPEN_THREADS.md's "broader audit of all setup types" thread), these are exactly the categories of bug to check every one of them against: real stop/target simulation (5), half-wired integration (6), standalone-poller promotion gaps (7), Unified Signal Table status-mapping (8), fire-gate-vs-data-availability timing (9), and backfill-detection-window-vs-live-firing-window mismatch (10). Before any new `setup_type` goes live in `acd.js`, ALL of the following must be satisfied:
  1. Run `node scripts/backtest_setup_status.mjs` → generates/updates `SETUP_STATUS` row in `performance_audit`
  2. Run `node scripts/update_optimal_stops.mjs` → generates/updates `OPTIMAL_STOP` row with data-derived stop/target
  3. If N<20 resolved trades, do NOT fire live — insert as `status='SHADOW'` only until N≥20
  4. Never write a stop, target, or WR claim as a literal number in `acd.js` — always read from `liveStats._opt[type]` or `performance_audit`
  4a. **Run a signal-level forward-return pre-test before building any trade machinery — the cheapest, most decisive screen in this checklist.** No stop, no target, no exit rule, no position state: at each signal event, measure the raw forward price change at several bar horizons (e.g. 1/3/5/10/20 bars) and compare the CONDITIONAL mean against the UNCONDITIONAL mean of every bar over the same horizon — never against zero, since a multi-year NQ sample has real underlying drift and "conditional mean is positive" alone is close to uninformative. Source: `scratch/opus_audit_7_results.md` §4(a) — an ATR-compression-breakout thread built four full backtest engines (fill models, stop sweeps, rigor checks) before this ~40-line, under-a-minute check settled the question decisively; had it run first, the thread would have ended on day one. This is the concrete, implementable form of the "market-behavior hypothesis → bar history first" rule above — that rule says which table to query, this says what to compute first. **Enrich with volume/order-flow, don't leave it pure-price**: bucket signal events by volume using `server/services/touchQuality.js`'s `getVolumeBaseline()` (90-day trailing per-minute-of-day avg/std, not a static threshold) and the `volZ`/`oneSidedRatio` formulas already established in `acd.js`'s `computeStackVolSignal` — reuse, don't reinvent a third volume metric. **The bucket cutoff itself must also be data-derived, not guessed**: a first attempt at the OR5/10/15/30 forward-return pre-test used `computeStackVolSignal`'s own live threshold (volZ>=1 AND oneSidedRatio>=0.6 — the real genuine-breakout bar) directly as the bucket split, and it was far too strict for a generic level-touch population (only 2-11 of ~300-380 touches per level cleared it, every "confirmed" bucket came back N<20) — a threshold calibrated for one purpose (flagging a rare, real breakout) doesn't transfer to a different purpose (splitting a general population in half). Fixed by using the pooled MEDIAN volZ across all touch events as the split point instead, guaranteeing a usable ~50/50 division by construction. Final result (`RESEARCH_CLAIM or_length_forward_return_pretest`): still no signal either way — pure-price found 1 of 60 cells clearing |t|>2 (chance-level at that many comparisons), the volume-median-split version found 1 of 120 (also chance-level, if anything cleaner than chance predicts) — the null holds up under both cuts, not just an artifact of pooling a real volume-driven effect into noise.
  5. **Simulate the real stop/target as an actual bar-by-bar trade before ever calling a signal "validated."** A statistically stable *sign* on a raw point value (e.g. "price at bar+N") is necessary but not sufficient — it has no drawdown tolerance and is not a tradeable strategy. Found 2026-07-14: 3 of 4 minute-bar scanner signals passed day-clustering, time-of-day, and 3-way chronological stability checks, then turned negative EV (-$15.75, -$18.49, -$3.20/trade) the moment a real p75-MAE-stop/p50-MFE-target was simulated instead of the raw exit value. Only after this step should a signal be treated as a live candidate.
  6. **Verify integration, don't assume it.** New setup types are easy to half-wire: check `dropToTimeline()` is called from the actual insert path (not just the pattern copied from elsewhere), check `SETUP_DISPLAY_LABELS` (`src/constants/setupDisplay.js`) has an entry, check `isLongSetup()`/`inferDirection()` resolve correctly for the exact string being inserted. Found 2026-07-14: a new setup's live poller skipped `dropToTimeline()` entirely and had no display label — both silent, both would only surface once the setup was visible enough to matter.
  7. **If the setup lives outside the level-fade candidates array (its own poller — e.g. a bar-window statistical signal, not a level touch), it must replicate the dynamic SHADOW→ACTIVE promotion check manually.** The candidates-array insert path already does this correctly: `liveStats._suppressedSetups` is rebuilt from the latest `SETUP_STATUS` rows every trading day and checked fresh on every single fire (`server/routes/acd.js` ~line 4564). A standalone poller has no such built-in mechanism — if you hardcode `status='SHADOW'` at insert time with no live re-check, the setup sits in SHADOW **forever**, even after clearing N≥20 live trades with good EV, because nothing else in the pipeline will ever flip it. Found 2026-07-14 in `minuteBarSignalDetector.js`'s first version. Fixed with a `getLiveStatus()` function — queries real resolved `active_setups` trades for the type (N≥20 & EV>-$5 → `ACTIVE`, else `SHADOW`), called fresh on every fire — use it as the template for any future standalone poller.
  8. **If the calibration script writes a new `recommendation` value, register it in `/api/performance-audit/unified`'s status-mapping** (`server/routes/acd.js` ~line 6976) or the setup type is silently invisible in the Unified Signal Table (`BacktestView.jsx`'s "Unified Signal Table"). Found 2026-07-14: `SETUP_STATUS`'s actual vocabulary (`SUPPRESS`/`THIN_N`/`PROMOTE`/`DAY_TYPE_MANAGED`) matched none of the recognized strings there, hiding ~61 of 113 setup_types from the table.
  9. **If a setup's fire gate is earlier than the data it depends on for suppression, its suppression logic is a silent no-op.** Any setup exempted from the standard blended-EV `SUPPRESS` check (a `DAY_TYPE_CONDITIONAL`-style carve-out in `backtest_setup_status.mjs`, or a DOW/day-type check inline in `acd.js`) must have its fire-gate timing verified against when that dependency actually becomes available — check the actual gate condition (`etMin >= ...`), not just that a suppression check exists in the code. Found 2026-07-14: `IB_BULLISH`/`IB_BEARISH` fired off a deliberate 30-min IB window (`etMin>=600`, 10:00 ET) but their day-type suppression checks depend on `acd_daily_log.day_type`, which isn't classified until IB close at 10:30 ET — so the checks were guaranteed no-ops every time they fired, and `IB_BULLISH` ran live at -$27.81/trade EV (N=106) with zero effective guardrail. Fixed by moving the fire gate to `etMin>=630` (not the 30-min level *definition*, just when the alert is allowed to fire) and by giving `DAY_TYPE_CONDITIONAL` setups a real per-day-type floor in `backtest_setup_status.mjs` (SUPPRESS if every bucket with N≥20 is below the standard `-$5` bar) instead of unconditionally trusting the day-type carve-out. Full writeup: docs/OPEN_THREADS.md.

## VARCHAR N literal overflow risk

- **Any string literal written into a short `VARCHAR(N)` column (`resolution_method`/`resolution`/`actual_outcome`/`replay_resolution` are all `VARCHAR(20)`; `status` is `VARCHAR(10)`; `origin_status` is `VARCHAR(12)`; `performance_audit.signal_type`/`.recommendation` are `VARCHAR(20)`) throws a raw, uncaught `value too long for type character varying(N)` Postgres error, not a graceful truncation — and if that column is written from inside a shared per-row loop (like `resolveSetupsByPrice()`'s single loop over every active/shadow setup), ONE bad literal crashes resolution for every OTHER setup in that same poll too, not just the one row.** Found 2026-07-20: `scripts/repair_null_pnl_shadow_setups_20260720.mjs`'s own `'RECOVERY_MARK_TO_MARKET'` (23 chars) hit this on its first real (non-dry-run) write, which prompted checking whether the same class of bug existed anywhere else — it did, already committed and pushed: `resolveSetupsByPrice()`'s breakeven-trail branch used `'SAME_BAR_ARM_AND_STOP'` (21 chars) and `'BREAKEVEN_TIME_EXPIRED'` (22 chars), both over the `resolution_method` `VARCHAR(20)` limit, sitting live and untriggered only because neither code path had fired yet in production. Fixed both (`SAME_BAR_ARM_STOP`/`TRAIL_TIME_EXPIRED`, ≤20 chars) and swept the whole project: grepped every `≤20`-char `VARCHAR` column in `active_setups`/`performance_audit` against every literal/derived value actually written to it in live code (`server/routes/acd.js`, every non-archived backfill/repair script) — no other overflow found, but did find a related near-miss: `scripts/flag_decision.mjs`/`scripts/record_claim.mjs` write an arbitrary-length human-authored `slug` straight into `performance_audit.signal_name` (`VARCHAR(60)`) with zero length check, and one live `OPEN_DECISION` slug was already sitting at exactly 60/60 chars — the next long slug would have crashed with the same error class. Added a fail-fast length guard to both (throws a clear message over 60 chars — deliberately not silent truncation, since two distinct 61+ char slugs could collide on the same truncated prefix). **When adding any new hardcoded status/method/label string anywhere in this codebase, check it against its target column's actual declared width in `server/schema.sql` before assuming it fits — a string that reads as "short enough" by eye is not the same as verifying the number.**

## Trading-day dates from CURRENT_DATE never toISOString

- **Trading-day dates: always derive from SQL `CURRENT_DATE`, never JS `new Date().toISOString()`.** The DB server runs in `America/New_York`; JS's `toISOString()` is UTC, and the two disagree once past 8PM ET — a full calendar day earlier in JS-UTC-land than the DB's own ET-based "today." This caused 3 separate same-day bugs on 2026-07-14 (`backtest_minute_bar_scan.mjs`, and pre-existing `backtest_setup_status.mjs`) where a script's own `run_date` silently drifted a day from its siblings', breaking every `MAX(run_date)`-based "latest run" join `performance_audit` consumers rely on (including `/api/performance-audit/unified`). Fetch it with `SELECT CURRENT_DATE::text as today` in every new backtest script — never `new Date().toISOString().slice(0,10)`.

## Naive timestamp parsing depends on ambient timezone

- **Never parse a naive (no-timezone) timestamp string with `new Date(str).toISOString()` — it silently depends on the ambient process/system timezone, not on any timezone you actually intend.** Found 2026-07-16 in `server/parsers/sierraParser.js`'s `parseDateTime()`: Sierra Chart export strings carry no timezone marker but are always America/New_York wall-clock time. `new Date("2026-07-14 10:48:58").toISOString()` gives a *different* answer depending on whether the process happens to be running with ambient timezone UTC or America/New_York — and this system's ambient timezone silently changed at some point, so **every trade imported from 2026-06-09 onward was stored 4-5 hours off** (4h in EDT, 5h in EST — a flat offset is wrong, the correct shift depends on whether the date being parsed falls in EDT or EST) while imports before that date (which happened to run under an environment resolving to UTC) were stored correctly. The frontend (`AllTradesView.jsx`/`CalendarView.jsx`) formats `entry_time` by treating the stored value as a genuine UTC instant and converting to `timeZone: 'America/New_York'` for display — so the post-06-09 bug's output *happened* to display correctly (two wrongs cancelling out) while the pre-06-09 *correct* storage displayed 4-5 hours **early**, the exact opposite of what either the user or Claude initially assumed from "recent trades look right." Also silently corrupted `log_date` (computed via `entryDateTime.split('T')[0]` on the already-wrong shifted string) for any trade whose real ET time was within ~4-5 hours of midnight, since the shift could push it across a calendar-day boundary. **Root cause of the timezone flip itself never fully identified** — likely a one-off manual script/backfill run from a different shell environment during a period with no corresponding git commits (2026-06-03 → 2026-06-12 gap) — but the fix doesn't depend on knowing that: `parseDateTime()` now explicitly computes the naive string's real UTC-equivalent instant via `Intl.DateTimeFormat`-based ET anchoring (`etNaiveStringToUtcIso()`, same file), verified byte-identical regardless of ambient `TZ`. **The pattern to reuse for any future naive-local-timestamp parsing**: guess a UTC instant from the naive components, ask `Intl.DateTimeFormat` what that guess actually looks like in the target zone, then correct by the wall-clock difference — this correctly handles both EDT and EST per-date, unlike a hardcoded `+4`/`+5`.
  - **Same bug produced two full-history duplicate-import events, both cleaned up 2026-07-16** (backup: `trades_backup_20260716`, full 40,453-row pre-repair snapshot): a 2026-06-09 mass re-import of already-existing pre-06-09 trades through the by-then-broken parser (4,100 rows, `scripts/repair_trades_dedupe_20260609_batch.mjs`) and a separate, unrelated 2026-04-22 re-import of the original 2026-03-11 mass historical load (1,168 rows, no time-shift involved, `scripts/repair_trades_dedupe_20260422_batch.mjs`, root cause not investigated). A third pass (`scripts/repair_trades_dedupe_remaining.mjs`, 3,769 rows) found a structural Sierra Chart TAL quirk unrelated to either import event: the same completed flat-to-flat position is logged on **multiple separate lines** (one tagged with a trailing ` BP`, one with ` EP`, sometimes a third with neither), and the importer inserted one `trades` row per line instead of recognizing them as one position — confirmed directly (`custom_fields->'sierra_data'` raw strings identical except for the BP/EP suffix) and independently audited by Gemini before deletion. All three passes verified zero `trade_screenshots` (the only FK referencing `trades.id`) impact before deleting. `trades` total: 40,453 → 31,416.
  - **Process lesson**: don't trust "recent data looks right" as proof a timestamp pipeline is healthy — this bug's two halves (wrong storage, compensating wrong display formatting) each looked fine in isolation depending on which period you happened to check. Verify via the *raw* `custom_fields->'sierra_data'` string against the stored column directly, not via the rendered UI, when auditing a timestamp pipeline.

## Share modules instead of reimplementing

- **Share modules when the same logic would otherwise be reimplemented.** The rigor diagnostic above was independently hand-written **three separate times** on 2026-07-14 (one per script) before being centralized into `server/services/rigorDiagnostics.js` (`computeRigor()`) — the exact inconsistency this principle exists to prevent. Any script computing the same kind of check (day-clustering, chronological stability, or similar) must import the shared version, not write a 4th copy. `computeRigor` takes a generic `pnlFn` so callers without a real dollar EV (e.g. `mine_tod_patterns.mjs`'s pure hit-rate claims) can pass a +1/-1 hit/miss proxy instead — the stability math is identical either way. **Same precedent repeated 2026-07-21**: the held-out replication check (see the confound checklist above) had already been hand-written twice ad hoc (`regime_c_persistence_debunked_placebo_test`, `globex_large_moves_start_near_pit_safe_levels`) before a third real instance (`volume_confirmed_candle_pattern_low_vol_trap`'s retraction) prompted centralizing it as `computeReplication()` in the same file — import it, don't write a 4th copy either. **A sharper version of the same mistake, 2026-08-09: don't just avoid reimplementing a function — check whether an existing COLUMN already answers the question before adding a new one.** Built `active_setups.fired_status` (a new column, immutable-at-insert, to distinguish a real live alert from a SHADOW-at-fire background touch after resolution overwrites `status`) before discovering `origin_status` (added 2026-07-17) was *already* bound to the identical value at every one of the 8 live-firing INSERT sites — confirmed by re-reading the actual VALUES clauses, and further confirmed that `scripts/export_row_level_audit_20260805.mjs`, written the very session that built the cascade-breaker logic, was already using `origin_status==='ACTIVE'` this exact way. The new column was strictly worse than redundant (it would only have covered data from the day it was added forward, while `origin_status` already covered history back to 2026-07-17). Reverted the same session once caught by direct user pushback — full account `docs/DECISIONS_LOG.md` 2026-08-09. General form: before adding a new persisted field to answer "what was true at the moment X happened, immutably," grep the target table's own INSERT sites for an existing column already carrying that answer — don't infer from a column's stated *purpose* in an older doc entry, check what it's actually bound to in the real SQL.

## PROMOTE recovery-detection needed a real-N floor

Re-ran `backtest_setup_status.mjs`: all 6 fake recoveries correctly reverted to `SUPPRESS`, `IB_LOW_FADE_LONG` correctly stayed live. ## setup_type name-only classification is structurally ambiguous

- **A shared classification function that infers its answer from `setup_type` NAME ALONE can silently return the wrong answer when the SAME name is inserted from two different live code paths under two different true contexts — check whether the INSERT site already knows the correct answer before trusting the name-based inference.** Found 2026-08-11 (roster-rebuild roadmap Phase 7, Setup F): `detectGlobexSetup()` (the overnight/Globex engine) fires 4 of its own setup_types — `PD_VAH_FADE_SHORT`/`PD_VAL_FADE_LONG`/`PD_POC_FADE_SHORT`/`PD_POC_FADE_LONG` — under the exact same string names as the RTH engine's own fades of the same levels. `getBetClass()` (`server/config/setupTypes.js`) infers `bet_class` purely from the setup_type string, so it silently classified EVERY Globex-session fire of these 4 types as `VALUE_FADE` (the RTH bucket) — it has no way to know which engine actually fired a given row. Confirmed live: 5,132 historical rows across 12 OTHER, unambiguously-Globex-only type names (`GLOBEX_VWAP_MAGNET/FADE`, the 8 `_OVERNIGHT` types) were ALSO mistagged `VALUE_FADE`, because `getBetClass()` simply had no `GLOBEX_LEVEL` branch at all until this fix. Worse: re-running the earlier same-night `VALUE_FADE` bet_class resweep after the fix found its real trade population had been ~15% contaminated by these mislabeled Globex rows (228 of 1525) — a wrong classification in a shared function silently corrupted a DIFFERENT bet_class's own analysis, not just the one it directly misclassified. **Fixed** two ways: (1) `detectGlobexSetup()`'s own INSERT no longer calls `getBetClass(c.type)` at all — it hardcodes `bet_class='GLOBEX_LEVEL'` directly, since every row that function writes IS a Globex fire by construction; it never needed the name-based inference, it just hadn't been asked to skip it. (2) `getBetClass()` gained a `GLOBEX_LEVEL_TYPES` Set for the 12 names that ARE unambiguous by name (matching the `FAILED_SWEEP_REVERSAL_TYPES`/`OPENING_DRIVE_15MIN_TYPES` precedent), and their historical rows were backfilled (backup: `active_setups_globex_betclass_backup_20260811`). The 4 genuinely name-ambiguous types are NOT backfilled — doing so needs a `fired_at` time-of-day check (Globex vs RTH hours) that hasn't been built yet (`OPEN_DECISION globex_ambiguous_names_need_session_backfill`) — so `getBetClass()` still returns `VALUE_FADE` for those 4 names when called generically (correct for their RTH-fired majority, silently wrong for their Globex-fired minority, same residual gap the INSERT-site fix doesn't touch). **General lesson: when the SAME identifier can legitimately mean two different things depending on which code path produced it, a name-only classifier is structurally unable to get it right for both — either give the two producers distinct identifiers, or have the producer that already knows the true context assert it directly instead of routing through the shared inference.**

## Unconditional resolveSetupType diversion freezes base-type population

- **An UNCONDITIONAL `resolveSetupType()` diversion (a variant that captures 100% of a base type's future touches, not just some) permanently freezes the base type's own population for any script that groups by raw `setup_type` — pool base+variant, or reverse-map, don't group blind.** Found 2026-08-10 (roster-rebuild roadmap Phase 3, I4): the 6 `_TRAIL` breakeven-trail variants (`FLOOR_R1_FADE_SHORT_TRAIL` etc.) divert EVERY touch of their base type unconditionally (`acd.js`'s `resolveSetupType()`, "unconditional diversion" comment) — so after each variant's `addedDate`, the base type (`FLOOR_R1_FADE_SHORT`) can never accumulate a new real trade again; real, growing data keeps landing under the `_TRAIL` name instead, where `backtest_breakeven_trail.mjs`'s `byType[t.setup_type]` grouping never looked. Confirmed live: `PD_POC_FADE_LONG` (base) real_n=19 (frozen, all pre-diversion) vs `PD_POC_FADE_LONG_TRAIL` real_n=11 (growing) — pooled, 30, past `MIN_N=20`; unpooled, neither half clears it alone. This is distinct from and NOT caught by the earlier same-day `breakeven_trail_4_more_variants_lost_calibration_row` resolution, which measured only the base type's own real_n and correctly-as-far-as-it-checked concluded "thin data, wait" without noticing growth was already happening under a name it never read. **Fixed** by pooling `_TRAIL`-suffixed trades into their `baseType`'s bucket (via `CONDITIONAL_VARIANTS`'s own registry — generic, not a hardcoded name list) before the sweep — self-heals the "no dead ends" rule going forward, though real N still hasn't cleared the guardrail as of the fix (an honest negative, not a claimed fix of the outcome). **General lesson: before grouping/aggregating any table by `setup_type`, check whether `CONDITIONAL_VARIANTS` has an unconditional entry pointing at it — an unconditional variant means the base type's own future population is structurally dead, and a script unaware of this will silently under-count real N for BOTH names indefinitely.**

## Conditional variant setup checklist

- **Conditional variant setup checklist** — when a single level name generates two setup types based on entry condition (e.g., `WPP_FADE_SHORT` vs `WPP_FADE_SHORT_GAP_UP`):
  1. Add the override to `resolveSetupType()` in `acd.js` (defined just above the `nearLevels` filter). This is the **single source of truth** — both the live path and early-touch backfill call it.
  2. Write a dedicated backtest script (`scripts/backtest_<variant>.mjs`) that persists SETUP_STATUS + OPTIMAL_STOP rows for the new type. Add it to `run_weekly_backtests.sh` under "Conditional-variant backtests".
  3. Add an entry to `CONDITIONAL_VARIANTS` in `server/config/setupTypes.js` with `baseType`, `direction`, `condition`, `backtestScript`. If the type name doesn't encode direction via a standard suffix, also add it to `CONTEXTUAL_DIRECTION_TYPES`.
  4. Update `AlphaEngineOverview.jsx` `suppressed` array — add entries for both the suppressed base type and the active variant, noting the condition.
  5. Add a note to `docs/OPEN_THREADS.md` to monitor variant at N=50.
  6. **Run `node scripts/test_invariants.mjs`** — this catches everything else automatically: OPTIMAL_STOP coverage, direction inference correctness, backtest script on disk, base type suppressed, and (added 2026-07-17) that every `OPTIMAL_STOP` row's stored `ev_per_trade` actually matches a fresh re-derivation of its own `optimal_stop`/`optimal_target`. If it passes, the pipeline is complete.
