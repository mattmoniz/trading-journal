<a id="wl-001"></a>

- **A "clear the halt / re-arm" gate must require EVERY independent check that can halt, not just the one it happens to read.** Found 2026-10-19 (independent DeepSeek review, `maybeAutoRearmAfterReconcile()` in `connectionManager.js`): the sim auto-rearm gated only on the open-orders report being clean, but a position-invariant mismatch halts in the same reconciliation pass — and with no resting orders the report is clean — so the halt was undone immediately. Whenever a halt can come from several independent checks, the thing that lifts it must consult all of them (an unknown/"no data" reading is not a pass either: a failed broker snapshot now makes the report unclean). Same review: a position read must take the LAST message in a collection window, not the first (a leading transient flat reading cancelled protection logic), and an exit must never be retired when the account read differs from the account orders are actually sent under. **Related process lesson:** a deferred "restart when flat" waiter armed in the background restarts whatever is on disk at that moment, including a half-finished edit — don't leave one armed while still changing server files (this one fired mid-edit; it happened to load consistent code, which was luck).


<a id="wl-002"></a>

- **Completed RTH session stats come from `daily_rth_stats` (2026-10-19, `server/services/dailyRthStats.js`), not from re-aggregating `price_bars_primary`.** Use `getCompletedSessions({beforeDate, limit})` / `getRollingRthRange({beforeDate})` for any "last N completed RTH sessions' high/low/range" need (ATR, gap fill, prior-session ranges). It returns the SAME values as the view queries (proved by `scripts/test_daily_rth_stats.mjs`, run weekly), serves completed sessions only (today's partial session you read yourself, range-bounded), and fails soft: if the table is empty/behind/erroring it runs the original view query, logs it, and repairs itself — never a silent null. `minorDefendedLevelDetector.getFullDayATR` is a different (full 24 h) definition and deliberately does NOT use it. Found with the profiler: the recurring `rth_low/rth_high` query was the gap-fill setup in `acdCandidateBuilder.js`, uncached on every detection pass. Spec, review and the still-open index/range-rewrite steps: `docs/PRICE_BARS_AND_STARTUP_SPEED_SPEC.md`.


<a id="wl-003"></a>

- **Data-growth check (shipped 2026-10-19): `scripts/data_growth_check.mjs`, weekly (`run_weekly_backtests.sh`) → `table_growth`.** The slow-cadence counterpart of the post-deploy watch, for slowdowns that come from the DATA growing rather than from a change. It records size / rows / full-scan rows-read for every table in the biggest 90% of the database (data-derived "big", not a fixed MB figure) plus row counts per `performance_audit` signal_type, judges each against its own weekly history (same median/MAD + p99 + modified-z test, learns for 4 weeks), flags a big non-backup table nothing has read since the last record (partitions are ignored; `EXPECTED_UNREAD` in the script lists deliberate exceptions with reasons, e.g. `price_bars_dedup_hist_v2`, a prepared cutover target), and names any query shape whose weekly average (from the server's own `perf_snapshots`) keeps rising. It only ever speaks through a plain-English OPEN_DECISION, one per finding per month. **Before shipping a query that runs on every poll/page load: `node scripts/explain_check.mjs "<sql>" [params]`** — runs EXPLAIN (does not execute), lists every full scan of a big table and filters that wrap a column in a cast (`ts::date`), exit 1 on a hit. Known finding it exposes: ANY `price_bars_primary` query full-scans the 683k-row `price_bars_dedup_hist` even with a bound date range, because the view itself wraps `ts` in `date_trunc('minute', ts)` and aggregates before filtering — callers cannot fix it, the view definition can (the failsoft cutover, `OPEN_DECISION contract_calendar_failsoft_join_20260915`, is the natural place). Append-only tables need a retention rule at the writer: `monitor_bet_correlation.mjs` now deletes its own older runs (it had grown `performance_audit` by ~30k rows a week; 88k old rows removed, backup `performance_audit_corr_monitor_backup_20261019`).


<a id="wl-004"></a>

- **Post-deploy performance watch (shipped 2026-10-19, v2 same day): `server/services/perfTelemetry.js` → `perf_snapshots`. Deliberately about each CHANGE, not an overall health monitor (user direction: find a slowdown right after the change that caused it, not weeks later).** Every server start writes a `DEPLOY` row (git sha); every 5 min a `SNAPSHOT` records DB-busy %, detection-pass time, event-loop stalls, detection-poll outages, row→ENTRY-order delay, rss/heap memory and pool waiters. The watch for a deploy lasts until BOTH RTH and GLOBEX have 12 snapshots of it (max 72 h, so a weekend restart waits for the open); each snapshot in it is judged against the PREVIOUS shas' snapshots in the same session bucket (last 14 days): flagged only when above that baseline's p99 AND modified z (median/MAD) > 3.5 — no fixed thresholds, "learning" until 60 baseline samples. Two system-imposed hard limits apply regardless of history: detection-pass time at the poller's abort time (`DETECTION_POLL_ABORT_MS`) and row→order delay at the entry lookback (`ENTRY_LOOKBACK_MINUTES`). 2 consecutive flags show the red **"SLOWER SINCE LAST CHANGE"** quick-check banner (`perfAttention` in `/api/setups/live-flags`, names the sha); 3 save an `INCIDENT` row (heaviest query shapes/routes/pool/loop) + an OPEN_DECISION. When the watch ends a `VERDICT` row records per metric WORSE / BETTER / NOT_WORSE (post vs pre-deploy medians), a memory-growth check against earlier boots, and which sessions were never observed; WORSE metrics open an OPEN_DECISION. **To say what a change is meant to achieve, run `node scripts/perf_expect.mjs <metric> <down|up> "<why>"` BEFORE restarting** — the verdict then reports MET / NOT_MET / NOT_OBSERVED for it and flags NOT_MET. Scheduled calibration steps are timed too (`scripts/lib/job_timing.sh` → `job_timings`, each step compared with its own earlier runs; a clearly slower step opens a LOW decision naming the git shas). Outside a watch window the live metrics are not judged. It never restarts or kills anything (a real position may be open). **After any change: leave the server running through the watch, then `node scripts/perf_report.mjs`** (per-sha medians/p90 + deltas). The Stop hook (`check-docs-drift.sh` section 5) reminds whenever `acd.js`, `queries.js`, `db.js`, `index.js` or another hot-path file changed. Known blind spot: slowdowns that grow with data over weeks are not caught by a change-tied watch — check growth-prone queries when they are written. Tests: `node scripts/test_perf_telemetry.mjs`.

- **Detection speed lessons (2026-10-19, found with the query profiler `GET /api/diag/query-profile` -- local only, also has per-route `requests` and `eventLoop`).** (1) **Postgres JIT was on and cost ~1.3 s on the view-based plans** (prior-day IB query 1,635 ms with JIT vs 276 ms without, identical rows) -- `db.js` now runs `SET jit = off` per connection. (2) **`getCached()` defaults to a 60 s TTL**: day-stable values read without `DAY_CACHE_TTL` silently recompute every minute (svwap sigma, delta percentiles, prior-month VA were ~2 s each, every minute). Pass `DAY_CACHE_TTL` for anything built only from strictly-prior days, and never cache null/empty. (3) **A `ts >= (SELECT MAX(ts) FROM price_bars_primary ...) - interval` window anchors on the VIEW and is ~10x slower than anchoring on the raw `price_bars` table** (801 ms vs 72 ms, identical rows). (4) **The detection response cache (20 s) swallowed every other 15 s poll** -- real passes ran every ~30 s; the server poller now sends `?fresh=1`. (5) Order sweep latency: orders are placed by `sweepRealOrders()`, which used to run only at the START of a pass, so a row inserted late in pass N waited for pass N+1 (median row-to-order 25-36 s, max 64 s); a second, sequential call now runs at the END of each pass (not a timer -- DeepSeek's design review found a 3 s timer lets entries race the resolver and multiplies uncached gate queries). (6) Page-polled heavy endpoints (`market/pulse`, `live-session-context`) have a 15 s micro-cache with request coalescing (`server/lib/microCache.js`). Objective metrics: `process_log` `SETUP_DETECTION_POLL` outages per RTH day (baseline 49-156), row-to-ENTRY-order delay (`scratch` query in OPEN_THREADS 2026-10-19), and the profiler's DB-time-as-%-of-wall-clock (113% -> 22% after the first round). Rule: **measure with the profiler, in steady state (after the cache warm-up), before and after -- a cold-start window after a restart looks 3x worse than reality.**

Rebuilding the same test with flow z-scored against a 90-day trailing per-minute-of-day baseline (`scratch/lib_delta_baseline.mjs`, modeled on `touchQuality.js`'s existing `getVolumeBaseline()`) gave a cleaner, more honest answer: even the *strongest* aligned-flow bucket (z>1) was statistically flat (CI crosses zero) — the original "stay in when flow stays strong" hypothesis did NOT hold up once properly normalized. The mirror case DID hold up cleanly: a reversal CONFIRMED by flow (z<=-1) predicts a real, clean loss if held through (-$10.52/trade, CI=[-$18.80,-$2.11], 60 distinct days). **Standing pattern across this entire research thread, not just this one test**: order flow in this roster looks like a more reliable "something's turning, get defensive" signal than a "trust it, stay in" signal — confirmed independently in 3 separate tests the same day (this one, a T1-floor-runner order-flow split, and the Friday 2026-10-02 ML-veto-gate trace). - **A step-function walker's completion-pass walk must start STRICTLY AFTER the bar that triggered it, never AT that bar — 2nd confirmed occurrence of this exact bug, found 2026-10-04 reproducing `t1FloorRunnerWalker.js`'s own validated backtest.** Feeding `stepT1FloorRunner()` a walk that starts at the T1-touch bar itself makes its own `floorHit` check trivially true on bar zero (the touch bar IS where price reached the floor level) — a false immediate resolution, not a real one. Produced a wildly wrong result (mean $0.40/trade vs. the documented, correct $8.26/trade) before being caught by the magnitude mismatch alone — same underlying lesson already in the Conventions section below ("completion-pass walk-start point must match the new step function's own semantics, not a sibling's"), now confirmed recurring on a SECOND walker, not a one-off. When reproducing or extending ANY existing step-function walker for a new test, verify the walk-start point strictly after its triggering bar before trusting a result that disagrees with an already-documented baseline — don't assume a disagreement is a new finding before ruling out this exact bug.
