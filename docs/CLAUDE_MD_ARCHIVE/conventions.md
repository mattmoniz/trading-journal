<a id="cv-001"></a>

- **When a real `active_setups` row's outcome rests on a basis the live system wouldn't actually accept (a stale price, a fill found only by ignoring the order's real expiry), add a boolean `*_basis` column and wire it into `REAL_TRADE_FILTER`'s exclusion list — never delete the row, never let it count as ordinary real N/EV either.** Recurred 5 times now (`ib_window_stale_basis`, `stale_entry_price_basis`, `late_fill_past_expiry_basis`, `bad_bars_basis`, and `stale_levels_basis` added 2026-10-27, set per row by evidence in `scripts/flag_stale_levels_basis_20261027.mjs`: the entry lies closer to the old level than to the corrected one; the flag is wired into `REAL_TRADE_FILTER` and `calibrate_live_roster.mjs`, NOT into the quick-check Performance card, which still shows every real fired trade) — see [docs/CONVENTIONS_DETAIL.md#flag-and-preserve-a-boolean-basis-column-excludes-a-row-from-real_trade_filter-without-deleting-its-history](../../docs/CONVENTIONS_DETAIL.md#flag-and-preserve-a-boolean-basis-column-excludes-a-row-from-real_trade_filter-without-deleting-its-history) before inventing a 4th one-off version.


<a id="cv-002"></a>

- **An MFE-to-risk ratio ("R-multiple") is only a meaningful "does this setup run far" metric when stop and target are a CALIBRATED PAIR (e.g. from `OPTIMAL_STOP`) — it's meaningless for a setup whose stop and target are each anchored to their OWN independent real structural level.** Found 2026-09-24 (user pushback: "why did they hit two huge targets today" after being told `A_UP_STRONG`/`C_PAIRED` have no real "propensity to run 2x+"): those setups' stop = Opening Range Low, target = Prior Day VAH — two unrelated real price levels, not a proportional pair. The resulting risk-to-target ratio on 15 real historical `C_PAIRED_LONG` trades ranged from **0.01 to 105.50** — pure noise driven by where entry happens to land between two fixed levels that day, not by how far price ran after entry. Averaging or ranking setups by this ratio for such a setup is meaningless (a low average doesn't mean "doesn't run far," a high one doesn't mean it does) — it was purely measuring how far apart two unrelated levels were, session to session. **The right metric for this shape of setup is TARGET_HIT rate (does price ever reach the independently-placed level), not MFE/risk.** Real numbers found: `C_PAIRED` (N=193) resolves `TIME_EXPIRED` 75.6% of the time (rarely resolves cleanly at all) but hits target more than stop when it does (26 vs 21, a real 55% edge among resolved trades) — so today's home runs were genuine (the setup does tend to win when it resolves), just not evidence of a "runs far" propensity, which was never the right question for this setup family. Before computing or trusting an MFE/risk-ratio-based "propensity to run" stat for ANY setup, check whether its stop and target come from the same calibration process (fair) or from two independently-anchored structural levels. **Exhaustive, code-derived list (not a guess): `server/config/setupTypes.js`'s `LEVEL_ANCHORED_EXIT_TYPES`/`usesLevelAnchoredExit()`** — every setup whose exit runs through `acdCandidateBuilder.js`'s `t1GuardLabeled()` (`TRT_LONG/SHORT/_V2/_MAH_LONG/_MAH_SHORT`, `A_UP_STRONG`, `A_DOWN_WEAK`, `C_PAIRED_LONG/SHORT`, `C_REVERSAL_LONG/SHORT` — 12 types total). **A first draft of this list wrongly guessed `ZONE_EDGE_FADE`/`FAILED_AUCTION` into it** — checked against the real code the same day and both actually use a calibrated exit (`OPTIMAL_STOP`/ATR-scaled), not independent levels; corrected before it was used anywhere. For this 12-type family, use TARGET_HIT rate, never MFE/risk.


<a id="cv-003"></a>

- **Two resolvers on different timers can race at the same expiry instant — a setup with its own designed-exit branch in `resolveSetupsByPrice()` (15s poll) must be excluded from the generic `expireStaleSetups()` backstop (60s timer) for a grace window, or the backstop wins some fraction of the time and writes the wrong `resolution_method`.** Found 2026-09-25: 7 of 36 `POC_ROTATION_JOIN` designed-timeout wins since 2026-09-15 were labeled `MARK_TO_MARKET` (excluded by `REAL_TRADE_FILTER`), silently shrinking the best setup's real N/EV; fixed via `DESIGNED_TIMEOUT_EXIT_PREFIXES` (`setupTypes.js`) + a 5-min grace in `setupExpiry.js`. Diagnostic that found it: `resolved_at` with fractional seconds = written by `NOW()` (the backstop); whole-minute = a bar timestamp (the designed branch). Any new custom-resolution setup family must be added to `DESIGNED_TIMEOUT_EXIT_PREFIXES`. Related structural gap, not fixed: `backtest_setup_status.mjs` computes WR as `TARGET_HIT` only, so target-less designed-timeout setups store WR=0% and can never clear PROMOTE's WR floor (`OPEN_DECISION poc_rotation_join_structurally_unpromotable_20260925`).


<a id="cv-004"></a>

- **A `setup_type` with no `_OVERNIGHT` suffix is NOT guaranteed to be RTH-only — some level families (e.g. `PD_VAH`) fire under the identical setup_type name in both RTH and Globex hours, distinguished only by the `is_rth` column.** Found 2026-09-24 building a market-event-substrate reconciliation pilot (`scripts/pretest_market_event_substrate_reconciliation.mjs`, Opus Audit #14 section 5): an RTH-only bar-derived touch scan was compared against the REAL fire population without an `is_rth` filter — 55.6% of real `PD_VAH_FADE_*` fires in the test window turned out to be Globex-hours fires of the exact same setup_type name, producing spurious "timing gaps" up to 19 hours that looked like a serious detection failure before being traced. **Any analysis/backtest/substrate that scopes its OWN detection to RTH-only (or Globex-only) bar history must ALSO filter the real-trade comparison population by `is_rth` explicitly — never assume a setup_type's naming implies which session it fired in.**


<a id="cv-005"></a>

- **When matching a real event against a bar-derived "touch" proxy for a level, record EVERY separate touch episode in a session, not just the first.** Same 2026-09-24 pilot: v1 recorded only each day's first touch of the level as "the" substrate event, matching every real fire that day against it — a level tested multiple separate times in one session (common) means a fire on, say, the 3rd touch gets compared against the 1st touch's timestamp, producing a spurious multi-hour "gap" that reads as a detection failure rather than a matching-granularity bug. Fixed by detecting every distinct touch episode (a bar-run where price is within the proximity threshold, collapsing consecutive touching bars into one event) and matching each real fire against its OWN nearest same-day episode, not the day's first one.


<a id="cv-006"></a>

- **A script that retrains itself on a sliding window and re-checks its own significance every day is optional stopping, even when each individual check is honest.** Found 2026-09-24 (Opus Audit #14, evaluation-protocol section): `scripts/tick_microstructure/recheck_tick_trend_fade_finding.mjs`'s daily retrain-and-recheck shared ~99% of its data day to day, so its own AUC/p-value history was one noisy measurement drawn repeatedly, not independent evidence — "promote once p<0.05 shows up" while checking daily inflates the real false-positive rate regardless of how the check itself is written. **Fix pattern, reusable for any future daily/weekly self-recalibration script in this codebase: freeze a canonical model/checkpoint once (with its own feature list and training cutoff saved), keep the daily retrain running only as informational drift-tracking, and pre-register a single future look (a distinct-new-day floor, e.g. `>=20` days) before treating the frozen model's post-freeze score as a checkpoint to act on.** See `freeze_model.py`/`score_frozen_model.py` for the reference implementation.


<a id="cv-007"></a>

- **A "shuffle to break the signal" leakage control must use the SAME real features consistently on both the fit and predict side, or correlated features can leak signal through even a null-trained model — prefer this codebase's own day-block LABEL permutation convention over inventing a feature-shuffle control.** Found 2026-09-24 building `scripts/tick_microstructure/train_ordinal_model.py`'s harness-sanity check: a first attempt shuffled TRAINING features but then scored the resulting (garbage-fit) model against the REAL, unshuffled TEST features — since the underlying order-flow features are mutually correlated, the model's noise coefficients still picked up real structure through the test set's own real feature correlations, producing a spurious "leakage" reading (Spearman=0.212, p=0.0014) on a check meant to land near zero. Fixed by switching to the already-established day-block permutation null (`day_block_permutation_null()` in `train_fade_outcome_model.py`) — permute which day's real LABELS go with which day's real rows/features, refit, and check that the model can no longer predict the real test labels — which correctly read ~0 (Spearman=-0.0224, p=0.74). Any new ML pipeline in this codebase should reuse the day-block label-permutation null rather than a feature-shuffle variant.


<a id="cv-008"></a>

- **A `localStorage`-persisted drag-to-reorder column order must be MERGED against the current column set at load time, never just filtered against it.** The obvious-looking pattern (`(savedOrder || defaultKeys).map(k => COLS.find(c => c.key === k)).filter(Boolean)`) only ever drops a key that's no longer valid — it can never re-add a key that's new since the user's last drag. Reconcile any current-columns key absent from the saved order back in (appended at the end) in the `useState` initializer itself. See [docs/CONVENTIONS_DETAIL.md#localstorage-drag-reorder-must-be-merged-not-filtered](../../docs/CONVENTIONS_DETAIL.md#localstorage-drag-reorder-must-be-merged-not-filtered) for the incident (a brand-new column silently missing for any user with an already-saved order).


<a id="cv-009"></a>

- **Any new script querying `price_bars_primary` with a lower-bound-only `ts >= X` filter must add an explicit upper bound.** `price_bars_primary` is a VIEW (join + `GROUP BY` aggregation, confirmed via `information_schema.tables.table_type='VIEW'`) — it can never have an index, so an unbounded query forces the aggregation across everything from `X` through the present before it can sort/`LIMIT`. See [docs/CONVENTIONS_DETAIL.md#pricebarsprimary-needs-an-explicit-upper-bound-too](../../docs/CONVENTIONS_DETAIL.md#pricebarsprimary-needs-an-explicit-upper-bound-too) for the 15-20x speedup this produced in one script and the broader materialize-historical-bars decision it points at. The mirror case is just as real: an **upper-bound-only** query (`ts < X`, no lower bound) is equally unbounded in the other direction — `getRollingATR()` (`levelProximityService.js`) had exactly this shape and was fine at live call volume, but exhausted the DB connection pool when reused for a backtest at a wider window (fixed 2026-10-08, see the `MAJOR_PIVOT_DEFENDED_BREAK` entry below). **A bounded query alone isn't sufficient either** — if a function also fans a per-date/per-key async lookup out via an unbatched `Promise.all`, a live-scoped function (normally few enough concurrent calls to never notice) can still exhaust the pool the moment it's reused at wider scope; batch it (see the same entry for the fix pattern) before trusting a live-scoped function is safe to reuse widely.


<a id="cv-010"></a>

- **Never look up a bar by an exact epoch/timestamp match against a real trade's `fired_at`** — real trades carry genuine sub-minute precision (recorded live via `NOW()`), but bars are always exactly on the minute, so an exact match silently fails and the trade gets dropped, not flagged. Floor the timestamp to the minute before the lookup. See [docs/CONVENTIONS_DETAIL.md#floor-timestamps-to-the-minute-before-matching-bars-to-firedat](../../docs/CONVENTIONS_DETAIL.md#floor-timestamps-to-the-minute-before-matching-bars-to-firedat) for the incident (31 real trades silently erased, producing a false "zero occurrences" finding).


<a id="cv-011"></a>

- **A live/shadow query reading "the most recently closed 1-min bar" via `ts < date_trunc('minute', NOW())` can silently read a bar ONE MINUTE TOO OLD for any candidate firing within the first several seconds of a new minute — the Sierra ingestion pipeline (`sierraWatcher.js`, 5s poll + 2s stability debounce by default) has real lag writing each bar into `price_bars_primary` after its minute closes, and the query has no way to distinguish "genuinely the latest bar" from "the latest bar that happens to be ingested yet."** Found 2026-09-17 (user pushed on why `entryOrderFlowShadow.js`'s EFS tag didn't fire on a real trade, circled live on quick-check.html): ~1/3 of a real day's RTH fires land within ~15s of their own minute boundary — exactly the window where the just-closed bar may not be ingested yet, and the query then silently falls back to the previous bar with no flag anywhere that this happened. Didn't change that specific trade's verdict (both candidate bars agreed: net selling), but is a systemic staleness risk for any future logic reading "the latest bar" right at fire time. Fixed in `getPriorClosedBarDelta()`: compute the EXPECTED most-recent-bar timestamp, compare it to what's actually available, retry once after ~8s if stale, and persist a `barStale` flag either way so a future audit can see when it didn't resolve — reuse this pattern (expected-vs-actual + one bounded retry + a stored staleness flag) for any other "read the latest bar right now" query, rather than trusting the naive `NOW()`-truncation query blind.


<a id="cv-012"></a>

- **Comparing a `NOW()`-derived timestamp string against a naive (`timestamp without time zone`) column's own timestamp string needs an explicit `::timestamp` cast before `::text` — `NOW()::text` carries a `-04`/`-05` UTC-offset suffix that a naive column's `::text` never does, so a raw string-equality compare silently never matches.** Caught while building the fix above (`entryOrderFlowShadow.js`), before it shipped: the expected-bar-timestamp check was first written as `date_trunc('minute', NOW())::text` compared against `ts::text` from `price_bars_primary` (naive) — would have always mismatched, making `barStale` permanently `true`. Fixed via `NOW()::timestamp::text` (applies the session's own `America/New_York` `TimeZone` setting per `db.js`'s own header comment on why naive columns store ET digits, not a hardcoded offset). Any future string- or exact-equality check between a `NOW()`-derived value and a naive column needs this cast first — verify with a direct `SELECT NOW()::text, NOW()::timestamp::text` before trusting a new comparison like this.


<a id="cv-013"></a>

- **`WEEKLY_VWAP` (`level_prices`, `compute_levels.js`) is ALL sessions from the first Globex bar of the week (Sunday 18:00 ET) through the START of the row's trade session (the prior evening 18:00); `MONTHLY_VWAP` is ALL sessions from 00:00 ET on the 1st of the month through the same cutoff (user 2026-10-27; by calendar date, so the Globex evening of the previous month's last day belongs to the previous month); neither has a row on a trade date with no earlier bar in its period (a Monday 1st, or the Monday after a Sunday 1st) or on weekend dates.** Redefined 2026-10-27 (weekly: user request; same first-Globex-bar anchor `WEEKLY_OPEN` uses, so holiday weeks need no special case). Before that the historical rows included the trade day itself while live wrote as-of-open, a lookahead of a median 54 points in every WEEKLY_VWAP/MONTHLY_VWAP backtest; any number measured on those rows (the old `WEEKLY_VWAP_LONG/SHORT` -19/-11 per trade) should not be cited. A cutoff at 09:29 would look more current but includes bars after an evening Globex fire on the same trade date; the start-of-trade-date cutoff is deliberate. See `docs/OPEN_THREADS.md` 2026-10-27 and claim `weekly_vwap_short_asofopen_backtest_flip_20261027`.


<a id="cv-014"></a>

<a id="cv-015"></a>

- **A `level_prices`-style "prior day" lookup (`WHERE trade_date <= X ORDER BY trade_date DESC LIMIT 1`) silently goes one extra session stale across any 2+ day market closure (a weekend, a holiday) — search `>=`/`ASC` (the nearest FOLLOWING-OR-EQUAL checkpoint), not `<=`/`DESC`.** `level_prices.trade_date` is the day a row APPLIES TO (it describes the session immediately BEFORE that date), so on a normal weekday `X` always has its own exact-match row and either search direction returns the same thing — but on a Saturday/Sunday `X` (a real calendar date some callers legitimately compute, e.g. `resolveDepartureDay()` during a Sunday-evening Globex reopen), there's no row for `X` at all, so `<=`/DESC falls back to the LAST row that exists — which, under the same convention, describes the session BEFORE the one you actually wanted. Found 2026-09-14 in `globexFlushDetector.js`'s `findDeparture()`: for a Sunday `departureDay`, `<=`/DESC picked Friday's own `trade_date` row (describing Thursday's close) instead of the row under `trade_date=Monday` (describing Friday's actual close, needed for a Sunday-evening departure check) — fixed by flipping to `>=`/ASC, verified byte-identical to the old query on all 44 real trading days checked, differing only on the weekend gap it was silently wrong on. Any new `level_prices` lookup using this "closest prior applicable row" pattern needs the same `>=`/ASC direction, not `<=`/DESC, or it will re-introduce this same one-session staleness the next time it crosses a closure.


<a id="cv-016"></a>

- **A "pick the most recent CALENDAR date with any bar data, THEN filter to a hour-of-day window" query against `price_bars_primary` silently returns NULL (not stale data) on the first trading day after any 2+ day closure — a different, worse failure mode than the `level_prices` staleness bug above, and not caught by an existing `.catch()`.** `getPriorDayRthRange()` (`server/services/queries.js`, shared by `momentumChaseDetector.js` and `acd.js`'s Stop Sweep detection) picked `MAX(ts::date) WHERE ts::date < X` first, then filtered that date's bars to RTH hours (570-959 min) — on a Monday, the "most recent date with any data" is Sunday, which has real Globex bars but ZERO real RTH bars, so the RTH filter matches nothing and `MAX`/`MIN` return NULL. The function's own `.catch(() => ({rows: []}))` didn't catch this because the query never threw — it's a **successful query returning a legitimate-looking empty/null result**, the same blind spot as `getCached()`'s null-vs-undefined footgun elsewhere in this codebase, just triggered by a calendar gap instead of a cache miss. Found 2026-09-21 (user-caught live: NQ up 200+pts in an hour, `MOMENTUM_CHASE_MEDIUM_LONG` structurally could not fire despite a favorable regime and price clearly through the real prior-day high, because `pdHigh`/`pdLow` were silently null) — the function was only 12 days old, so this had a narrow footprint (checked: the other affected Monday, 9/14, would not have fired regardless — price wicked past the real prior high but no 5-min bar ever closed above it — so this was 1 real trade delayed ~54min/entered ~200pts worse, not a long-running loss). **Fixed by moving the hour-of-day filter INSIDE the subquery that picks the date**, so it can only ever select a date that genuinely has bars in that window — the same shape of fix as the `level_prices` convention above (search for a real match, don't fall back to "closest date regardless of whether it actually qualifies"), one level more dangerous here because the failure is silent NULL, not silently-stale-but-present data. - **`active_setups.status` (lifecycle: `ACTIVE`/`SHADOW`/`RESOLVED`/`EXPIRED` — is this position still open) and `active_setups.origin_status` (provenance: `ACTIVE`/`SHADOW`/`BACKFILL`/`UNKNOWN` — was this ever shown as a real live alert) share the literal string `"SHADOW"` for two completely unrelated concepts, and this confuses real users, not just code.** Found 2026-09-21 (user, after `MOMENTUM_CHASE_MEDIUM_LONG` fired live and correctly went missing from both the "Live" and "All" Session Timeline toggles): the Live/All toggle only ever filters `origin_status`; the timeline ALSO unconditionally excludes any row with lifecycle `status IN ('SHADOW','ACTIVE')` (i.e., anything not yet resolved) regardless of that toggle — so a genuinely real, origin-`SHADOW`-tagged trade that's still *open* is invisible everywhere until it resolves, and the reason has nothing to do with which toggle is selected. `range-summary`'s own code comment already flags this exact naming collision risk for developers ("an easy pair to conflate since both use 'ACTIVE'/'SHADOW' as literal values for two unrelated concepts") but nothing warned that it also produces genuinely confusing UI behavior for the user. <a id="cv-018"></a>

- **A bare Python `None` in a single-row `pd.DataFrame` with no OTHER value in that column to force numeric inference gets `dtype=object`, which a downstream numeric consumer (LightGBM's `predict`/`predict_proba`, and likely others) flatly rejects — and this is invisible in a BATCH context, only appearing the moment a caller builds a single-row frame straight from raw values.** Found 2026-09-21 building `score_one.py` (fire-time ML scoring, `scripts/ml_meta_labeling/`): `score_candidate()` (`score.py`) had worked correctly in `run_silo_scoring.py`'s batch loop for weeks despite iterating one row at a time internally, because each `features[col]` value there was read off an already-typed pandas Series (built from a full DataFrame where OTHER rows had real floats in that column, so pandas correctly inferred `float64` with `NaN` for the missing ones) — a numpy `float64 NaN` carries its own dtype and infers correctly even alone in a fresh single-row frame. A caller reading straight from the DB into a plain Python dict (exactly what any future live-inference/microservice caller would also do, and exactly what `score_one.py` does) passes a bare Python `None` instead, which has no dtype information at all, so `pd.DataFrame([{...single row with a None...}])` defaults that column to `object` — LightGBM's `_check_for_bad_pandas_dtypes` then raises `"pandas dtypes must be int, float or bool"`. Fixed with explicit `row.apply(pd.to_numeric, errors='coerce')` right after building the single-row frame, verified via a full batch-scoring regression (identical TAKE/VETO counts before and after, since the batch path never hit this). Any function built to score/predict on ONE row at a time from raw (non-pandas-Series) input needs this same explicit numeric coercion — the batch-tested version of the same function is not sufficient proof it's safe for single-row live use.


<a id="cv-019"></a>

- **An OVERNIGHT-suffixed level-fade trade's reported `mfe_points`/`mae_points` (and any "captured vs. available" / "left on the table" stat derived from them) can be almost entirely an artifact of an untradeable price GAP, not real captured price action — check whether the touch was a gap-through before trusting the number.** `mfe_points`/`mae_points` are computed by walking bars from `fired_at` to `resolved_at` and measuring excursion against the row's own static `entry_zone` (`resolveSetups.js` ~line 518-523) — if that entry is a level whose price sat far from where the market actually reopened (a weekend/holiday gap crossed the level without any bar ever trading through it), the "MFE" mostly measures the size of the gap itself, not anything happening during the trade's real, short bar-by-bar life. Found 2026-09-14: a real `10D_IB_MID_FADE_SHORT_OVERNIGHT` trade reported "43% of a 315pt MFE captured" — ~280pt of that 315pt was the Friday-close-to-Sunday-reopen gap itself (no continuous price path for any detector to trade through), and the market's real post-gap behavior over the next several hours was a contained ~120pt range, not a missed trend. Before treating a level-fade OVERNIGHT trade's MFE-based capture stat as a real missed-opportunity signal, check the bar immediately before `fired_at` against `entry_zone` — if they're far apart, the level was crossed by a gap, not touched continuously, and the MFE number is measuring the gap, not a tradeable move.


<a id="cv-020"></a>

- **A number that survives being computed twice by the same script is not verified — it only proves the script is consistent, bugs included.** Independent re-derivation (by hand with a different method, or dispatched to Gemini without showing it the original methodology) is what actually catches a deterministic bug a repeated run cannot. Audit a disagreement in both directions, don't assume whichever answer already existed is correct. See [docs/CONVENTIONS_DETAIL.md#a-number-computed-twice-by-the-same-script-isnt-verified](../../docs/CONVENTIONS_DETAIL.md#a-number-computed-twice-by-the-same-script-isnt-verified). **A specific instance of this same trap: when diagnosing why a dashboard/summary number looks wrong, a "verification" query that copies the same filter/scope the dashboard itself uses isn't independent — it just reproduces the same blind spot.** Found 2026-09-22: the ML Meta-Labeling Silo widget showed only 8 scored candidates for the day and looked like a broken live-scoring pipeline; a first diagnostic query "confirmed" this by filtering to the exact same single `model_version` the widget's own default view uses — because the model had been retrained twice that afternoon and `ml_verdicts` is keyed by `model_version` with no cross-version carryover, this just re-showed the same narrow slice. Dropping the `model_version` filter entirely (asking "was this trade scored under ANY model," not "under THIS one") immediately showed the real number: 67 of 68 real trades that day were scored — nothing was broken, the earlier verdicts were just sitting under a prior model version the default view no longer looked at. Before trusting a "confirmed the dashboard is right/wrong" check, ask whether the check's own scope was borrowed from the thing being checked.


<a id="cv-021"></a>

- **Two script runs minutes-to-hours apart, both querying a live window like `WHERE trade_date >= X` with no upper bound (or an upper bound of "today"), are NOT comparable — the underlying population can genuinely grow between them as the live system keeps ingesting real data, and a population-size-dependent computation (a percentile boundary, a tercile cutoff, a rolling baseline) can silently shift enough to flip a result's sign.** Found 2026-10-08: a subgroup backtest (`POC_ROTATION_JOIN` fade-vs-continuation, split by leg duration) looked like a strong, real "fade wins" result in one run (+$53.6/trade, day-blocked CI excluding zero) and the opposite ("continuation wins," CI excluding zero the other way) in a second run of logically-identical code roughly two hours later — not a bug in the comparison logic itself, but because the total event population had grown from 1,553 to 1,631 real events in the interim (the live app kept running and adding real trading sessions), which shifted a duration-tercile cutoff used to define the subgroup. This is a close cousin of the standing "call the SAME code twice before attributing a diff to your own change" rule above, but sharper: that rule catches a REAL bug in changed code; this one is about a bug-free comparison becoming invalid purely because of elapsed wall-clock time against a live table, something re-running the identical script a second time won't even surface (both runs would individually look internally consistent). **Any research thread that runs more than one script against a live-growing table and compares the outputs must either (a) pin an explicit, fixed upper-bound date for every query in that thread and reuse it verbatim in every subsequent script, or (b) compute every comparison point within a single script's one continuous run, never across separate invocations.** Before trusting a cross-script comparison where the delta flipped sign or disappeared, check whether the two runs actually queried the identical population before concluding anything about the market.


<a id="cv-022"></a>

- **A trade-simulation "target" set to a self-referential statistic of the SAME population being tested (its own median/percentile MFE, its own mean, etc.) makes the resulting win rate a tautology, not a finding.** If ~half a population's outcomes are, by definition, above that population's own median, then "win = reached the median" will always land near 50% regardless of any real edge — the win rate measures nothing about the underlying signal's quality. Found 2026-09-10 (`scratch/zigzag_magnitude_filter_backtest.mjs`): a fade-trade backtest set each threshold bucket's target to that bucket's own p50 MFE, producing an eerily flat ~50.0-51.4% win rate across 6 wildly different thresholds — initially suspected as a too-tight-stop artifact, but widening the stop 10x (0.02x ATR → 0.30x ATR) left the win rate essentially unchanged, which is what confirmed the target itself, not the stop, was the tautology. Any backtest computing its own target/threshold FROM the same outcome population it then measures win rate against needs a target derived independently (a fixed value tested identically across every arm, or a value derived from a DIFFERENT population/period) before the win rate means anything. **Same trap, different shape, found the same day**: asking "does this ZigZag leg continue or reverse the immediately-prior leg's direction" is ALSO a tautology, not a finding — consecutive accepted ZigZag legs always alternate direction by construction (a LOW's leg goes up to the next HIGH, down to the next LOW), so that comparison is guaranteed to say "reversal" almost every time regardless of real market behavior. Caught after being reported out loud with the result misread in the bargain (an 99%-reversal number described as "99% continuation"). Always compare a leg's direction against an INDEPENDENT trend measure (real net price change over a genuine time window, a moving average) — never against its own immediately-adjacent leg.


<a id="cv-023"></a>

- **Never key a per-trade state object (a `Map`, a lookup keyed by timestamp) by `fired_at`/`fired_at_ms` in any event-driven simulation over `active_setups`.** 12.6% of real trades share an exact `fired_at` with another trade (confluence-cluster siblings fire within milliseconds of each other) — a Map keyed this way silently lets a later trade's state overwrite an earlier trade's entry under the same key, corrupting which trade's outcome gates which. Found 2026-09-08: a loss-streak backtest script keyed its suppression-state Map by `fired_at_ms` and produced a 75%-inflated result (RTH delta $3615.22 vs. the correct $1900.72), caught only by disagreement against an earlier, correctly-keyed script. Key by a genuine per-row identifier instead (array index, or the row's own `id`) — see `scripts/backtest_morning_weakness_deepdive_20260908.mjs`'s fix for the pattern.


<a id="cv-024"></a>

- **Any "find the last/prior real row of this same kind" lookup query (a same-setup-type reference fire, a prior-touch price, a last-signal timestamp — any `ORDER BY ... DESC LIMIT 1` intended to find a DIFFERENT row) must explicitly exclude the row currently being processed by its own `id`, not rely on a timing/ordering condition to do it implicitly.** If the lookup runs shortly after the current row's own INSERT (the common case — most of these shadow/gate mechanisms tag "right after insert"), the just-committed row is already visible to a subsequent SELECT and can satisfy a `fired_at < NOW()`-style bound trivially (a few milliseconds is still "before now") — on any day where no OTHER real row of that kind exists yet, the query silently matches ITSELF, and a "does the new value differ from the reference" check then compares a value to itself, which can NEVER be true. Found 2026-09-22 (user-caught live: "I see EFS working but never EFL" — turned out not to be rare, but structurally broken): `entryOrderFlowShadow.js`'s `getLastSameSetupFire()` had exactly this gap — confirmed decisively, all 123 of 123 affected historical rows had their "reference" price exactly equal to their own entry price. This silently zeroed out `LONG_REPEAT_ADVERSE_FLOW` for its entire life (0 flagged across 150 real evaluations) while the mirror `SHORT_MORNING_ADVERSE_FLOW` rule (no reference-lookup, no self-match risk by construction) worked fine the whole time — the asymmetry between two rules that are supposed to be comparable is itself a tell worth noticing. Fixed by threading the row's own `id` through as an explicit `excludeId` param (`IS DISTINCT FROM $N` in the SQL, not `!=`, so a genuinely-absent id on a retrospective/hypothetical caller doesn't accidentally exclude every row via SQL's NULL semantics) and backfilling the historical rows that had self-matched. **When auditing a mechanism that shows suspiciously low/zero real activity, checking for this exact bug shape — literally query whether the "reference" value stored on flagged-candidate rows ever differs from the row's own value — is a fast, decisive test** that distinguishes a real structural bug (every reference exactly equals its own row, impossible by chance) from a genuinely rare/weak signal (references exist and vary, just rarely satisfy the rest of the condition).


<a id="cv-025"></a>

- **A day-blocked bootstrap confidence interval needs correlated confluence-cluster siblings collapsed to one representative event BEFORE the resampling runs — deduping `is_cluster_primary`/`cluster_touch_id` for N/P&L aggregation (the existing hard rule below) does NOT also fix this.** These are two different bugs from the same root cause (one real touch producing 2+ correlated rows), caught by two different mechanisms: the N/P&L dedup rule prevents double-counting a touch's dollar total; this one prevents a CI from treating 2-3 highly-correlated outcomes (siblings agree on win/loss 85.7% of the time, measured 2026-09-22) as independent evidence, which inflates apparent statistical confidence even when the raw N/P&L numbers themselves are already correctly deduped elsewhere. Day-blocking alone (resampling whole trading days) doesn't catch this either — a day containing one big correlated cluster still casts as many "votes" in the resampled mean as its raw row count, not the ~1 real independent event it represents. Fixed in the ML meta-labeling silo via a new `collapseClusterSiblings()` (`server/services/rigorDiagnostics.js`) — collapse-by-cluster before `dayBlockedBootstrapCI()`, not instead of day-blocking. Reuse this for any future CI/significance test over `active_setups` outcomes, not just the ML silo.


<a id="cv-026"></a>

- **Confound checklist for any new comparison-style backtest (two arms compared against each other).** Before recording or promoting any "config/condition A beats B" finding, check all four:
  1. **Do the two compared arms differ ONLY in the hypothesis variable**, or does one arm have a structural/algebraic edge (a later entry against the same fixed exit, a smaller remaining risk distance)? Ask whether the "smarter" arm would still win with the intelligence stripped out and only the structural difference left.
  2. **Is the baseline computed by the exact same method/window as the thing being compared** — resimulated in the same pass, never read from a stored column computed under different historical conditions.
  3. **Does the signal select a sub-population** (overshot / made-a-new-extreme / pattern-present / any filter)? If so, is there a same-selection-minus-the-signal-condition control bucket — the `SIGNAL` / `SAME_SELECTION_NO_SIGNAL` / `NEVER_SELECTED` 3-way template in `scripts/pilot_cvd_divergence.mjs` is the pattern to reuse, not reinvent.
  4. **Was this the largest of K effects pulled from a sweep** (top-N setup_types, best candidate in a grid)? If so, run `computeReplication()` (`server/services/rigorDiagnostics.js`) — a held-out/permutation check that pools the selected subset against everything NOT selected and reports whether the direction and magnitude survive.
  Items 1-3 are domain-specific reasoning each time, not a generic detector (deliberately not built — would create false confidence); item 4 has a real, reusable function. See [docs/CONVENTIONS_DETAIL.md#confound-checklist-for-comparison-style-backtests](../../docs/CONVENTIONS_DETAIL.md#confound-checklist-for-comparison-style-backtests) for the 5+ times this exact failure shape recurred before the checklist was built.


<a id="cv-027"></a>

- **A containment/bound check that compares a window against a value DERIVED FROM that same window is a tautology, not a filter — it can never fail.** Found 2026-09-14: a "5-15 bar bounded range" containment check (`contained = every bar's high/low within buf of the window's OWN max/min`) was structurally guaranteed to pass, since `wHigh`/`wLow` are themselves the max/min of the bars being checked against them — no bar inside a window can ever exceed that window's own extremes. This silently made an entire multi-hour research population (a "battle zone" detector) non-restrictive — the real filtering was coming entirely from the OTHER conditions (level-proximity, eventual-breakout), not the containment check the population was named after. The tell was a suspiciously-round "100.0% of candidates passed containment" — when a supposedly-selective filter's pass rate is at or near 100%, check whether its bound is computed from an independent reference (a rolling ATR, a fixed distribution percentile) or from the very data it's screening, before trusting the population it produced.


<a id="cv-028"></a>

- **A sigma/std threshold's denominator must be sampled at a comparable frequency to the live reading it's compared against — a coarser-sampled denominator (e.g. one value per day) systematically understates real dispersion and makes an ordinary live reading look artificially extreme.** Found 2026-09-14 (user report: "are we really 4.8 standard deviations from VWAP??"): `getTrailingVwapStd()`/`getTrailing24hrVwapStd()` (`server/services/queries.js`, feeding the live `VWAP_MAGNET`/`GLOBEX_VWAP_MAGNET` trigger threshold, `threshold=max(50, std*1.5)`) built their std from ONE end-of-day-close-vs-VWAP sample per trading day, then compared a live INTRADAY distance against it — price naturally wanders further from a running VWAP mid-session than it typically ends up at the close, so an EOD-close-only sample understates the true intraday spread and any live reading compared against it reads more extreme than it really is (and, since this fed a live trigger threshold, made that threshold tighter than intended). Fixed via `sampleIntradayVwapDists()` (samples every 30 bars through each session, not just the close) — the general lesson: whenever a std/dispersion measure is used as the yardstick for a *live, moment-in-time* value, verify the historical sample it's built from is sampled at the SAME granularity as the thing being measured, not a coarser one.


<a id="cv-029"></a>

- **Any backtest with an asymmetric stop/target distance (target closer than stop, or vice versa) combined with a long or no time limit needs a placebo test — randomize the direction/signal label, re-simulate the identical structure, compare — before trusting ANY resulting win rate, even one that looks plausible rather than obviously too good.** A driftless random walk hits the near barrier before the far one with probability `farDist/(nearDist+farDist)` (gambler's ruin) — a target at 0.5x ATR against a stop at 1.5x ATR alone predicts a ~75% win rate with ZERO real directional skill. Found 2026-09-10 (`scratch/defended_breakout_phase3_notimeout_confluence.mjs`): removing a time cap on a defended-level-breakout backtest produced a spectacular-looking WR=82.2%/EV=$114.79 that was correctly not trusted on sight (extreme sweep result → hand-trace) and was proven purely geometric via a same-structure random-direction placebo (WR=81.5%/EV=$95.76, nearly identical). **The dangerous part: the SAME placebo method, applied retroactively to an earlier, much more modest-looking capped-at-720min result from the same thread (WR=57.5%, EV=$16.96) that had NOT been flagged as suspicious, also failed** (real WR=58.1%/EV=$22.82 landed inside the noise range of 5 independent placebo trials). A result that looks reasonable is not automatically exempt from the same scrutiny that catches an implausible one — if the stop/target geometry is asymmetric, placebo-test by default, not just when the number looks too good.


<a id="cv-030"></a>

- **In any backtest or resolver, a stop that takes effect when the market is ALREADY beyond it must fill at the market (that bar's open), never at the stop price — "arm a stop to level X after N minutes" mechanisms are where this bites.** Found 2026-10-20: the live POC_ROTATION_JOIN breakeven-hold exit (shipped 2026-10-11 on a +39 dollars/trade backtest) snapped the stop to entry at minute 60 and booked any trade that was underwater at that moment as a breakeven exit; a real stop at entry above the market closes at market. With realistic fills (`exit = min(stop, open)` for a long, `max(stop, open)` for a short; two independent builds agreed) the advantage fell to about +2.5 vs the plain fixed-stop exit (not significant), the profit-lock variants that looked decisive (+14.7) lost all advantage, and 8 of 14 live exits sat at the arming bar booked at -2 while the broker flattened at the real price. The same trap hid behind a spec line ("if a stop is hit the exit price is the stop price") that two independent builders followed faithfully, so agreement between builders does not test the fill assumption itself. Before trusting any backtest that moves a stop at a time or on a lock rule, replay it with the market-fill rule. See `RESEARCH_CLAIM poc_join_breakeven_hold_advantage_overstated_20261020` and `OPEN_DECISION poc_rotation_join_exit_decision_after_fill_artifact_20261020` (audit of the other arm-a-stop mechanisms is still open).


<a id="cv-031"></a>

- **A research script that feeds a live detector's function must call it with the SAME inputs the live poller does, and its event population must be checked for overlap with real live rows before any result is trusted.** Found 2026-10-20 (a divergence between two independent builds exposed it): `detectSignalEvents()` builds a volume-weighted rolling median profile, and the live poller (`pocRotationJoinDetector.js:131`) passes bar `volume`; the 2026-10-08/12 POC_ROTATION_JOIN validation scripts and everything written from their loader on 2026-10-19/20 selected only open/high/low/close. See `RESEARCH_CLAIM poc_join_research_no_volume_degenerate_detector_20261020` and `OPEN_DECISION poc_join_edge_unproven_live_construction_20261020`. `scripts/lib/pocJoinLoader.mjs` now defaults to `withVolume: true`.


<a id="cv-032"></a>

- **Never pass claim/decision text containing a literal `$` through `node -e "..."` (or any inline double-quoted shell string) — write it to a real file and execute that instead.** Bash interpolates `$<digit>` as a positional shell parameter (usually empty) before Node ever sees the string, silently corrupting the text with no error at write time — `$0.96` becomes `/bin/bash.96`, `$16.96` becomes `6.96` (the `$1` vanishes). Found 2026-09-10: a `recordClaim()` update sent via `node -e "..."` corrupted every dollar figure in a persisted `RESEARCH_CLAIM` row; caught only by chance, re-reading the row back during an unrelated verification check — the write itself reported success. `scripts/record_claim.mjs`/`flag_decision.mjs` calls with any `$` in the text must go through a `.mjs` file (`node scratch/some_file.mjs`), never an inline `-e` string.

- **`quick-check.html`'s every `fetch()` call must pass `{ cache: 'no-store' }` — this is a live polling dashboard, and a plain `fetch()` without it can silently serve a browser-cached response on mobile Safari, especially via the Cloudflare Tunnel, since the server sends an `ETag` (Express's default) with no explicit `Cache-Control` header.** Found 2026-09-22, user-caught live via a screenshot: the Session Timeline card was frozen at 7:43am while other cards on the same page kept updating, and the ML Silo modal's "All" P&L was reportedly identical for 2 straight days. Root cause: none of this file's 24 `fetch()` calls specified a cache mode, so the browser's default HTTP cache could revalidate-and-reuse a stale response instead of hitting the live endpoint — this affected every polled card equally, but was only humanly *visible* on slow-changing data (a trade list that only gains a few rows per hour) vs. fast-changing data (a volume z-score that looks "fresh" even if it's technically 30s stale). The existing `visibilitychange` handler (2026-09-17, forces every `load*()` to re-fire when the tab regains focus) only made the JS *retry* the fetch — it never told the browser to bypass its own HTTP cache, so the retry could still resolve to the same stale cached body. Fixed by adding `cache: 'no-store'` to all 24 call sites (`scratch/add_no_store_20260922.mjs`, a bracket-aware script, not a naive regex — several calls have a nested function call in the URL expression, e.g. `todayET()`, which a simple `fetch\([^)]+\)` regex would have broken on). **Any new `fetch()` added to this file must include the same option** — a live trading dashboard should never serve browser-cached data, and this bug class won't throw a JS error or show up in any log (this file has zero client-side error reporting), so it can only be caught by a direct report like this one or by deliberately checking network behavior, never by reading server logs. **A deeper version of the same bug, found the same day, right after the above fix was shipped and verified**: fixing every `fetch()` call's caching doesn't help if the HTML DOCUMENT ITSELF — the file containing that JavaScript — is also browser-cacheable, since a stale page load runs stale JS regardless of how fresh its own fetches would be. `server/index.js`'s 3 standalone pages (`/quick-check`, `/setup-performance`, `/loss-prevention`) are served via a bare `res.sendFile()`, whose Express default is `Cache-Control: public, max-age=0` — confirmed via `curl -D -`, not assumed. User report: a just-shipped, server-verified feature (a dismiss button) "still" wasn't visible client-side. Fixed with a shared `noCacheHtml()` helper (`res.set('Cache-Control', 'no-store')` before every `res.sendFile()` call) on all 3 routes. **Any new standalone `server/public/*.html` page's route needs the same header** — this is a distinct fix from the fetch-level one above; both are needed, neither substitutes for the other. **The same bug class recurred a 3rd way, found 2026-09-28 (DeepSeek design-critique review, scoping a not-yet-built Sierra Chart control dashboard) — this time in the React app itself, not `quick-check.html`.** `src/utils/useSharedPollData.js` and its sibling `usePollData.js` — the shared polling hooks most of the React app's own live data (Morning Prep, Dashboard, etc.) goes through — had the identical bare `fetch(url)` with no cache mode, the whole time, never caught because the 2026-09-22 fix was applied per-callsite to `quick-check.html` specifically and never swept to the React app's own shared utilities. Fixed the same way (`cache: 'no-store'`) in both files. **The generalized lesson, not just a 3rd instance to log**: a stale-HTTP-cache fix applied at the call-site level does not protect a *different* file that reaches the network a different way — check every shared fetch utility/hook a codebase has (`grep 'fetch('` across `src/utils/`, not just the file where the symptom was reported) whenever this bug class is fixed anywhere, and before building anything new (like a real-money control dashboard) that will poll through an EXISTING shared hook, verify that hook already has this protection rather than assuming it does because a similar-looking page was fixed once.

- **A delegated `document`-level BUBBLE-phase click listener's `stopPropagation()` cannot stop an ANCESTOR of the click target from firing its own `onclick` — bubbling reaches that ancestor before the event ever reaches `document`.** Found 2026-09-28 (same investigation as the filter-persistence bug above): `quick-check.html`'s `#timeline-head` has `onclick="toggleTimelineCollapse()"` on the whole header row, and the Live/All/Globex toggle buttons inside it are handled via a delegated `document.addEventListener('click', ...)` (the standard pattern here, since these buttons are recreated by `innerHTML` on every 20s poll — see the comment directly above it). <a id="cv-074"></a>

- **Never parse a naive (no-timezone) timestamp string with `new Date(str).toISOString()` — it silently depends on the ambient process/system timezone, not on any timezone you actually intend.** The pattern to reuse for any future naive-local-timestamp parsing: guess a UTC instant from the naive components, ask `Intl.DateTimeFormat` what that guess actually looks like in the target zone, then correct by the wall-clock difference — this correctly handles both EDT and EST per-date, unlike a hardcoded offset (`etNaiveStringToUtcIso()` in `sierraParser.js`). **Process lesson: don't trust "recent data looks right" as proof a timestamp pipeline is healthy** — verify via the raw source string against the stored column directly, not the rendered UI. See [docs/CONVENTIONS_DETAIL.md#naive-timestamp-parsing-depends-on-ambient-timezone](../../docs/CONVENTIONS_DETAIL.md#naive-timestamp-parsing-depends-on-ambient-timezone) for the multi-month timezone-flip incident and the two duplicate-import cleanups it led to. **A second, distinct failure mode in the same family, found by DeepSeek code review 2026-09-10**: `new Date(naiveTsStr.replace(' ','T')+'Z').getTime()` compared directly against `Date.now()` is a live-breaking bug, not just an imprecise one — the naive string gets mislabeled as UTC (running ~4-5h behind its true epoch), so `Date.now() - thatValue` computes a genuinely fresh (5-real-minutes-old) signal as ~245 minutes old. Both `majorPivotDefendedBreakDetector.js` and `stallDefendedLevelDetector.js` had this exact bug in their "is this signal recent enough to insert" check (30/60min windows), meaning **neither live detector could ever have actually inserted a real setup** — confirmed by direct calculation before fixing, caught before either had fired live (real N=0 for both at the time). Fixed via a new shared `etNaiveTimestampToMs()` (`acdShared.js`, wraps the already-existing, now-exported `etNaiveStringToUtcIso()`) — use this for ANY comparison between a naive bar/entry timestamp and a genuinely-UTC anchor (`Date.now()`, `NOW()`-derived values). **Naive-vs-naive arithmetic does NOT need this fix** — computing `expires_at` by adding minutes to the same mislabeled value is self-consistent and was never actually wrong, since the mislabeling only matters once something touches a true-UTC value. **A third, distinct failure mode in the same family, found 2026-09-22**: `minutesSinceOvernightOpen()` (`server/services/globexRotationBadge.js`, imported by `overnightOrderflowEntryDetector.js`) built its ET Date the standard Z-mislabeling way but then read it back with **local** getters (`.getHours()`/`.getMinutes()`) instead of UTC getters — this is the exact inverse of the two failure modes above (which correctly built a Z-mislabeled Date but then compared it against a genuinely-UTC anchor without correcting) and is arguably more dangerous, because it produces plausible-looking wrong numbers rather than an obviously-huge drift: since this process runs with `TZ=America/New_York` (asserted at startup, `server/index.js`), local getters silently applied the ET-UTC offset a SECOND time on top of the Z-mislabeling, systematically misclassifying which side of a checkpoint (9pm/12am) a bar fell on — badge and detector had been doing this since the night `OVERNIGHT_ORDERFLOW_LONG/SHORT` shipped, caught only because the user directly recalled a specific rotation count ("I saw 5 by 9pm") that didn't match what the (still-buggy) code reported. **Rule: any function that reads hour/minute digits off a Date built via the Z-mislabeling convention must use `.getUTCHours()`/`.getUTCMinutes()`/`.getUTCDay()`, never the local equivalents — even though this process's ambient TZ is already America/New_York, which is exactly what makes the local-getter version look coincidentally plausible instead of throwing or producing an obviously-wrong value.** Before trusting ANY new function that extracts hour/minute/day-of-week from a naive-timestamp-derived Date object, check whether it was built via the Z-mislabeling convention (`new Date(str.replace(' ','T')+'Z')`) — if so, grep that function for `.getHours(`/`.getMinutes(`/`.getDay(`/`.getDate(` and flag every one as a same-shape bug candidate, not just the specific field involved in whatever symptom prompted the check. **Process lesson, equally important**: the first correction offered for this incident was ITSELF wrong, because it was computed by re-running the same suspect function (with a partial fix in place) rather than independently reproducing the raw bar data through a clean-room calculation first — a "fix" isn't verified by calling the fixed function again, only by an independent recomputation that doesn't share the code path under suspicion. <a id="cv-097"></a>

- **Caching an async lookup keyed by date/pivot under `Promise.all` concurrency must cache the in-flight PROMISE, not the awaited value — a naive `if (!cache.has(k)) cache.set(k, await fetch())` has a real race.** When many candidates on the same key (e.g. 25 stacked pivots sharing a date) are processed via `Promise.all`, they all call the cache-check before any of them finishes awaiting and writing back — so they all miss and all fire the same expensive query anyway, silently defeating the whole point of caching. Found 2026-09-09 (`server/services/pivotConfluenceAnalysis.js`'s `getCachedBaseline`/`getCachedATR`/`getCachedLevels`): this made a 25-deep pivot stack spanning 2 distinct dates take ~7s instead of the expected ~1s, caught only by timing it, not by reading the code. Fix: `if (!cache.has(k)) cache.set(k, fetchFn(...))` — no `await` before the `.set()` call — so every concurrent caller for the same key awaits the SAME promise. Same request-coalescing idea as `setupDetectionInFlight`/`confluenceTodayInFlight`, applied per-key instead of globally. Any new per-key async cache introduced under concurrent processing needs this pattern from the start, not discovered by a slow benchmark later.


<a id="cv-098"></a>

- **A "zone," "streak," or any other stateful tracker that's supposed to persist across time must be walked over ONE continuous bar sequence — never rebuilt inside a per-calendar-day (or per-`trade_date`) outer loop.** A per-day loop that reinitializes its own state each iteration (`for (const day of days) { const zones = []; ... }`) silently caps how far back any accumulated history (a touch count, a denial streak, "has this broken yet") can reach — at most one day's worth, no matter how long the real underlying event actually lasted. Found 2026-09-09 (`scratch/denial_streak_breakout_backtest.mjs`, a same-day research script): a real, verified ~32-hour, 30-touch overnight battle at one price zone (2026-09-07 evening through 2026-09-09 02:30am) got silently split across the `trade_date` boundary into two separate zones, each restarting its own touch/streak count at zero — confirmed because the max streak observed anywhere in the entire 1-year backtest was 13, roughly half the real example, and could never be more since no zone's window ever spanned more than ~24h. This is the same root shape as the older `allRthBarsRow.rows`-freezes-at-4pm footgun above, one level more general: any concept meant to span days needs its own continuous, persistent state, refreshed (not reset) as new daily inputs (e.g. a fresh `level_prices` cluster) arrive, with a reset happening only on a real domain event (the zone actually breaking) or genuine staleness (untouched for a long, explicit window) — never on a calendar/loop boundary that has nothing to do with the concept itself.
