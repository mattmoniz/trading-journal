Context: `docs/G0_GAP_AUDIT_20261101.md` (corrected 2026-11-02), `docs/AGENTIC_SYSTEM_SCOPE_20261101.md` section 9. These touch live order code, so per CLAUDE.md the order is: design, independent critique, implementation, independent code review, then a restart (a restart disarms the Sierra switch; sim profiles auto-rearm, `DTC_AUTO_REARM_SAFE` kept by the user 2026-11-01). ## 1. Entry freshness gate (G0 item 2, narrowed after reading the code)
Fact: the shared price helper `getLatestBars()` / `getCurrentPrice()` (`server/services/priceRetrieval.js`) already returns nothing when the freshest NQ bar in `price_bars_primary` is older than `FRESHNESS_MINUTES = 15` (a static plumbing parameter, documented as slack over the ~60 s ingestion poll), so every DETECTION call site fails safe on a stale feed. The live-flags banner (`server/routes/setups.js`) uses its own `PRICE_BARS_STALE_MINUTES = 10`. The gap: `sweepEntries()` (`server/services/sierraChart/orderSweep.js`, called at the start and end of each detection pass) places an ENTRY order for an ALREADY-EXISTING `active_setups` row without checking feed freshness (MARKET entries in `MARKET_ENTRY_PREFIXES` are the sharpest case: the order is sent at market on information that may be minutes old). The only existing fail-closed staleness check is in the escalate-unfilled-entry-to-market path (`orderSweep.js` about line 347).
Proposal: once per sweep, before any entry is placed, read the age of the latest NQ bar (one cheap query, cached for the sweep). If the feed is stale, or the query fails (fail closed), skip every entry candidate this sweep through the existing `recordEntrySkip(row, reason)` with a readable reason such as `price feed stale: latest NQ bar N min old` (so it lands in `gated_candidates` and the per-row `broker_note`, the same visible-reason convention as the other gates), and never touch exits, stops or reconciliation (exits must never be blocked by a data problem). A resting LIMIT already working is not canceled by this gate; only NEW placement is gated. Closure windows (`isGlobexWeekClosed`, the 17:00-18:00 maintenance gap) need no special case because nothing is eligible then anyway.
Open design questions: (a) the threshold. Options: the existing 15 minutes (consistent with the helper), the banner's 10, or derived from the data (for example a multiple of the recent median inter-bar gap, with a floor) to follow the repo's no-static-threshold rule; thin overnight Globex can have legitimately sparse 1-minute bars, so a tight rule risks blocking real entries. (b) whether MARKET entries need a tighter bound than resting LIMIT entries. (c) where the check sits in the chain relative to `isOrderEligible`, the daily-loss gate and `checkEntryGates` (order matters for which reason is recorded; repo history shows a later override silently winning). (d) alert path: reuse `priceBarsStale` plus a nightly count of FEED_STALE skips in `live_attestations`.
Verification plan: a unit test with injected bar ages (fresh, stale, query error), a rolled-back real-schema dry run of the skip insert, a check that exits are never gated, `test_invariants.mjs` unchanged, then a live restart and a read of the skip rows.

## 2. Boot self-test of the kill switch and daily-loss gate (G0 item 5)
Fact: `killSwitch.forceHaltOnBoot()` runs unconditionally at startup (`connectionManager.js`), the daily-loss gate has unit tests (`scripts/test_dll_gate.mjs`), sim profiles auto-rearm after a clean reconciliation. Gap: nothing asserts after EVERY restart that the system really came up disarmed and refusing.
Proposal: after boot (before any auto-rearm), run a side-effect-free self-test: (1) `killSwitch` state is disarmed with a halted reason; (2) `isOrderEligible()` for a synthetic setup returns not eligible with a reason; (3) the daily-loss gate returns blocked with a visible reason for a synthetic account with unknown P&L, and for an unset limit; (4) `sweepRealOrders()` with a MOCK dtc client submits zero orders while disarmed. Record the result in `live_attestations` (check name `boot_selftest`, trade date today) and, on failure, alert and SUPPRESS the auto-rearm for that boot (a failed self-test must not be undone by the auto-rearm path). Open questions: where exactly to hook (before or after the DTC logon), how to avoid any real order path being exercised, whether the self-test itself can deadlock a boot, and what else is worth asserting.

## 3. Failure rehearsal (G0 item 10)
A scripted, repeatable rehearsal run against the SIMULATED account and offline mocks, never a real-money profile: restart mid-position, DTC disconnect mid-order, a stale price feed with a resting entry, an exit rejected then retried against a different position, sleep/wake (process alive, DTC dropped), a duplicate server process, a tick file missing at the session start. For each: expected state, what must be visible (banner, `gated_candidates`, `live_attestations`), and the pass/fail check. Open questions: which scenarios can be automated safely, which need a manual step on the sim, and a sensible order.
