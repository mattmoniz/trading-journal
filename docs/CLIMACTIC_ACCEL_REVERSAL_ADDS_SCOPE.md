# Climactic Acceleration Reversal — "Adds" (Scaling In) Extension Scope

**Status: MOOT, do not pursue.** The base single-shot idea this extension would have scaled into was RESOLVED NEGATIVE the same day (see `docs/CLIMACTIC_ACCELERATION_REVERSAL_SPEC.md`'s "RESOLVED NEGATIVE, 2026-09-10" section) — the chosen cell's day-blocked bootstrap CI includes zero and its EV is 107.1% concentrated in 5 trades out of 132. There is no validated base strategy left to pyramid into. This document is kept only as a record of the design thinking (particularly the Phase 0 tautology correction below, which is a reusable lesson) — do not build any of it.

Original framing, kept for context: parked here 2026-09-10 after the base single-shot idea (`docs/CLIMACTIC_ACCELERATION_REVERSAL_SPEC.md`) appeared to clear Phase 2 (35/35 real-vs-placebo cells positive, N=132, best practical cell target=1.0x ATR/hold=240min, EV=$26.40, $6.60/hr of exposure) — that appearance did not survive the later robustness check.

## Motivation
The base strategy takes one fixed-size entry at the exact bar a climactic move crosses its p90 threshold, with a fixed target (0.5x-2.5x ATR) and fixed hold. That's a small, deliberate bite out of moves that (per the missed-move research this whole thread grew from) average 300-400+ points — the base strategy is not designed to capture the full move, only a validated fraction of it. The question raised: if the underlying climactic move keeps extending before the eventual reversal, could **adding to the position at each further extension** (a better fade price each time, if the reversal does eventually happen) capture meaningfully more of the total move?

## The real risk this scope exists to respect
**The single-shot version already gets stopped out 67-89% of the time**, rising toward the higher end at longer holds. That means most individual entries are wrong about timing, at least once, before the eventual outcome resolves. Blindly adding size every time the move extends further, without careful stop management, is functionally "averaging into a losing position" on the majority of individual attempts — exactly the shape of mistake this codebase's own risk-management priorities exist to catch. **Do not build this assuming it obviously helps.** It could easily make the strategy worse (bigger realized losses on the majority of cases where the reversal hasn't happened yet) rather than better.

## Phase 0 — cheapest possible screen, do this FIRST, before any engineering

**CORRECTED 2026-09-10 (DeepSeek design review, caught before this was ever built)**: the metric originally specified here was itself flawed in the same shape as this whole thread's own "ZigZag leg vs its own adjacent leg" tautology (see `CLAUDE.md`'s Convention entry). The original plan — group signals by "underlying move," compare 1st-signal-only forward return vs. 2nd/3rd-signal-in-sequence forward return — **conditions on the move having continued to re-trigger**, which selects for exactly the subset that eventually reverses while saying nothing about the majority that don't. As DeepSeek put it: "later-in-the-same-adverse-excursion signals necessarily get a better fade price *on the subset that eventually reverses* while telling you nothing about the majority that don't... as written, Phase 0 would pass regardless [of whether adds are worthless]."

**The corrected Phase 0 metric**: measure **aggregate P&L across every sequence, including every one that never reverses** — first-lot-alone vs. first-lot-plus-add(s), summed over the FULL population of climactic-acceleration events (not just the subset that happened to re-trigger a second time). A sequence that gets a second signal but then just keeps extending against both lots until both stop out must be counted at its real, full loss — not excluded from the comparison. Only if the AGGREGATE (all-sequences-included) P&L of the adds version beats the first-lot-alone version does the premise survive. This was actually already present as scope item 5 below, buried after the build-design questions — it should be run FIRST, before any of the design questions in the next section, since it's the one check that can kill the whole idea outright.

## If Phase 0 survives — open design questions to resolve in order
1. **What exactly counts as "the same underlying move" for grouping re-triggers?** Needs a real definition (e.g., same direction, no intervening signal in the opposite direction, underlying continuous acceleration condition never fully resets) — this is a genuine design decision, not a technicality, and should be tested for sensitivity like every other threshold this session.
2. **Stop management across adds — unified vs. independent.** Two real options to test separately, not assume:
   - **Independent per-lot stops** (each add gets its own structural stop at its own trailing-window extreme): simpler, but likely means earlier lots keep getting stopped while later lots are still open — need to check whether this nets out positive or just compounds losses.
   - **Single unified stop across the whole position** (one stop, re-set to the LATEST trailing window's extreme each time a new lot is added): more like real discretionary pyramiding, but changes the risk profile substantially — a single stop breach could realize a loss on ALL lots at once, and needs its own placebo-tested simulation, not an assumption it's obviously safer.
3. **Position sizing per add.** Equal-weighted lots vs. decreasing size on each successive add (since risk plausibly compounds the further into an uncertain move you go) — both need testing, not a default assumption that pyramiding should scale up or down.
4. **Maximum add depth** (cap how many times the position can scale in) — needs a data-derived cap (e.g., from the real distribution of how many times a climactic condition re-triggers on the same move before either stopping out or reversing), not a guessed round number — same "no static thresholds" discipline as everything else built this session.
5. **Aggregate outcome measurement.** Once a real design is chosen, the comparison that actually matters is: does the AGGREGATE (all-lots-combined) EV and worst-case drawdown beat the single-shot version's EV, not just whether any individual add "worked." A multi-lot simulation needs its own MAE tracking across the combined position, not just the fixed per-trade point measured for the single-shot version.

## Testing discipline (same as every other idea this session)
Phase 0 (cheap, no trade machinery) → if it survives, Phase 1 equivalent (raw forward-return pre-test of the chosen aggregate design) → Phase 2 (real stop/target bar-by-bar simulation across all lots + 10-trial randomized-direction placebo, same as the base strategy's own Phase 2) → only then consider building anything live. Given the base strategy itself is still SHADOW-eligible-but-not-yet-wired (Phase 2 done, not yet through the new-setup-type checklist), this extension is a further-out, lower-priority thread — the base single-shot version should be wired and validated with real N first before adding this real complexity on top of it.
