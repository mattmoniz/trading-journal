## The idea, as given (verbatim from the user, source: a found-online-style writeup, not user-original)

Feed a rolling-regression / volume-dynamics feature vector into a classifier (KNN or XGBoost) to detect intraday pivot points in real time, instead of relying on lagging moving averages.

**1. Geometric slopes (speed/acceleration of price, not raw price):**
- Rolling OLS linear regression on closing price over short windows (3, 5, 10 bars) on 1-min or 5-min bars → slope `m` from `y = mx + b`.
- Pivot signature: slope rapidly approaches zero from a high absolute value, then sharply reverses sign.
- Velocity = slope(t) − slope(t−1). Acceleration = velocity(t) − velocity(t−1). Claim: acceleration spikes just before a real pivot as buying/selling pressure exhausts.

**2. Volume signatures:**
- RVOL: current bar volume ÷ rolling median volume for that exact time-of-day over the past 20 trading days (normalizes for the intraday U-shape). Claim: RVOL > 3.0 combined with a narrowing price spread = climax/absorption, a candidate pivot.
- Volume delta (aggressive buys − aggressive sells) accumulated over a rolling 3-bar window, if tick/order-flow data is available. Claim: price makes a new high but rolling delta drops = divergence, signals an unsupported move / imminent top.

**3. Proposed feature vector per bar**: `[3-bar slope, 5-bar slope, slope acceleration, current RVOL, 3-bar volume delta]`, fed to KNN (nearest-neighbor in feature space) or XGBoost (threshold splits) trained to output pivot / no-pivot.

Any rebuild of the delta-divergence piece needs to explain why it would come out differently this time, not just re-run the same shape of test.
- **Pre-entry inflection/exhaustion detection was explicitly tabled** (`OPEN_DECISION table_preentry_inflection_detection_pending_orderflow_data`, LOW) after a Gemini/Claude debate concluded this system's current 1-minute-aggregated data structurally cannot resolve true order-flow absorption/exhaustion — every reasonable formulation tried (this includes an RVOL/climax-shaped test) came back negative, and the conclusion was "real data-resolution ceiling, not a string of bad ideas." **This new idea should be read as a candidate for un-tabling that decision, not as untested territory** — it needs to either bring something genuinely new past that ceiling (finer time resolution, real order-book depth) or have a good answer for why the rolling-slope framing escapes the same ceiling the RVOL/delta framing didn't.

## DeepSeek critique (2026-08-03) — read this before building anything

Full independent critique: `scratch/deepseek_response.md`. Verdict, summarized:

1. **This is still mean-reversion, not a genuinely different strategy family.** DeepSeek's own words: "detecting 'where a price move ends and reverses' is the *definition* of a fade entry, just one step upstream of the touch." If what the user actually wants is a trend-continuation/breakout entry, this idea doesn't deliver that regardless of how well it works — set it aside entirely in that case. If what's actually wanted is "a better reversal detector" (still valuable, just not literally "non mean reversion"), proceed, but drop that framing. **Needs a direct answer from the user before building**, not assumed either way.
2. **Do NOT build the ML pipeline (KNN/XGBoost/Python/scikit-learn).** That's a full new technology stack this codebase has zero infrastructure for, and per the standing "no dead ends" rule, a classifier trained before the underlying signal is proven real is the canonical failure case. The core hypothesis is fully testable with existing tools (`simple-statistics`'s `linearRegression()`, `computeRigor`/`computeReplication`, the same pattern `pilot_volume_climax_absorption.mjs` already uses). Only invest in ML infra if a cheap rule-based test clears a real bar first.
3. **The two halves of the idea have different fates against this codebase's data**: the rolling-slope/acceleration half is genuinely novel and escapes the tabled `table_preentry_inflection_detection_pending_orderflow_data` data-resolution ceiling (it's a pure price-geometry signal, well-defined on 1-min closes). The volume-climax half does NOT escape that ceiling (a true single-bar climax/reversal is an intra-bar phenomenon 1-min bars can't resolve) — it's likely to reproduce `pilot_volume_climax_absorption.mjs`'s existing pooled-negative result. **Test slope-deceleration alone as its own arm** — if it's null and only volume produces separation, that's not a new finding.
4. **Don't build a new 20-day-median RVOL pipeline.** It's substantially the same measurement as the existing `getVolumeBaseline()`/volZ pipeline already live in `STACK_VOL_BREAK_LIVE` (z-score vs. ratio-to-median are monotonic transforms of the same underlying signal). Reuse the existing one; a 3.0x-median cutoff roughly corresponds to 2.5-3 sigma, so just sweep volZ at higher cutoffs (1.5/2.0/2.5) if screening for more extreme volume events is the actual point.
5. **The concrete first test, ready to build**: `scripts/backtest_slope_pivot.mjs` — population is every 1-min bar in the ~410-day history (not filtered to level touches), computes 3/5/10-bar OLS slope + velocity + acceleration, flags a "pivot candidate" when slope crosses below its own trailing 100-bar 1-sigma band AND acceleration spikes AND (existing) volZ clears a swept cutoff. Ground truth is a **forward-return definition** (NOT the already-failed fractal-pivot definition from `structural_breakout_phase0_retest_test`) — max favorable excursion over the next N bars, checked for retracement. **5 arms**: baseline (random bars), slope-only, volume-only, combined, and a placebo (same thresholds applied 10 bars early, to catch a general-regime-property false positive rather than real pivot timing). Kill criterion: combined arm must beat all 4 other arms conjunctively, pass `computeRigor`+`computeReplication`, and survive a window/threshold sweep — matching the exact discipline that killed `structural_breakout_phase0_retest_test` at 0/8. **If it fails, close the thread — do not escalate to "maybe ML finds what rules can't."** A classifier can't find signal in a feature space that has none.
