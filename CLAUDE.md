# CLAUDE.md

Trading journal: React frontend (Vite, port 3000) + Express backend (port 3002) + PostgreSQL (`trading_journal` db). See [ARCHITECTURE.md](ARCHITECTURE.md) for full route/service/table inventory — this file is conventions and rules, not structure.

**Start of session / after a context clear: read [docs/OPEN_THREADS.md](docs/OPEN_THREADS.md) first.** It tracks unfinished work, unconfirmed proposals, and stale-stats findings from prior sessions — the goal is to never lose a thread to a context reset.

## Dev workflow

- Start: `./start.sh` (kills stale processes, starts server + client, self-heals the `pre-commit` hook symlink) — Stop: `./stop.sh` or `fuser -k 3002/tcp` — Restart: `./restart.sh` (thin wrapper around `start.sh`, not a separate implementation)
- **Single-instance server takeover lives in ONE place: `scripts/lib/server-lifecycle.sh`** (`cleanup_ports`/`stop_systemd_server`/`handback_on_exit`/`start_health_monitor`), sourced by `start.sh`, `restart.sh`, `stop.sh`, and `scripts/dev-server-guard.sh` (what `npm run server` now actually runs). Found 2026-08-18: `restart.sh` had silently duplicated `start.sh`'s cleanup logic by hand and drifted out of sync (missing the systemd-stop-first step and the EXIT-trap handback), and bare `npm run server` had none of this at all — together these let 5 simultaneous `nodemon` supervisors pile up from separate sessions across one day, fighting over port 3002 and each other until `trading-journal-server.service` tripped its failure-burst limit and went permanently `failed` mid-RTH, with zero live setups firing `ACTIVE` all day as a result. **Never reimplement any piece of this by hand in a new entry point — source the shared lib.** `.claude/hooks/session-start.sh` also has a standing backstop that loudly flags >1 simultaneous `nodemon server/index.js` supervisor if something still bypasses all of the above.
- `git commit` runs a **pre-commit hook** (`scripts/git-hooks/pre-commit`, symlinked from `.git/hooks/pre-commit` — `.git/hooks/` isn't tracked, `./start.sh` re-creates the symlink if missing) that blocks new hardcoded trading-threshold anti-patterns in `acd.js`/`caseEngine.js`, plus 3 more broadly-scoped patterns across `server/`/`src/`/`scripts/` (wrong $/pt constants, `SUM(pnl)`-style CumPL-diff violations, the JS-`toISOString()`-for-a-trading-day-date bug) — 7 patterns total, defined once in `scripts/hardcoded-threshold-patterns.sh` and shared with the Stop hook's advisory version. Deliberate exception: `ALLOW_HARDCODED=1 git commit ...`.
- Server only: `npm run server` (now `scripts/dev-server-guard.sh` — stops systemd, kills any stale nodemon/node instance, hands the port back on exit; no longer a bare `nodemon` with no cleanup) — Client only: `npm run client`
- DB: `server/schema.sql` is a full `pg_dump --schema-only` snapshot (122 tables/views, regenerated 2026-06-30 after a dead-table cleanup) — there's still no tracked migration history, so it drifts again the moment a table is added/altered live without regenerating. See the regen command in [ARCHITECTURE.md](ARCHITECTURE.md#schema-source-of-truth). When in doubt, query `information_schema.tables`/`information_schema.columns` against the live DB rather than trusting the file is current.

## Hard rules

- **Anything that drives or anticipates a decision — a data point, a computed signal, a classifier, a backtest finding, not just a "script" — must be built so the system keeps learning from it and can revisit it. No dead ends.** Before considering anything of this kind done, check all four:
  1. **Persisted somewhere queryable** (`performance_audit` or a real table) — not a script-local variable, a one-off `scratch/*.json` file, or a hardcoded literal in the serving code.
  2. **Has a recheck/recalibration path** — a scheduled script (`run_weekly_backtests.sh`), a `RESEARCH_CLAIM` 30-day cycle, or at minimum a documented manual recheck trigger. Not compute-once-and-forget.
  3. **Actually wired to a consumer, or explicitly flagged if not** via a `flag_decision.mjs` `OPEN_DECISION` — a signal nobody reads is a dead end whether or not it's persisted.
  4. **Discoverable** — an entry in `ARCHITECTURE.md`'s inventory or this file's "Where to look" section, not an orphan only findable by grepping and hoping.
  This is the reason `RESEARCH_CLAIM`, `OPEN_DECISION`, "export the real function," and the no-static-thresholds rule below already exist — treat it as the reason those mechanisms exist, not a fifth one to build. See [docs/HARD_RULES_DETAIL.md#no-dead-ends-the-four-part-checklist](docs/HARD_RULES_DETAIL.md#no-dead-ends-the-four-part-checklist) for the incident that prompted this and the recurring hand-typed-stat failure case.
- **Any new setup, signal, or calibration finding must be evaluated for BOTH the RTH window (9:30am-4pm ET) and the Globex/overnight window (6PM-8:30AM ET) before being considered complete — never default to RTH-only and call it done.** A tested-and-recorded "doesn't apply overnight" is fine; an untested gap is not. The RTH level-fade engine (`acd.js` ~3830-4430) and `detectGlobexSetup()` are structurally different — if their live-wiring mechanisms differ (e.g. only one has a `sizeMultiplier` stack), wire into whichever supports it and flag (`OPEN_DECISION`) whichever doesn't, rather than silently leaving a finding RTH-only. See [docs/HARD_RULES_DETAIL.md#rth-globex-both-required](docs/HARD_RULES_DETAIL.md#rth-globex-both-required).
- **No static thresholds.** Every threshold in this codebase must be derived from a rolling distribution (σ from a rolling mean/std), never a hardcoded number. This applies to entries, stops, targets, signal triggers — everything. If you're about to write a literal number as a cutoff, stop and compute it from historical data instead.
- **P&L must use the CumPL diff method**, not `SUM(pnl)` or `SUM(FlatToFlat)` — both overcount. See the SQL pattern in [ARCHITECTURE.md](ARCHITECTURE.md#pnl-calculation-cumpl-diff--critical-dont-regress-this). `/api/daily-logs` and `/api/stats/daily` both implement this — keep them in sync if you touch either. **A raw, account-type-unscoped CumPL-diff is a DIFFERENT and WORSE bug than the `SUM(pnl)` it replaces — always scope to `custom_fields->>'account' LIKE '%-PRO%'`**, matching `stats.js`'s `/stats/capture-ratio`. When there's no PRO-account CumPL data for a given day, fall back to raw `SUM(pnl)` for that day only — imprecise but not corrupted. See [docs/HARD_RULES_DETAIL.md#cumpl-diff-pl-method](docs/HARD_RULES_DETAIL.md#cumpl-diff-pl-method) for the practice-account balance-reset incident this guards against.
- **This journal trades MNQ (Micro E-mini Nasdaq): $2/point, $2 round-trip commission ($1 per side).** Ground truth lives in `server/config/instruments.js`'s `LIVE_INSTRUMENT.commissionPerRoundTrip` (imported by `server/routes/acd.js` and `scripts/update_optimal_stops.mjs`), mirrored in `src/constants/contract.js` for the frontend. **Never copy a `$/pt` or commission constant from another script without checking it matches this** — and don't trust an in-code "verified" comment either, see the standing rule on that below; check it against `acd.js`'s live values first. See [docs/HARD_RULES_DETAIL.md#mnq-commission-constant](docs/HARD_RULES_DETAIL.md#mnq-commission-constant) for the 2026-08-11 commission correction and a prior $/pt-copy incident.
- **~80% of `active_setups` is synthetic backfill data, not live-fired trades — check `origin_status` before treating any figure derived from this table as realized/historical performance.** `active_setups.origin_status` (immutable at insert) distinguishes `ACTIVE` (real, live-visible) / `SHADOW` (suppressed, background-only) / `BACKFILL` (synthetic) / `UNKNOWN` (pre-2026-07-09, unrecoverable). **A `SUM(actual_pnl)` or backtest built from `active_setups` without filtering by `origin_status` is a strategy simulation, not an account record.** Before presenting any `active_setups`-derived dollar figure as "what happened," check what fraction of its population is `BACKFILL`. See [docs/HARD_RULES_DETAIL.md#activesetups-backfill-vs-originstatus](docs/HARD_RULES_DETAIL.md#activesetups-backfill-vs-originstatus).
- **Never fabricate a stat.** Any win-rate/hit-rate claim needs N≥20 in the sample before it's reported as decisive (see `engineReadHitRates.js` convention). Below that, say so explicitly rather than rounding to a confident-sounding number.
- **Never hand-type a WR%/N/$ literal into a live-rendered card, label, or description string.** This has recurred 7+ times, several silently drifting to *directionally wrong* (e.g. a hardcoded "88% WR" vs. a real 66% WR at negative EV). Either derive the text from a `row` field already fetched from `performance_audit` in the same function, or write a dedicated `scripts/backtest_<name>.mjs` that populates one — never hand-type the number, even as a placeholder "for now." **When touching ANY file that renders a WR%/N/$ figure for any reason, even in passing, check whether that figure is a live query result or a literal before moving on.** See [docs/HARD_RULES_DETAIL.md#never-hand-type-a-wrn-literal](docs/HARD_RULES_DETAIL.md#never-hand-type-a-wrn-literal) for all 7 instances.
- **No lookahead in backtests/replays.** Case engine, day-type reassessment, and all backtest scripts must only use information that would have been available at that point in time. This is a frequent source of subtle bugs — when writing a new backtest script, explicitly check that no future bar/level data leaks into a decision made earlier in the session.
- **Volume-profile computations (POC/VAH/VAL) must spread each bar's volume across its own high-low tick range, never bucket 100% of it at one price.** `server/services/developingValueService.js`'s `computeProfile(bars)` is the single correct reference implementation (spreads volume evenly across each bar's H-L range, then extends VAH/VAL alternately toward whichever side has more volume next until 70% total is enclosed) — for any period-range VA (week/month/quarter/2-day), call its exported `computeVolumeProfileForRange(queryFn, { startDate, endDate, ... })` wrapper rather than writing a new SQL aggregation. See [docs/HARD_RULES_DETAIL.md#volume-profile-spreading-pocvahval](docs/HARD_RULES_DETAIL.md#volume-profile-spreading-pocvahval) for the multi-location bucket-by-low bug this replaced.
- **Export the real function, never reimplement live-derived classification logic inline in a backtest script.** If a backtest/mining script needs a value that a live service already computes (a regime, a day-type, a level, any derived classifier — not a raw DB column), it must `import`/reuse that service's real exported function, or read a persisted canonical table populated by it, never re-code the math by hand. When adding a new derived/live classifier, export its core function(s) at creation time rather than waiting for a second script to need it and reimplement instead. See [docs/HARD_RULES_DETAIL.md#export-the-real-function-never-reimplement](docs/HARD_RULES_DETAIL.md#export-the-real-function-never-reimplement) for the two-independent-reimplementations-disagreeing incident.
- **Every tested research/exploratory claim — not just setup-calibration ones — gets recorded via `scripts/record_claim.mjs`, positive or negative.** `recordClaim({slug, claimText, sourceFile, sourceDate, sampleSize, winRate, evPerTrade, rigorStatus, status})` writes/updates a `signal_type='RESEARCH_CLAIM'` row in `performance_audit` with a 30-day `next_recheck_due`; `node scripts/record_claim.mjs --list` shows every claim and flags overdue ones. `status` is `CONFIRMED` (independently re-verified), `PROVISIONAL` (real but thin/unstable/unchecked-for-rigor), or `STALE` (needs a fresh recheck). This is separate from the setup-calibration tables (`SETUP_STATUS`/`OPTIMAL_STOP`/etc.), which have their own lifecycle. **Always import and call `recordClaim()` — never hand-write the INSERT**, even for a one-off script. See [docs/HARD_RULES_DETAIL.md#every-tested-claim-gets-recorded-via-recordclaimmjs](docs/HARD_RULES_DETAIL.md#every-tested-claim-gets-recorded-via-recordclaimmjs) for the hand-rolled-INSERT/same-day-recheck-due bug this caught.
- **A `next_recheck_due` on a `RESEARCH_CLAIM` row is a FLAG, not an auto-rerun** — if the finding is still open (not a settled/rejected/confirmed one-time study), wire its source script into `run_weekly_backtests.sh` or `run_daily_calibration.sh` too, or it never actually recomputes itself. Unlike `SETUP_STATUS` (a single generic `GROUP BY setup_type` scan that auto-covers every setup_type), each `RESEARCH_CLAIM` is backed by a bespoke script with no generic scanner — the promotion/wiring decision stays a human call, only the *recompute* becomes automatic once scheduled. `test_invariants.mjs` check `[10]` WARNs (aggregate count only) on unscheduled claims; per-claim detail is in `scratch/research_claim_unscheduled.txt` for triage. See [docs/HARD_RULES_DETAIL.md#researchclaim-recheck-flag-vs-recurring-cron](docs/HARD_RULES_DETAIL.md#researchclaim-recheck-flag-vs-recurring-cron).
- **Resolve every `isolation: worktree` Agent dispatch before the spawning session ends — never leave one for a future session to discover by accident.** The harness only auto-deletes an isolated worktree if the agent made *no* changes; if it made any, the path/branch are handed back and a human/session must explicitly commit+merge or deliberately discard (`git worktree remove` + delete the branch). `.claude/hooks/session-start.sh` flags any stray worktree at session start as a backstop, but the real fix is not leaving one dangling. See [docs/HARD_RULES_DETAIL.md#resolve-every-isolation-worktree-dispatch](docs/HARD_RULES_DETAIL.md#resolve-every-isolation-worktree-dispatch).
- **Do not guess on third-party tool behavior** (especially Sierra Chart specifics) — fetch documentation or ask before asserting how an external tool behaves.
- **Never write a file >400 lines in a single Write call.** Use Write for the first section, then `cat >>` via Bash to append the rest. This avoids the 32k output token limit that silently truncates large writes.
- **Use Gemini for mining/analysis, Claude for implementation.** When a task is combinatorial exploration or pattern-mining over `performance_audit`/trade data, dispatch it to Gemini via the `scratch/claude_request.md` protocol rather than grinding through it directly — Gemini has read-only DB access and doesn't burn Claude's context on large query output. Claude's job is building the systems and interpreting/applying what Gemini finds. Reserve direct work for small, deterministic, single-query aggregations, and for anything Gemini has already gotten wrong twice (see the 2-strikes rule below). Does not relax **Audit all Gemini output** below.
- **For higher-stakes work — anything that could end up gating/sizing a live trade, or any live-wiring change to production code — use a 3-phase Gemini workflow, not just mine-and-run.** (0) Before writing any code, send Gemini the intended approach/design (not code) and ask it to critique the plan itself. (1) Full AUTONOMOUS mine-and-run for the actual analysis. (2) A separate review-only pass on the resulting code (explicit "do not execute, do not edit" header) before trusting any number or shipping any live change. Use this specifically for anything touching risk management or live execution behavior, not just entry-signal research. See [docs/HARD_RULES_DETAIL.md#three-phase-gemini-workflow-for-higher-stakes-work](docs/HARD_RULES_DETAIL.md#three-phase-gemini-workflow-for-higher-stakes-work) for the incident that prompted adopting this.
- **"Claude looks to Gemini for critique and heavy lifting"** — the default mode for substantive research/analysis work generally, not just higher-stakes work. Gemini's job spans the full loop: (1) review the idea/design before code is written, (2) do the heavy-lifting mine-and-run analysis, (3) review code before it's implemented/shipped, including real implementation Claude is about to wire live. Claude's job is an explicit, stated review-and-approve gate on every piece of Gemini output — never a silent pass-through of a number, conclusion, or script — then synthesize/decide/report; this is not a request to consult the user before each dispatch. Reserve solo direct work for small single-query lookups or a direct factual question, not for anything that involves forming a conclusion from an analysis. See [docs/HARD_RULES_DETAIL.md#gemini-critique-and-heavy-lifting-broadened-default](docs/HARD_RULES_DETAIL.md#gemini-critique-and-heavy-lifting-broadened-default) for worked examples.
- **Gemini gets 2 correction attempts, then Claude takes over.** When Gemini's output is wrong (wrong numbers, wrong methodology, SQL error loops — not a partial/incomplete response), send a correction prompt and re-invoke. If the 2nd attempt is also wrong, stop correcting and do the task directly instead of retrying a 3rd time.
- **Audit all Gemini output before acting on it.** Gemini produces plausible-looking but sometimes wrong — occasionally fabricated — analysis. After reading `scratch/antigravity_response.md`, verify 3–5 key claims by re-querying the DB directly before promoting any finding to `performance_audit` or changing live parameters: (1) 100%/0% WR with N≥10 → check `COUNT(DISTINCT log_date)` for single-session clustering; (2) grid output → compare "current params" cell to existing `performance_audit` baseline; (3) N counts → verify with a direct `COUNT(*)`; (4) any TRADE recommendation → re-run the WR/EV query yourself. **Always read the actual script/query, never just the writeup, before trusting any "successfully executed" claim** — if a dispatch produces a script, re-run it locally before trusting its findings; never treat the response file's prose summary as the source of truth on its own. See [docs/HARD_RULES_DETAIL.md#audit-all-gemini-output-before-acting-on-it](docs/HARD_RULES_DETAIL.md#audit-all-gemini-output-before-acting-on-it) for the confirmed-fabrication incidents.
- **Every pending product/architecture decision — "wire this in or delete it," "merge this branch," "change this cadence" — gets recorded via `scripts/flag_decision.mjs`, not left as prose in `docs/OPEN_THREADS.md`.** `flagDecision({slug, decisionText, sourceFile, sourceDate})` writes a `signal_type='OPEN_DECISION'` row; `decisionText` must include real context — what's being decided, why it matters, what resolving it looks like. `node scripts/flag_decision.mjs --list` shows every pending decision; `--resolve <slug> '<resolution text>'` closes one out. Every pending decision prints unconditionally at the start of every session (`.claude/hooks/session-start.sh`'s `OPEN_DECISIONS` section) — nothing here depends on a future session remembering to re-read prose elsewhere. See [docs/HARD_RULES_DETAIL.md#every-pending-decision-gets-recorded-via-flagdecisionmjs](docs/HARD_RULES_DETAIL.md#every-pending-decision-gets-recorded-via-flagdecisionmjs).
- **A code comment claiming a number was "verified" or "cross-checked" is not itself verification** — this is a more dangerous risk than a one-off wrong Gemini response, because it sits trusted in committed production code instead of a scratch file someone might still double-check. Treat "verified" language in an existing comment as a claim to re-check when you're about to depend on the value it's attached to, not as a substitute for checking it yourself. See [docs/HARD_RULES_DETAIL.md#a-verified-code-comment-is-not-itself-verification](docs/HARD_RULES_DETAIL.md#a-verified-code-comment-is-not-itself-verification) for the `DEFAULT_DPP=5` incident (25 setup_types calibrated wrong before it was caught).
- **When a script both computes a derived value (a sweep, a classifier, an optimizer) and separately stores/prints a number labeled as describing it, that pairing needs a standing check** — a feature added on top of an existing field can silently break the field's own meaning without anyone touching the field's line. When you add a smarter computation on top of a value a field already claims to describe, either rewire that field in the same commit or explicitly rename/re-scope it — and if the value is trusted enough to sort/display/gate anything, add an invariant check that re-derives it via the real function, not a plausibility check a bug could trivially satisfy. See [docs/HARD_RULES_DETAIL.md#derived-value-field-drift-when-a-smarter-computation-is-added](docs/HARD_RULES_DETAIL.md#derived-value-field-drift-when-a-smarter-computation-is-added) for the `ev_per_trade` incident this names.
- **Auditing a backtest's simulation logic is not the same as auditing where its baseline comes from — a comparison is only as trustworthy as its least-audited side.** When building or auditing any script that claims "config X beats baseline Y," verify baseline Y was computed by the exact same method as X in the same pass — a stored/precomputed number read from elsewhere, even one that looks authoritative because it's "the live value," needs the same scrutiny as the thing being tested against it. See [docs/HARD_RULES_DETAIL.md#baseline-must-be-computed-the-same-way-as-the-candidate](docs/HARD_RULES_DETAIL.md#baseline-must-be-computed-the-same-way-as-the-candidate) for the incident this reversed a finding on.
- **A backtest comparing two conditions against a shared, unchanging exit needs to rule out a structural/algebraic advantage before crediting the "smarter" condition with the win.** When a new backtest's two arms differ in WHEN they enter but share the same exit levels, add an entry-price-only control arm (no "smart" filter, just the later/different entry) before trusting that a filter/pattern/signal explains an EV gap — the gap may be entirely explained by the entry price itself. See [docs/HARD_RULES_DETAIL.md#structural-advantage-control-in-comparison-backtests](docs/HARD_RULES_DETAIL.md#structural-advantage-control-in-comparison-backtests) for the overshoot-entry incident (~$77/trade of an apparent edge was actually ~$6).
- **When a backtest script's overfitting guardrails get tightened and re-run, anything that no longer survives needs its OLD `performance_audit` row explicitly deleted, not just left unrefreshed by the new run.** When re-running a script with stricter/different guardrails, explicitly query which prior rows for that `signal_type` are NOT in this run's fresh output and delete them (or diff on a marker field the new version writes that the old one didn't) — don't assume `ON CONFLICT DO UPDATE` alone keeps the table consistent, since it only touches rows the new run actually produces. See [docs/HARD_RULES_DETAIL.md#delete-stale-rows-when-guardrails-tighten](docs/HARD_RULES_DETAIL.md#delete-stale-rows-when-guardrails-tighten).
- **A backtest candidate grid needs a floor derived from the underlying DATA'S OWN RESOLUTION, not just statistical overfitting guardrails** (thin-tail/plateau/OOS/rigor) — those catch overfitting to a few trades, not overfitting to a precision the data cannot actually resolve. Before trusting ANY backtest whose candidates are themselves a distance/time/price granularity (a trail width, a tick-level threshold, a sub-bar timing window), check that granularity against the data's own real resolution — a candidate finer than what the underlying data can distinguish will pass statistical guardrails by construction, since the "noise" it's exploiting is measurement noise, not market behavior. See [docs/HARD_RULES_DETAIL.md#backtest-candidate-grid-floor-from-data-resolution](docs/HARD_RULES_DETAIL.md#backtest-candidate-grid-floor-from-data-resolution) for the sub-bar-noise trailing-stop incident.
- **Check for frontend render errors before calling any frontend change done.** Run `npm run lint:frontend` (ESLint `no-undef`, catches missing-import/undefined-variable `ReferenceError`s) and `npm run build` (catches broken import/export paths and esbuild-level errors lint won't). Also check `scratch/gemini_alerts.txt` / `scratch/server_errors.jsonl` for `[CLIENT_ERROR]` entries. If real browser/Playwright tooling isn't available, say so explicitly rather than claiming an interactive check was done — static checks confirm nothing throws on load, not that a specific interaction behaves correctly. `.claude/hooks/post-edit-lint.sh` runs single-file lint on every touched file as a fast real-time layer underneath this — it does NOT replace the full `npm run build` + browser-check gate (single-file lint can't see cross-file import/export breaks or interaction bugs). See [docs/HARD_RULES_DETAIL.md#check-for-frontend-render-errors-before-calling-a-change-done](docs/HARD_RULES_DETAIL.md#check-for-frontend-render-errors-before-calling-a-change-done).
- **Whenever a change touches data-fetching — a new component with its own `fetch`/poll, a new or modified API endpoint, or edits to an existing one on a hot path — verify actual loading performance before calling it done, not just that it renders without errors.** "No console errors" and "actually fast" are different claims this codebase has repeatedly conflated. Using Playwright:
  1. **Count and list actual network requests** (`page.on('request', ...)`, filter to `/api/`) — group by endpoint and flag anything firing more than once per load. `grep` the exact URL string across `src/` before adding a new fetch of something that sounds "already available elsewhere."
  2. **Time the actual settle point**, not just first paint — watch the page's loading indicator until it hits zero, not just `domcontentloaded`.
  3. **For any new/modified endpoint, `curl` it standalone** (`-w "%{time_total}s size=%{size_download}\n"`) and compare against its cost *inside a real concurrent page load* — a large gap means connection contention or a pile-up, not a slow query.
  4. **If a response is unexpectedly large, check the query is actually bounded** — this codebase has repeatedly found genuinely unbounded historical queries hiding behind code that looked bounded at a glance.
  Don't run this full checklist for every one-line change, but any change adding a fetch, a component on Morning Prep/Trades, or touching a known-hot endpoint gets it. See [docs/HARD_RULES_DETAIL.md#verify-data-fetching-performance-not-just-no-errors](docs/HARD_RULES_DETAIL.md#verify-data-fetching-performance-not-just-no-errors) for the concrete incidents (51MB unbounded response, N+1 firing 18x, a 16x request multiplication) this checklist was built from.
- **Before proposing or building anything new, `grep ARCHITECTURE.md` for the relevant capability first** — the doc is more complete than it gets credit for, and re-deriving via `grep`/exploration when the answer is already written down wastes real time. When a task starts with "can we build X" or "is Y already tracked somewhere," `grep -i` the relevant keyword against `ARCHITECTURE.md` before writing a single line of new code or running an exploratory grep across `server/`/`scripts/`/`src/`. See [docs/HARD_RULES_DETAIL.md#check-architecturemd-before-building-or-exploring](docs/HARD_RULES_DETAIL.md#check-architecturemd-before-building-or-exploring).
- **Verifying a statistical split is real is not the same as verifying the classifier that produced the split is valid.** A backtest that conditions setup EV on a newly-invented regime/classification (not an existing, already-computed field) can pass every rigor check this codebase uses while the classifier itself is still an arbitrary construction — window lengths/cutoffs picked semi-informally, never sensitivity-tested, never checked for independent predictive power, never adjusted for the multiple-comparisons surface of testing several regime schemes against dozens of setup_types at once. A plausible economic narrative for why a split makes sense is not validation either. Before trusting a *newly-built* classifier's conditioning effects, validate the classifier's own parameter robustness and independent predictive power first. See [docs/HARD_RULES_DETAIL.md#validating-a-classifier-is-not-the-same-as-validating-its-split](docs/HARD_RULES_DETAIL.md#validating-a-classifier-is-not-the-same-as-validating-its-split) for the worked example where 3 EV splits passed rigor and all 3 classifiers behind them then failed independent validation.
- **A `PENDING` `OPEN_DECISION` describes the state of the codebase *as of whenever it was last checked*, not necessarily now — verify its underlying claim before relying on it if you're doing related work**, especially anything touching a file it names. The mechanism guarantees a decision won't be silently forgotten; it does not guarantee the decision's factual claim is still accurate, and nothing currently re-checks a claim automatically. Before citing a pending decision's claim as current fact, a cheap `grep`/direct check costs little and prevents compounding a stale finding into new work. See [docs/HARD_RULES_DETAIL.md#a-pending-opendecision-can-be-stale](docs/HARD_RULES_DETAIL.md#a-pending-opendecision-can-be-stale) for the incident where a decision described already-deleted code.
- **A prior "confirmed empirically" claim — including Claude's own, including from earlier in the same session — is not evidence once it has crossed a context-compaction boundary; the actual verification script/query is gone and only the conclusion survives.** A compaction summary preserves *what was concluded*, not *how it was checked*, and a wrong methodology survives the summary just as confidently-worded as a correct one. Before resolving an `OPEN_DECISION`, or otherwise treating any pre-compaction "confirmed via a standalone script" claim as load-bearing, redo the actual check against current live data rather than trusting the conclusion. See [docs/HARD_RULES_DETAIL.md#pre-compaction-claims-are-not-evidence](docs/HARD_RULES_DETAIL.md#pre-compaction-claims-are-not-evidence) for the incident this was named from (a "fix" committed against a false premise, later corrected).
- **A hypothesis about market behavior gets tested against raw bar/price history first; only route a hypothesis through `active_setups` trade-level N when the question is specifically about how this system's OWN setups perform.** If the question is "does market condition X predict market outcome Y" (a claim about NQ price behavior in general), build it as a bar-level scan over `price_bars_primary` first — cheap, dense, and not selection-biased by which setups fired. Only route through `active_setups`/real trade N once the question becomes "does this system's OWN setup capture that edge" (a claim about execution, not the market). Getting a real zero from a trade-level test doesn't mean the market phenomenon doesn't exist — it may just mean the question was asked through too thin a lens. See [docs/HARD_RULES_DETAIL.md#market-behavior-hypotheses-go-through-bar-history-first](docs/HARD_RULES_DETAIL.md#market-behavior-hypotheses-go-through-bar-history-first) for three threads that were structurally forced toward a false zero this way.

## Conventions

- **A `localStorage`-persisted drag-to-reorder column order must be MERGED against the current column set at load time, never just filtered against it.** The obvious-looking pattern (`(savedOrder || defaultKeys).map(k => COLS.find(c => c.key === k)).filter(Boolean)`) only ever drops a key that's no longer valid — it can never re-add a key that's new since the user's last drag. Reconcile any current-columns key absent from the saved order back in (appended at the end) in the `useState` initializer itself. See [docs/CONVENTIONS_DETAIL.md#localstorage-drag-reorder-must-be-merged-not-filtered](docs/CONVENTIONS_DETAIL.md#localstorage-drag-reorder-must-be-merged-not-filtered) for the incident (a brand-new column silently missing for any user with an already-saved order).
- **Any new script querying `price_bars_primary` with a lower-bound-only `ts >= X` filter must add an explicit upper bound.** `price_bars_primary` is a VIEW (join + `GROUP BY` aggregation, confirmed via `information_schema.tables.table_type='VIEW'`) — it can never have an index, so an unbounded query forces the aggregation across everything from `X` through the present before it can sort/`LIMIT`. See [docs/CONVENTIONS_DETAIL.md#pricebarsprimary-needs-an-explicit-upper-bound-too](docs/CONVENTIONS_DETAIL.md#pricebarsprimary-needs-an-explicit-upper-bound-too) for the 15-20x speedup this produced in one script and the broader materialize-historical-bars decision it points at.
- **Never look up a bar by an exact epoch/timestamp match against a real trade's `fired_at`** — real trades carry genuine sub-minute precision (recorded live via `NOW()`), but bars are always exactly on the minute, so an exact match silently fails and the trade gets dropped, not flagged. Floor the timestamp to the minute before the lookup. See [docs/CONVENTIONS_DETAIL.md#floor-timestamps-to-the-minute-before-matching-bars-to-firedat](docs/CONVENTIONS_DETAIL.md#floor-timestamps-to-the-minute-before-matching-bars-to-firedat) for the incident (31 real trades silently erased, producing a false "zero occurrences" finding).
- **A number that survives being computed twice by the same script is not verified — it only proves the script is consistent, bugs included.** Independent re-derivation (by hand with a different method, or dispatched to Gemini without showing it the original methodology) is what actually catches a deterministic bug a repeated run cannot. Audit a disagreement in both directions, don't assume whichever answer already existed is correct. See [docs/CONVENTIONS_DETAIL.md#a-number-computed-twice-by-the-same-script-isnt-verified](docs/CONVENTIONS_DETAIL.md#a-number-computed-twice-by-the-same-script-isnt-verified).
- **Confound checklist for any new comparison-style backtest (two arms compared against each other).** Before recording or promoting any "config/condition A beats B" finding, check all four:
  1. **Do the two compared arms differ ONLY in the hypothesis variable**, or does one arm have a structural/algebraic edge (a later entry against the same fixed exit, a smaller remaining risk distance)? Ask whether the "smarter" arm would still win with the intelligence stripped out and only the structural difference left.
  2. **Is the baseline computed by the exact same method/window as the thing being compared** — resimulated in the same pass, never read from a stored column computed under different historical conditions.
  3. **Does the signal select a sub-population** (overshot / made-a-new-extreme / pattern-present / any filter)? If so, is there a same-selection-minus-the-signal-condition control bucket — the `SIGNAL` / `SAME_SELECTION_NO_SIGNAL` / `NEVER_SELECTED` 3-way template in `scripts/pilot_cvd_divergence.mjs` is the pattern to reuse, not reinvent.
  4. **Was this the largest of K effects pulled from a sweep** (top-N setup_types, best candidate in a grid)? If so, run `computeReplication()` (`server/services/rigorDiagnostics.js`) — a held-out/permutation check that pools the selected subset against everything NOT selected and reports whether the direction and magnitude survive.
  Items 1-3 are domain-specific reasoning each time, not a generic detector (deliberately not built — would create false confidence); item 4 has a real, reusable function. See [docs/CONVENTIONS_DETAIL.md#confound-checklist-for-comparison-style-backtests](docs/CONVENTIONS_DETAIL.md#confound-checklist-for-comparison-style-backtests) for the 5+ times this exact failure shape recurred before the checklist was built.
- **A negative verdict on a runner/winner-extension-class finding must cite a specific TESTED mechanism failure with a number — "negative by analogy/inference to a different pipeline's result" is not a valid closure.** Run the adversarial stress-test battery (exclude dominant family → exclude top day → exclude cluster → verify P&L → check for bugs) by default before recording any POSITIVE runner finding too, not only when challenged after the fact. See [docs/CONVENTIONS_DETAIL.md#negative-trace-rule-for-runner-findings](docs/CONVENTIONS_DETAIL.md#negative-trace-rule-for-runner-findings) for the incident this closes.
- **Benchmarking bundle size across commits (git worktrees): never symlink `node_modules` between a worktree and the main repo** — Vite's dependency-optimizer cache (`node_modules/.vite`) is shared through the symlink and can silently contaminate build output from a different commit's module graph, even after deleting `node_modules/.vite` between runs. Give each worktree its own real `npm install`, and build each commit in its own fully separate Bash/tool call. See [docs/CONVENTIONS_DETAIL.md#benchmarking-bundle-size-across-worktrees](docs/CONVENTIONS_DETAIL.md#benchmarking-bundle-size-across-worktrees) for the self-audit this bit before catching it.
- Backtest scripts live in `scripts/`, named `backtest_<hypothesis>.js`, run manually via `node`, and typically write findings to the `performance_audit` table. They are not imported by the running app.
- **Frontend API calls fetch the backend directly (`:3002`), never the relative `/api` path.** `src/constants/api.js` exports the one `API_URL` constant every view/component imports — never redeclare `const API_URL = '/api'` locally. Routing API traffic through Vite's `/api` proxy puts it on the same origin as the app's own module-serving, and Chrome's per-origin connection cap can starve a newly-navigated-to view's module fetch behind background polling. See [docs/CONVENTIONS_DETAIL.md#frontend-api-calls-go-directly-to-3002-never-through-api-proxy](docs/CONVENTIONS_DETAIL.md#frontend-api-calls-go-directly-to-3002-never-through-api-proxy) for the root-cause investigation.
- **Day-stable backend queries (bounded strictly `< date`, or otherwise fixed for a whole trading day) should be cached on `server/lib/cache.js`'s `cacheGet`/`cacheSet`, not recomputed on every poll.** Already used by `acd.js`/`auctionRead.js`/`keyLevels.js`/`weekly.js`/`stats.js`/`morningBrief.js`/`sessionForecastService.js` — check this file before hand-rolling a new module-level cache object; `cacheSet` returns its `val`, so `return cacheSet(key, result, ttl)` works inline. Use a shorter TTL (minutes, not hours) for anything reading the *target date's own same-day* data. See [docs/CONVENTIONS_DETAIL.md#cache-day-stable-backend-queries](docs/CONVENTIONS_DETAIL.md#cache-day-stable-backend-queries) for the two-convention comparison this is based on.
- **`useSharedPollData` (`src/utils/useSharedPollData.js`) dedupes the recurring poll interval automatically, but NOT independently-added consumers of a new URL, and NOT (before 2026-07-15) the very first load.** Before wiring a new component to an existing polled endpoint, `grep` for the exact URL string first — this hook has already silently gained duplicate non-shared fetchers of the same endpoint multiple times. See [docs/CONVENTIONS_DETAIL.md#usesharedpolldata-dedup-gaps](docs/CONVENTIONS_DETAIL.md#usesharedpolldata-dedup-gaps) for the in-flight-guard fix (16 requests for one URL on a single page load, down to 1).
- **A genuinely expensive endpoint that's also polled frequently or fetched by several components on mount needs a request-coalescing lock, not just a data cache.** If a response takes longer than its own poll interval, or several components independently fetch it at once on page load, concurrent/overlapping requests pile up and compete for the same DB connections — a self-inflicted DoS against your own database. Pattern (see `acd.js`'s `setupDetectionInFlight` / `confluence.js`'s `confluenceTodayInFlight`): a module-level in-flight promise; the first caller runs the real handler, concurrent callers `await` the same promise. Don't add this reflexively — only where polling frequency or multi-component fan-out can realistically overlap with the endpoint's own response time. See [docs/CONVENTIONS_DETAIL.md#request-coalescing-lock-for-expensive-polled-endpoints](docs/CONVENTIONS_DETAIL.md#request-coalescing-lock-for-expensive-polled-endpoints) for the 13-24s+ measured pile-up this fixed.
- Sierra Chart TAL data is stored as JSONB under `custom_fields->'sierra_data'` rather than typed columns — this lets new TAL columns appear without a migration and lets old Activity Log format rows coexist.
- Account filter state is lifted to `App.jsx` and shared between Calendar and Dashboard — don't duplicate it locally in a component.
- **Views stay mounted across tab switches — never add a new top-level view back to the old conditional-unmount pattern.** `App.jsx` tracks a `visitedViews` Set and CSS-hides (`display:none`) inactive views instead of removing them from the tree. Consequence: any `setInterval`/polling effect in a view now keeps running while hidden unless it's gated — new polling code inside a view must read `useViewActive()` (`src/utils/useViewActive.js`) and add it to the effect's dependency array with an early `if (!isViewActive) return;`. Bounded, user-triggered job-status polls (e.g. `ACDBacktestRunner`) are the deliberate exception. See [docs/CONVENTIONS_DETAIL.md#views-stay-mounted-across-tab-switches](docs/CONVENTIONS_DETAIL.md#views-stay-mounted-across-tab-switches).
- **Don't keep adding to `App.jsx`.** When a change needs new UI, extract it into its own file (`src/components/dashboard/` or `src/views/`) instead of inlining it. If a constant or helper needs to be shared across view files, put it in `src/constants/` or `src/utils/` — don't leave it as an unexported local `const`/`function` in App.jsx; that exact mistake caused several `ReferenceError`s across a file boundary after the 2026-07-13 code-split. See [docs/CONVENTIONS_DETAIL.md#dont-keep-adding-to-appjsx](docs/CONVENTIONS_DETAIL.md#dont-keep-adding-to-appjsx).
- **Unnecessary monolith files get an automatic, non-blocking nudge — not a fixed line-count limit.** `.claude/hooks/post-edit-filesize.sh` compares a touched file's line count against its own cohort (sibling files in the same directory/extension) using median + MAD, firing only when the file is BOTH a statistical outlier for its cohort AND grew by at least a cohort-median's-worth of lines since the last commit. Advisory only — splitting isn't always right, cohesion sometimes matters more than line count. See [docs/CONVENTIONS_DETAIL.md#monolith-file-size-nudge-is-statistical-not-a-fixed-limit](docs/CONVENTIONS_DETAIL.md#monolith-file-size-nudge-is-statistical-not-a-fixed-limit).
- **No-new-entries dead zone (4:00-6:00 PM ET):** `runSetupDetection()` (`server/routes/acd.js`) forces any new RTH candidate that would otherwise fire `ACTIVE` in this window to `SHADOW` instead (`suppression_reason='POST_RTH_DEAD_ZONE'`). Does NOT force-close already-open positions — only NEW entries are blocked. Overlaps with, but is broader than, the pre-existing 5-6PM ET hard-close gap. See [docs/CONVENTIONS_DETAIL.md#no-new-entries-dead-zone-4-6pm-et](docs/CONVENTIONS_DETAIL.md#no-new-entries-dead-zone-4-6pm-et).
- **Server-autonomous detection:** `server/index.js` runs a `setInterval` every 15s calling `GET /api/acd/setup-detection`, across the full CME Globex week (Sun 6PM–Fri 5PM ET, with the daily 5–6PM ET maintenance gap excluded) — not just RTH. This is intentional — it makes level fade detection independent of browser clients. Do not remove it. The INSERT in `acd.js` is `ON CONFLICT DO NOTHING` so concurrent client polls don't double-write. **A hard rule describing this poller's schedule/endpoint is exactly the kind of fact that silently drifts when the poller itself changes** — if you touch its schedule or endpoint again, grep for "9:30" / "RTH" / "market hours" across `CLAUDE.md`, `src/components/dashboard/`, and `src/views/` in the same session, not just the code. See [docs/CONVENTIONS_DETAIL.md#server-autonomous-detection-schedule](docs/CONVENTIONS_DETAIL.md#server-autonomous-detection-schedule) for how stale this entry itself went undetected for 7 weeks.
- **Level fade detection gate:** `acd.js` line ~3838 checks `allRthBarsRow.rows.length >= 3` (not 60). IB-specific levels (`ibHighToday`/`ibLowToday`, `IB_MID_SCALP_FADE`, `OR_MID_AFTER_IB_FADE`) self-gate via `etMinNow >= 630` — do not restore the 60-bar gate.
- **sizeMultiplier is an IIFE** inside the `levelScalpSetup` object in `acd.js`. All sizing adjustments live there. When adding a new factor: (a) research backs it (N≥20), (b) add to the IIFE, (c) update `AlphaEngineOverview.jsx`, (d) document in OPEN_THREADS.
- **DAY_TYPE_MANAGED types need their bucket breakdown re-read, not just their headline recommendation.** A `DAY_TYPE_CONDITIONAL` type (currently `IB_BULLISH`/`IB_BEARISH`) staying off `SUPPRESS` can mean "genuinely strong on its good day-type" or "one thin/borderline bucket happens to clear the bar this week" — the recommendation string alone doesn't distinguish these. `.claude/hooks/session-start.sh`'s `DAY_TYPE_MANAGED WATCH` section prints every such type's full bucket breakdown at the start of every session — read it, don't skip past it as boilerplate. See [docs/CONVENTIONS_DETAIL.md#daytypemanaged-bucket-breakdown-re-read](docs/CONVENTIONS_DETAIL.md#daytypemanaged-bucket-breakdown-re-read) for the regression this caught.
- **`active.sizeMultiplier` overwrite footgun:** the level-fade IIFE sets a real, ~20-factor `sizeMultiplier` (0.10-1.5x) on `levelScalpSetup`. Later in the same handler, the "Build full trade brief" block sets `active.sizeMultiplier` again for a different reason (post-loss "Death Sequence" protection) — applied as an additional ceiling (`Math.min(existing, 0.5)`), never a replacement. **Any future code that sets a field a candidate object already sets in its own construction must merge/cap, never blindly overwrite** — check what the candidate already computed first. See [docs/CONVENTIONS_DETAIL.md#activesizemultiplier-overwrite-footgun](docs/CONVENTIONS_DETAIL.md#activesizemultiplier-overwrite-footgun) for the two-layer incident (an unconditional overwrite, then an unscoped `hasLossToday`) this was fixed in.
- **New setup type checklist (anti-hardcode gate) — also the checklist for auditing *existing* live setups, not just gating new ones.** Before any new `setup_type` goes live in `acd.js`, ALL of the following must be satisfied:
  1. Run `node scripts/backtest_setup_status.mjs` → generates/updates `SETUP_STATUS` row in `performance_audit`.
  2. Run `node scripts/update_optimal_stops.mjs` → generates/updates `OPTIMAL_STOP` row with data-derived stop/target.
  3. If N<20 resolved trades, do NOT fire live — insert as `status='SHADOW'` only until N≥20.
  4. Never write a stop, target, or WR claim as a literal number in `acd.js` — always read from `liveStats._opt[type]` or `performance_audit`.
  4a. **Run a signal-level forward-return pre-test before building any trade machinery** — the cheapest, most decisive screen in this checklist. No stop, no target, no exit rule: at each signal event, measure the raw forward price change at several bar horizons and compare the CONDITIONAL mean against the UNCONDITIONAL mean over the same horizon (never against zero — a multi-year NQ sample has real underlying drift). Enrich with volume/order-flow using `touchQuality.js`'s `getVolumeBaseline()` and `acd.js`'s `volZ`/`oneSidedRatio`, and derive any bucket cutoff from the pooled data (e.g. median volZ), not a threshold borrowed from a different purpose.
  5. **Simulate the real stop/target as an actual bar-by-bar trade before ever calling a signal "validated."** A statistically stable *sign* on a raw point value is necessary but not sufficient — it has no drawdown tolerance and is not a tradeable strategy.
  6. **Verify integration, don't assume it.** Check `dropToTimeline()` is called from the actual insert path, check `SETUP_DISPLAY_LABELS` has an entry, check `isLongSetup()`/`inferDirection()` resolve correctly for the exact string being inserted.
  7. **If the setup lives outside the level-fade candidates array (its own poller), it must replicate the dynamic SHADOW→ACTIVE promotion check manually** — the candidates-array path already does this via `liveStats._suppressedSetups`; a standalone poller has no such built-in mechanism and will sit in SHADOW forever without a `getLiveStatus()`-style live re-check.
  8. **If the calibration script writes a new `recommendation` value, register it in `/api/performance-audit/unified`'s status-mapping** or the setup type is silently invisible in the Unified Signal Table.
  9. **If a setup's fire gate is earlier than the data it depends on for suppression, its suppression logic is a silent no-op** — verify the fire-gate timing (`etMin >= ...`) against when the suppression dependency actually becomes available, not just that a suppression check exists in the code.
  10. **A backtest/backfill's detection population must match what the live poller actually fires on — window, touch-definition, and all.** A narrower/stricter historical scan describes a different, more selective strategy than what's actually live. Same-day-forming levels (Opening Range, Initial Balance) need their own formation gate or a re-test introduces lookahead.
  11. **A level with zero real touches ever is not automatically SHADOW-safe** — `backtest_setup_status.mjs` groups by `setup_type`, so a type with 0 rows never gets even a `THIN_N` row, and the live insert gate treats "absent from `_suppressedSetups`" as "not suppressed." Before considering a new level "covered," check `SELECT 1 FROM performance_audit WHERE signal_type='SETUP_STATUS' AND signal_name=<type>` — seed a manual `THIN_N` placeholder if absent.
  The `Stop` hook (`.claude/hooks/check-docs-drift.sh`) scans for hardcoded anti-patterns and will warn if any of these are violated. The `SessionStart` hook checks for setup_types missing a fresh SETUP_STATUS row. See [docs/CONVENTIONS_DETAIL.md#new-setup-type-checklist-anti-hardcode-gate](docs/CONVENTIONS_DETAIL.md#new-setup-type-checklist-anti-hardcode-gate) for the found-2026-07-14 incident behind every numbered item.
- **`active_setups`' `existingSetup` dedup check only prevents two *simultaneously open* rows — it does NOT stop the same exact touch instant from being inserted twice once the first one resolves.** Fixed with an unconditional second unique index `idx_as_unique_touch_instant` on `(trade_date, setup_type, fired_at)` (alongside the existing partial index on ACTIVE/SHADOW only), and **every `ON CONFLICT` clause against `active_setups` is now bare `ON CONFLICT DO NOTHING`** (no explicit target) so it catches a violation against *either* index — a targeted clause only suppresses a violation against the index it names. See [docs/CONVENTIONS_DETAIL.md#varchar-n-literal-overflow-risk](docs/CONVENTIONS_DETAIL.md#varchar-n-literal-overflow-risk) for two live-but-untriggered overflows this caught, plus a near-miss in `flag_decision.mjs`/`record_claim.mjs` now guarded with a fail-fast length check.

See [docs/CONVENTIONS_DETAIL.md#shadowsetuptypes-hardcoded-list-anti-pattern](docs/CONVENTIONS_DETAIL.md#shadowsetuptypes-hardcoded-list-anti-pattern) for both the original bug (3 real, promoted setups permanently hidden) and the fallback list's own quiet re-drift.
- **Trading-day dates: always derive from SQL `CURRENT_DATE`, never JS `new Date().toISOString()`.** The DB server runs in `America/New_York`; JS's `toISOString()` is UTC, and the two disagree once past 8PM ET — a full calendar day earlier in JS-UTC-land than the DB's own ET-based "today." Fetch it with `SELECT CURRENT_DATE::text as today` in every new backtest script. See [docs/CONVENTIONS_DETAIL.md#trading-day-dates-from-currentdate-never-toisostring](docs/CONVENTIONS_DETAIL.md#trading-day-dates-from-currentdate-never-toisostring) for the 3 same-day bugs this caused.
- **Never parse a naive (no-timezone) timestamp string with `new Date(str).toISOString()` — it silently depends on the ambient process/system timezone, not on any timezone you actually intend.** The pattern to reuse for any future naive-local-timestamp parsing: guess a UTC instant from the naive components, ask `Intl.DateTimeFormat` what that guess actually looks like in the target zone, then correct by the wall-clock difference — this correctly handles both EDT and EST per-date, unlike a hardcoded offset (`etNaiveStringToUtcIso()` in `sierraParser.js`). **Process lesson: don't trust "recent data looks right" as proof a timestamp pipeline is healthy** — verify via the raw source string against the stored column directly, not the rendered UI. See [docs/CONVENTIONS_DETAIL.md#naive-timestamp-parsing-depends-on-ambient-timezone](docs/CONVENTIONS_DETAIL.md#naive-timestamp-parsing-depends-on-ambient-timezone) for the multi-month timezone-flip incident and the two duplicate-import cleanups it led to.

These are informational — they do NOT feed SUPPRESS/PROMOTE logic, because "unstable" doesn't mean "losing." Classify each flag (degrading vs. improving vs. noisy-but-stable vs. too-thin-to-tell) before acting. Aggregate coverage: `GET /api/acd/rigor-stability-coverage` + `RigorStabilityPanel` in `AlphaEngineOverview.jsx`. **One deliberate, narrow exception**: `backtest_setup_status.mjs`'s per-day-of-week sub-pass (`SETUP_STATUS_DOW`) DOES gate live SUPPRESS/ACTIVE directly on `computeRigor`'s `clean` bit — a false SUPPRESS there directly blocks real trading opportunities, a materially different cost than the other pipelines' informational badge. - **`antigravityEdges.js` Promise.all ordering footgun:** `getLiveEdgesContext()` fires all DB queries in a single `Promise.all` wave (20 entries). The destructured variable names are **positionally bound** — adding or removing a query shifts every entry below it to a wrong variable with no runtime error. Always update the destructuring list and the array body together, and check the index comments (0–19) when inserting. Cache-miss-only entries (indices 0–3) use `isCached ? Promise.resolve(null) : query(...)` — do not move them to a later position without updating the cache skip logic.
- **`acd.js` block-scoping footgun:** `liveStats` is declared with `let` inside the level-fade block (`if (currentPrice && allRthBarsRow.rows.length >= 3)` at line ~4065, inner `if (last5.length >= 3...)` at ~4108). ## Documentation maintenance — keep this perpetually current

This file and [ARCHITECTURE.md](ARCHITECTURE.md) are the handoff point for the next session (human or Claude) — treat letting them go stale as a real cost, the same as introducing a bug. A `Stop` hook (`.claude/settings.json`) checks at the end of every session whether structural files changed without a matching doc update and prints a reminder — if you see that reminder, act on it before ending the turn rather than dismissing it.

Concretely, whenever a session does any of the following, update the relevant doc **in that same session**, not as a follow-up:
- Add/remove a route file, service file, or DB table → update [ARCHITECTURE.md](ARCHITECTURE.md)'s route/service/table tables, and if a table was added/dropped/altered, regenerate `server/schema.sql` (command is in ARCHITECTURE.md)
- Add/remove a dashboard component → update the frontend structure table in [ARCHITECTURE.md](ARCHITECTURE.md)
- Establish a new hard rule or convention (the user corrects an approach, or confirms a non-obvious one) → add it to the **Hard rules** or **Conventions** section above
- Fix something listed in [docs/KNOWN_ISSUES.md](docs/KNOWN_ISSUES.md) → remove that entry; discover a new one → add it
- The user confirms a fix/decision but it isn't fully implemented in the same session, proposes a follow-up that isn't confirmed yet, or you find a stat/display that's stale or disconnected from its source of truth → add it to [docs/OPEN_THREADS.md](docs/OPEN_THREADS.md) **before the session ends** — don't rely on conversation memory alone to carry pending work forward. This is on you to maintain proactively; the user has delegated it rather than asking for it each time.
- `docs/` also holds point-in-time specs (`MONTE_CARLO_SPEC*.md`, `BACKTESTING_PLAYBOOK.md`) and parked design docs (`*_parked.md`) — those describe proposals, not live state, and aren't required to track the running app. Don't confuse them with ARCHITECTURE.md.
- **Any change that supersedes existing code, data, or documentation must clean up what it replaces in the same session** — don't leave stale duplicate descriptions, dead constants/variables, orphaned scratch/temp files, or superseded DB rows sitting alongside the replacement. Concretely: rewriting a script's methodology → grep for every other doc that describes the old methodology (not just the primary one) and update all of them, and remove now-unused constants/params from the code itself; reverting a bad live change → delete the temp files used to make and revert it; a finding that invalidates an old proposal → replace/remove the old note, don't just append a new one next to it (OPEN_THREADS.md especially — resolved items get struck through with a "Resolved <date>" note per its own convention, not left dangling as if still open; see that file's own header — the older "delete when fixed" wording was changed 2026-07-14).
