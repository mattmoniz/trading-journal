## Persist to a root-caused answer, dont stop at a plausible negative

- **Don't give up on a thread without vetting it thoroughly — persist to a real, root-caused answer, not the first plausible-looking stopping point.** User stated explicitly 2026-07-18: "You're taking the lead. I can't have you giving up on something without vetting it thoroughly. Persist that." Said right after a GARCH-scaled-stop investigation where the first result (fitted GARCH alpha reading ~0 every single day) could have been accepted at face value as "this whole approach is fake" — instead, root-causing it surfaced a real ES-symbol-contamination bug driving that reading, then a second numerical-degeneracy bug once that was fixed, then a third, unrelated stale-calibration bug in the consuming script. The real answer (a genuine but modest effect) was only reachable by refusing to stop at any of the earlier "looks debunked" checkpoints. **A result that looks like a dead end is exactly as suspect as a result that looks too good** — the audit discipline already applied to suspiciously positive numbers (Gemini output, "verified" comments) applies equally to suspiciously conclusive negative ones. When something comes back surprising, too clean (identical value across every observation), or flatly debunking, treat it as a lead to root-cause mechanically, not a stopping point — only stop once the result is stable under continued scrutiny, not merely once you've found *an* explanation that sounds plausible. ## Never combine trailing ampersand with run_in_background for Gemini

- **Never combine a trailing `&` with the Bash tool's own `run_in_background: true`** when calling `invoke_gemini.sh` (or any long-running script). Stacking both loses harness tracking of the real process — the wrapper returns instantly after backgrounding the job with `&`, so a "completed" notification fires seconds later while `agy` is still working, and reading `antigravity_response.md` at that point shows partial/misleading output that looks like a stall or failure. Just call `./scripts/invoke_gemini.sh <timeout>` directly with `run_in_background: true` and no `&` — let the harness track the actual duration. (Discovered 2026-07-13: this mistake also let two `agy` processes run concurrently against the same output file, corrupting it with interleaved writes — `invoke_gemini.sh` now takes a `flock` on `scratch/.invoke_gemini.lock` and refuses to start a second run.)

## Orphaned start.sh dev-server supervisor incident

- **A background `./start.sh` Bash call left running when a Claude Code session ends becomes an orphaned dev-server supervisor, invisible to `systemctl status` and capable of silently taking the app down hours later.** Found 2026-07-18: a prior session ran `./start.sh` (which launches its own `nodemon`+`vite` tree and, since 2026-07-13, deliberately `systemctl stop`s the managed `trading-journal-server.service` on takeover — see the comment in `start.sh`) as a background Bash call and ended without running `./stop.sh`. The orphaned `nodemon` process kept running for hours after the session ended, watching `server/**/*.{js,mjs,json}` and auto-restarting its own child on *any* file save (not just a commit) — explaining "the server bounced overnight with zero commits happening," previously misdiagnosed as a mysterious crash/watchdog issue. Once that orphan's own child eventually died, nothing brought the app back: systemd had been told to `stop`, not left to crash, so `Restart=on-failure` never fired, and the next session found the app fully dark with no obvious cause in `journalctl`. **Fixed at the root**: `start.sh` now has a `trap ... EXIT INT TERM` that hands port 3002 back to `trading-journal-server.service` whenever the dev session ends by *any* means — Ctrl+C, a clean exit, or the process just being killed — not only via an explicit `./stop.sh` call. Verified live (launched `start.sh`, sent it `SIGTERM` to simulate an abandoned session, confirmed systemd auto-recovered within ~15s). **The trap is a strong mitigation, not a guarantee** — a `SIGKILL` on the whole process tree (or the underlying VM itself dying) still bypasses it. If you run `./start.sh` as a background Bash call, either run `./stop.sh` before the turn/session ends or verify the trap fired (`systemctl --user is-active trading-journal-server.service`) — don't just let a background dev session dangle and assume it's harmless. **The trap had a second, worse blind spot, found live 2026-08-09: it only fires when `start.sh`'s own top-level process exits — not when `nodemon`'s spawned CHILD crashes independently while `start.sh`/`nodemon`/`vite` all stay alive.** `nodemon`'s documented behavior on a crash is "waiting for file changes before starting..." — it does not retry on its own, so a single crash (an uncaught exception, or a port race if something restarts `trading-journal-server.service` while the dev session is still up) permanently kills serving with every visible process indicator (`ps`, `pgrep`) still looking healthy. This is exactly what happened: a `./start.sh` session started 2026-08-05 stopped the managed service correctly on takeover, then its `nodemon` child eventually crashed on its own, and the top-level session was simply never terminated, so the trap never got a chance to fire — the managed `trading-journal-server.service` spent the next **4 days, 114,824 consecutive attempts**, crash-looping on `EADDRINUSE` against the still-alive orphan, completely undetected (full account `docs/DECISIONS_LOG.md` 2026-08-09). **Fixed two ways, both verified live, not just reasoned about**: (1) `start.sh` now runs a background health-monitor that polls port 3002 directly (not process liveness) and self-heals via the same recovery path as the EXIT trap if the port goes dark for 45s+ after being up, or never comes up within 90s cold — tested with `timeout --signal=TERM 70 ./start.sh`, no false positive during 70s of healthy operation, clean handback confirmed on termination; (2) the systemd unit's *default* `StartLimitIntervalSec=10s`/`StartLimitBurst=5` was itself part of the problem — with `RestartSec=5`, at most ~2 restart attempts ever fit inside any 10s window, so the burst threshold was structurally unreachable and the unit would retry forever instead of ever reaching a detectable `failed` state. A drop-in override (`~/.config/systemd/user/trading-journal-server.service.d/override.conf`, NOT git-tracked — lives outside the repo) widens this to `StartLimitIntervalSec=60`/`StartLimitBurst=6` — proved this actually works by deliberately reproducing the failure (bound a dummy listener on 3002, tried to start the real service against it, watched it correctly land in `ActiveState=failed` within ~40s instead of looping silently). **General lesson**: a recovery mechanism scoped to "the top-level process exits" doesn't cover "a supervised child dies while every supervisor above it stays nominally alive" — those are different failure shapes, and a fix for one doesn't imply coverage of the other; verify by actually killing the specific thing you're claiming to detect, not just the outer wrapper.
