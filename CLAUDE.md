# CLAUDE.md

Trading journal: React frontend (Vite, port 3000) + Express backend (port 3002) + PostgreSQL (`trading_journal` db). See [ARCHITECTURE.md](ARCHITECTURE.md) for full route/service/table inventory — this file is conventions and rules, not structure.

**Start of session / after a context clear: read [docs/OPEN_THREADS.md](docs/OPEN_THREADS.md) first.** It tracks unfinished work, unconfirmed proposals, and stale-stats findings from prior sessions — the goal is to never lose a thread to a context reset.

## Dev workflow

- Start: `./start.sh` (kills stale processes, starts server + client, self-heals the `pre-commit` hook symlink) — Stop: `./stop.sh` or `fuser -k 3002/tcp`
- `git commit` runs a **pre-commit hook** (`scripts/git-hooks/pre-commit`, symlinked from `.git/hooks/pre-commit` — `.git/hooks/` isn't tracked, `./start.sh` re-creates the symlink if missing) that blocks new hardcoded trading-threshold anti-patterns in `acd.js`/`caseEngine.js`, plus 3 more broadly-scoped patterns across `server/`/`src/`/`scripts/` (wrong $/pt constants, `SUM(pnl)`-style CumPL-diff violations, the JS-`toISOString()`-for-a-trading-day-date bug) — 7 patterns total, defined once in `scripts/hardcoded-threshold-patterns.sh` and shared with the Stop hook's advisory version. Deliberate exception: `ALLOW_HARDCODED=1 git commit ...`.
- Server only: `npm run server` (nodemon, port from `.env` `PORT=3002`) — Client only: `npm run client`
- DB: `server/schema.sql` is a full `pg_dump --schema-only` snapshot (122 tables/views, regenerated 2026-06-30 after a dead-table cleanup) — there's still no tracked migration history, so it drifts again the moment a table is added/altered live without regenerating. See the regen command in [ARCHITECTURE.md](ARCHITECTURE.md#schema-source-of-truth). When in doubt, query `information_schema.tables`/`information_schema.columns` against the live DB rather than trusting the file is current.

## Hard rules

- **Anything that drives or anticipates a decision — a data point, a computed signal, a classifier, a backtest finding, not just a "script" — must be built so the system keeps learning from it and can revisit it. No dead ends.** Added 2026-07-18 per explicit user directive ("its not just scripts it[s] data or datapoints anything that drives or anticipates in decision making must be help the system keep learning and growing. No dead ends") after a session spent the day building exactly this pattern piecemeal (persisting `VOL_REGIME_HIST`, then `GARCH_VOL_SCALE`, recording `RESEARCH_CLAIM` rows for every tested finding) without it ever being named as a governing rule new work is held to. Concretely, before considering anything of this kind done, check all four:
  1. **Persisted somewhere queryable** (`performance_audit` or a real table) — not trapped in a script-local variable, a one-off `scratch/*.json` file, or a hardcoded literal in the serving code. A hardcoded snapshot of a once-real number is the textbook failure case here — see the hand-typed-stat rule below, 7 confirmed instances, most recently `keyLevels.js`'s `tierStats` object (2026-07-18): a real calibration got computed once, dropped into a literal, and then just sat there while the real number underneath it drifted 3-6x away, including a full sign flip, with nothing to ever notice.
  2. **Has a recheck/recalibration path** — a scheduled script (`run_weekly_backtests.sh`), a `RESEARCH_CLAIM` 30-day cycle, or at minimum a documented manual recheck trigger. Not compute-once-and-forget.
  3. **Actually wired to a consumer, or explicitly flagged if not yet wired.** A signal nobody reads is a dead end whether or not it's persisted — either it feeds a live decision (sizing, suppression, a displayed card) or it's tracked as a `flag_decision.mjs` `OPEN_DECISION` so someone has to actively decide to wire it in or drop it, never just silently sitting there unreferenced.
  4. **Discoverable** — has an entry in `ARCHITECTURE.md`'s inventory or this file's "Where to look" section, not an orphan only findable by grepping around and hoping.
  This names the connective principle behind several mechanisms that already exist as separate conventions — `RESEARCH_CLAIM` (item 2), `OPEN_DECISION` (item 3), "export the real function, never reimplement" (item 1, applied to code), the no-static-thresholds rule below (item 1, applied to a threshold specifically) — treat this as the reason those exist, not a fifth new mechanism to build. When starting something new that computes or anticipates anything, ask which of the four it's missing before calling it done.
- **Any new setup, signal, or calibration finding must be evaluated for BOTH the RTH window (9:30am-4pm ET) and the Globex/overnight window (6PM-8:30AM ET) before being considered complete — never default to RTH-only and call it done.** User directive 2026-07-22, given directly after the confluence-pair proximity calibration was built and backtested RTH-only (`scripts/backtest_confluence.js`'s `getRTHBars()`) without the question of overnight applicability ever being raised. This codebase already has two parallel, structurally different detection engines — the full RTH level-fade engine (`acd.js` ~3830-4430, `sizeMultiplier` IIFE, `keepLevelsAll`, confluence-aware) and the much simpler `detectGlobexSetup()` (~line 594, single-level touches only, no `sizeMultiplier` stack, no confluence tracking at all as of 2026-07-22) — and it is easy for a new finding built/tested against one to simply never get asked about the other. Concretely, before calling any new setup-discovery or calibration thread done: (1) test it against Globex/overnight data too, not just RTH, even if the result is negative or thin — a tested-and-recorded "doesn't apply overnight" is fine, an untested gap is not; (2) if the live wiring mechanisms differ between the two engines (e.g. RTH has a `sizeMultiplier` stack to hook a bonus into, Globex currently doesn't), wire into whichever supports it and explicitly flag (`OPEN_DECISION`) whichever doesn't rather than silently leaving it RTH-only with no record of the gap. See `confluence_pair_globex_backtest` `RESEARCH_CLAIM` for the first applied instance of this rule.
- **No static thresholds.** Every threshold in this codebase must be derived from a rolling distribution (σ from a rolling mean/std), never a hardcoded number. This applies to entries, stops, targets, signal triggers — everything. If you're about to write a literal number as a cutoff, stop and compute it from historical data instead.
- **P&L must use the CumPL diff method**, not `SUM(pnl)` or `SUM(FlatToFlat)` — both overcount. See the SQL pattern in [ARCHITECTURE.md](ARCHITECTURE.md#pnl-calculation-cumpl-diff--critical-dont-regress-this). `/api/daily-logs` and `/api/stats/daily` both implement this — keep them in sync if you touch either. **A raw, account-type-unscoped CumPL-diff is a DIFFERENT and WORSE bug than the `SUM(pnl)` it replaces — always scope to `custom_fields->>'account' LIKE '%-PRO%'`, matching `stats.js`'s `/stats/capture-ratio` (the established correct reference).** Found 2026-07-19 fixing `server/services/patternMemoryUpdate.js`'s `session_pnl` (`OPEN_DECISION` `pattern_memory_update_session_pnl_needs_cumpl_audit`): a naive `LAG(cum_pl) OVER (PARTITION BY account ORDER BY log_date)` interprets a practice/sim account's periodic balance reset as a single-day loss in the tens of thousands — confirmed live, `PRACTICEDec108855775`'s `cum_pl` dropped from $13,000.00 (2024-12-16 close) to resetting near zero the next day, which an unscoped diff reads as a **-$12,155 loss that never happened**. Caught only because the "fix" was audited against real numbers before trusting it — Gemini's first pass reported the CumPL-diff and `SUM(pnl)` "matching almost perfectly," which was wrong (its query used a flawed `COALESCE(LAG(...), cum_pl)` fallback that silently zeroed out exactly the rows that would have exposed the reset); a from-scratch re-implementation of the canonical pattern surfaced the $13K-scale discrepancy immediately. `-PRO%` accounts don't get balance-reset mid-history the way practice ones do — this is why `stats.js` already scoped this way; `patternMemoryUpdate.js` didn't, until this fix. When there's no PRO-account CumPL data for a given day (only ~48 of 358 historical trading days have any), fall back to raw `SUM(pnl)` for that day only — imprecise but not corrupted, same documented-exception convention as `dll.js`'s own fallback.
- **This journal trades MNQ (Micro E-mini Nasdaq): $2/point, $1 round-trip commission** — matches `server/routes/acd.js`'s live resolution path (`const PNL_PER_POINT = 2; // MNQ = $2/point`, `const COMMISSION = 1`), the ground truth for what's actually traded. **Never copy a `$/pt` or commission constant from another script without checking it matches this.** Found 2026-07-14: `scripts/archive/backfill_level_fades.js` used `PT=5, COMM=5` (matching neither MNQ's real $2 nor standard NQ's real $20) — an uncaught error present since that script's creation, silently copied into 6 new `repair_*.mjs` scripts written earlier the same session before being caught. Overstated every affected setup_type's dollar-EV by ~2.5x (correct sign, wrong magnitude) until fixed via `scripts/repair_dollars_per_point.mjs`. If you're about to write a `$/pt` or commission constant in a new script, check it against `acd.js`'s live values first — don't trust an existing script's constant just because it's already there.
- **~80% of `active_setups` is synthetic backfill data, not live-fired trades — check `origin_status` before treating any figure derived from this table as realized/historical performance.** Found 2026-07-17 (Opus Audit #3, `docs/OPEN_THREADS.md`): `resolution_method` breakdown is `BACKFILL` 6,375 + `EARLY_TOUCH_BACKFILL` 4 (inserted retroactively by old backfill/repair scripts, **never fired through the live system at all**) vs. `PRICE_CLEAN` 231 (genuinely live-resolved) out of 7,988 total rows. `active_setups.origin_status` (immutable at insert, never touched by any resolution UPDATE — unlike `status`, which gets overwritten to `RESOLVED`/`EXPIRED`) now distinguishes `ACTIVE` (real, live-visible)/`SHADOW` (suppressed, background-only)/`BACKFILL` (synthetic)/`UNKNOWN` (pre-2026-07-09, unrecoverable — no `SETUP_STATUS` snapshot history reaches back that far). **A `SUM(actual_pnl)` or backtest built from `active_setups` without filtering by `origin_status` is a strategy simulation, not an account record** — this bit an entire session's worth of walk-forward-backtest/DLL-sweep/weekly-P&L work before the gap was found. Before presenting any `active_setups`-derived dollar figure as "what happened," check what fraction of its population is `BACKFILL`.
- **Never fabricate a stat.** Any win-rate/hit-rate claim needs N≥20 in the sample before it's reported as decisive (see `engineReadHitRates.js` convention). Below that, say so explicitly rather than rounding to a confident-sounding number.
- **Never hand-type a WR%/N/$ literal into a live-rendered card, label, or description string.** Found 2026-07-13: 6 separate instances across `mine_session_bias.mjs`, `antigravityEdges.js` (IB re-test cards, gap-fill card, V-pattern card, `SETUP_CONTEXT` adjustment table), and `acd.js` (`levelMap.bestCtx`) — all presented a specific hand-typed number as if freshly computed, several silently drifted to the point of being *directionally wrong* (e.g. `acd.js` claimed IB_LOW was an "88% WR" edge; the real, live number was 66% WR at **negative** EV). **7th instance found 2026-07-18**: `server/routes/keyLevels.js`'s `/api/confluence/today-zones` `tierStats` object — hand-typed despite its own comment claiming it was "latest weekly rigor-checked calibration," found while consolidating an unrelated GARCH backtest and comparing its touch-detection constants against the live confluence system. Every tier was off 3-6x vs. the real latest `performance_audit` `CONFLUENCE_AUDIT` row, `SINGLE` wrong-signed (+$6.91 hardcoded vs. real **-$3.02**). Fixed the same way as the other 6: query `performance_audit` live (12h cache, `server/lib/cache.js`). Full writeup: [docs/OPEN_THREADS.md](docs/OPEN_THREADS.md). Either derive the text from a `row` field already fetched from `performance_audit` in the same function, or write a dedicated `scripts/backtest_<name>.mjs` that populates one — never hand-type the number, even as a placeholder "for now." **This pattern keeps recurring (7 instances now) — when touching ANY file that renders a WR%/N/$ figure for any reason, even in passing, check whether that figure is a live query result or a literal before moving on, don't wait to stumble into it.**
- **No lookahead in backtests/replays.** Case engine, day-type reassessment, and all backtest scripts must only use information that would have been available at that point in time. This is a frequent source of subtle bugs — when writing a new backtest script, explicitly check that no future bar/level data leaks into a decision made earlier in the session.
- **Volume-profile computations (POC/VAH/VAL) must spread each bar's volume across its own high-low tick range, never bucket 100% of it at one price.** `server/services/developingValueService.js`'s `computeProfile(bars)` is the single correct reference implementation (spreads volume evenly across each bar's H-L range, then extends VAH/VAL alternately toward whichever side has more volume next until 70% total is enclosed) — for any period-range VA (week/month/quarter/2-day), call its exported `computeVolumeProfileForRange(queryFn, { startDate, endDate, ... })` wrapper rather than writing a new SQL aggregation. Found 2026-07-17: a `ROUND(low/0.25)*0.25 ... GROUP BY` bucket-by-low pattern (plus a non-standard fixed 35%-up/35%-down value-area split instead of the correct alternating-to-70% method) had been hand-duplicated across `scripts/compute_levels.js` (PW/PM/3M_VAH/VAL/POC — the values written to `level_prices`, feeding every backtest/live level-fade candidate for those levels), `server/routes/acd.js` (6 occurrences: the live 2-day-composite POC, 2 prior-month VA computations, 2 prior-day VA fallbacks), and `server/routes/weekly.js` (3 endpoints, all confirmed dead/no frontend caller). Because a bar that trades through a 5-point range in one minute got 100% of its volume counted at the bottom tick, every affected VAH/VAL/POC was dragged toward the low of the session/period — drift confirmed real and often large (many periods showed 100+ point differences once corrected) once independently spot-checked directly (not just via Gemini's own estimate, which had at least one confirmed replication error against the actual live SQL — audited per the standing Gemini-output-audit rule). Fixed by centralizing on `computeProfile`/`computeVolumeProfileForRange`, backing up and recomputing the full `level_prices` history for the affected level_names, and re-tagging every trade in `trades.level_proximity` (whose nearest-level ranking could have been skewed by a wrong VA value even when the final tag wasn't itself a VA level) against the corrected data. Full writeup and backup-table names: docs/OPEN_THREADS.md / docs/DB_BACKUP_CATALOG.md.
- **Export the real function, never reimplement live-derived classification logic inline in a backtest script.** If a backtest/mining script needs a value that a live service already computes (a regime, a day-type, a level, any derived classifier — not a raw DB column), it must `import`/reuse that service's real exported function, or read a persisted canonical table populated by it, never re-code the math by hand. Found 2026-07-16: two independent Gemini attempts at a Markov-vs-volatility-regime comparison each had to hand-reimplement `classifyRegime()` from scratch (`volatilityRegimeService.js` had no persisted history to check against), and the two reimplementations disagreed with each other and with the live tool's own prior validation — a real, silent drift bug, not a hypothetical. Fixed at the root by exporting `fiveMinBars`/`stdevLogReturns`/`getPercentile`/`classifyRegime`/`getMorningVolBaseline` from `volatilityRegimeService.js` and building `scripts/backfill_volatility_regime_history.mjs`, which imports them directly and persists one row/day to `performance_audit` (`signal_type='VOL_REGIME_HIST'`) as the now-canonical source every future comparison should join against. When adding a new derived/live classifier, export its core function(s) at creation time rather than waiting for a second script to need it and reimplement instead.
- **Every tested research/exploratory claim — not just setup-calibration ones — gets recorded via `scripts/record_claim.mjs`, positive or negative.** A hypothesis that gets tested, produces a real N/WR/EV number, and only lives as prose in `docs/OPEN_THREADS.md` or a `scratch/*.json` file has no lifecycle: nothing re-checks it, and the next session re-derives it from scratch (sometimes differently — see the rule above). `recordClaim({slug, claimText, sourceFile, sourceDate, sampleSize, winRate, evPerTrade, rigorStatus, status})` writes/updates a `signal_type='RESEARCH_CLAIM'` row in `performance_audit` with a 30-day `next_recheck_due`; `node scripts/record_claim.mjs --list` shows every claim and flags overdue ones. `status` is `CONFIRMED` (independently re-verified), `PROVISIONAL` (real but thin/unstable/unchecked-for-rigor), or `STALE` (needs a fresh recheck, generally by age). This is separate from the existing setup-calibration tables (`SETUP_STATUS`/`OPTIMAL_STOP`/`DAY_TYPE_ALPHA`/etc.) — those already have their own lifecycle; `RESEARCH_CLAIM` is for everything else. Built 2026-07-16 per an Opus consultation on making this codebase's research findings durable instead of evaporating each session; seeded with 7 audited claims from this session (one caught a real Gemini-fabricated set of numbers before it entered the ledger — see docs/OPEN_THREADS.md). **Found 2026-07-20 (new session): two scripts (`test_extension_vs_garch_vol.mjs`, `test_extension_vs_next_level_distance.mjs`) hand-rolled their own `performance_audit` INSERT instead of calling `recordClaim()` — and set `next_recheck_due` to the SAME DAY the claim was written, not +30 days, so the session-start hook flagged both as overdue the very next day.** Fixed both to call the canonical helper. **When writing any new script that persists a `RESEARCH_CLAIM` row, always import and call `recordClaim()` — never hand-write the INSERT, even if it looks like a one-off** — this is the same "shared module, don't reimplement" principle applied to a persistence helper instead of a computation function.
- **A `next_recheck_due` on a `RESEARCH_CLAIM` row is a FLAG, not an auto-rerun — if the finding is still open (not a settled/rejected/confirmed one-time study), wire its source script into a recurring cron too, or it never actually recomputes itself.** This is the direct answer to "why doesn't this work like `SETUP_STATUS`, which already auto-promotes any setup_type the moment it crosses real N≥20" — `backtest_setup_status.mjs` can do that for free because it's a single generic `GROUP BY setup_type` scan with no hardcoded list, so every live setup_type rides the same daily/weekly cron automatically. A `RESEARCH_CLAIM` has no equivalent generic scanner — each is backed by a bespoke one-off script — so the *only* way it keeps re-checking itself against fresh data is if that specific script is added to `run_weekly_backtests.sh` or `run_daily_calibration.sh`, same as any calibration script (`calibrate_delta_confirmation.mjs`, `scan_regime_combinations.mjs`, `backtest_pd2_2dpoc_complete.mjs`, `backtest_vwap_reclaim_hold_phase1.mjs`/`_globex_phase1.mjs` all do this) — the promotion/wiring decision still stays a human call (see `scan_regime_combinations.mjs`'s `flagDecision()`-on-clean-cell pattern), only the *recompute* becomes automatic. **`test_invariants.mjs` check `[10]`** (added 2026-08-04, direct user question) verifies every `RESEARCH_CLAIM` source script's filename appears in one of those two cron files — WARN-only and deliberately quiet in the routine alert stream (one aggregate count, not one line per claim: as of 2026-08-04, 149 of 161 historical claims are unscheduled, and that's mostly *expected*, since most of this codebase's `RESEARCH_CLAIM` backlog is settled/rejected one-time studies that don't need a standing recheck) — full per-claim detail is written to `scratch/research_claim_unscheduled.txt` for triage, not spammed into `scratch/gemini_alerts.txt`. Read that file when deciding whether a specific open finding deserves to be wired in; don't treat the aggregate WARN count as something to drive toward zero.
- **Resolve every `isolation: worktree` Agent dispatch before the spawning session ends — never leave one for a future session to discover by accident.** The harness only auto-deletes an isolated worktree if the agent made *no* changes; if it made any, the path/branch are handed back and a human/session must explicitly commit+merge it or deliberately discard it (`git worktree remove` + delete the branch). Found 2026-07-16: a 2026-07-01 `isolation: worktree` dispatch (24hr Globex VWAP feature) left ~3,100 uncommitted lines across 31 files sitting untouched for two weeks — nothing in this repo's workflow surfaces an orphaned worktree, so it was only found by accident during an unrelated dead-code grep. `.claude/hooks/session-start.sh` now flags any worktree besides the main checkout at the start of every session (see its `STRAY_WORKTREES` check) as a backstop, but the real fix is not leaving one dangling in the first place.
- **Do not guess on third-party tool behavior** (especially Sierra Chart specifics) — fetch documentation or ask before asserting how an external tool behaves.
- **Never write a file >400 lines in a single Write call.** Use Write for the first section, then `cat >>` via Bash to append the rest. This avoids the 32k output token limit that silently truncates large writes.
- **Use Gemini for mining/analysis, Claude for implementation.** When a task is combinatorial exploration or pattern-mining over `performance_audit`/trade data — "which pairs are best under condition X," "what does the data show about Y across N setup types," multi-scenario simulations — dispatch it to Gemini via the `scratch/claude_request.md` protocol rather than grinding through it directly. Gemini has read-only DB access and doesn't burn Claude's context on large query output; only the findings should come back into context, not raw rows. Claude's job is building the systems (scripts, endpoints, hooks) and interpreting/applying what Gemini finds — not re-deriving the mining work itself. Reserve doing it directly for small, deterministic, single-query aggregations (e.g. one bucketed backtest over one table) where dispatching would cost more round-trip time than it saves, and for anything Gemini has already gotten wrong twice on this task (see the 2-strikes rule below). This does not relax **Audit all Gemini output before acting on it** below — mining work still gets verified before anything is promoted to live.

(1) Full AUTONOMOUS mine-and-run for the actual analysis, same as the rule above. (2) A separate review-only pass on the resulting code (explicit "do not execute, do not edit" header) before trusting any number or shipping any live change. Once adopted, phase 0 caught a real design gap in a risk-management gate backtest (marginal utility against the existing suppression stack was the single most important thing to check and hadn't been planned for), and phase 2 caught the resulting script's level-name mapping was broken/incomplete before any promotion decision was made on it. ## Conventions

- **A `localStorage`-persisted drag-to-reorder column order must be MERGED against the current column set at load time, never just filtered against it.** The obvious-looking pattern (`(savedOrder || defaultKeys).map(k => COLS.find(c => c.key === k)).filter(Boolean)`) only ever drops a key that's no longer valid — it can never re-add a key that's new since the user's last drag, because that key simply isn't in the saved array to begin with. Found 2026-07-28, independently in two places (`SetupReferenceView.jsx`, `SetupHistoryView.jsx`) — both had this exact bug, and it silently deleted the brand-new `misc` column for any user with an already-saved order, surfaced only via a user screenshot that was missing the column entirely (looked like "the column reset," but was actually "the column never had a chance to appear"). Fixed by reconciling any `DEFAULT_COLS`/`SETUP_LOG_COLS` key absent from the saved order back in (appended at the end) in the `useState` initializer itself — synchronous, no render flicker, and the existing "persist on change" effect writes the corrected order straight back to `localStorage`. Any future table with this drag-reorder-plus-persist pattern needs the same reconciliation, not the filter-only version.
- **Any new script querying `price_bars_primary` with a lower-bound-only `ts >= X` filter must add an explicit upper bound.** `price_bars_primary` is a VIEW (join + `GROUP BY` aggregation over `price_bars` + `price_bars_contract_calendar`, confirmed via `information_schema.tables.table_type='VIEW'`) — it can never have an index, so an unbounded query forces the aggregation across everything from `X` through the present before it can sort/`LIMIT`. Found 2026-07-27: a new backtest script's per-trade bar lookup took ~900ms-1.2s/call (2.5+ hours projected for ~11,000 rows) until a tight upper bound (`ts < X + interval`) was added, dropping it to 62ms (15-20x). Full writeup and the broader structural fix (materialize historical bars into a real indexed table): ARCHITECTURE.md's `price_bars_primary` section, `OPEN_DECISION`s `price_bars_primary_unbounded_query_audit`/`price_bars_primary_materialize_historical_bars`.
- **Never look up a bar by an exact epoch/timestamp match against a real trade's `fired_at` — real trades carry genuine sub-minute precision (recorded live via `NOW()`), but bars are always exactly on the minute, so an exact match silently fails and the trade gets dropped, not flagged.** Floor the timestamp to the minute before the lookup. Found 2026-07-27: a backtest script's `Map`-based exact-epoch lookup discarded 31 real trades into a "skipped, no bar found" bucket — one of them (id=67604) was a genuine occurrence of the exact condition being tested, silently erased, producing a false "zero occurrences ever" finding. The bug was masked because the one row used to "verify" the lookup method earlier happened to have `fired_at` exactly on the minute (an unrepresentative pick) — pick a normal, live-recorded row (non-zero seconds) when spot-checking any timestamp-matching logic, not whichever row `LIMIT 1` happens to return.
- **A number that survives being computed twice by the same script is not verified — it only proves the script is consistent, bugs included.** Independent re-derivation (by hand with a different method, or dispatched to Gemini without showing it the original methodology) is what actually catches a deterministic bug a repeated run cannot. Found 2026-07-27, twice in one session: a bar-6 exit-rule figure and a "zero real occurrences" claim were both wrong, both reproduced identically on a second run of the same buggy code, and both only corrected once an independent second derivation disagreed and the disagreement was chased down rather than dismissed. Applies even when the independent check itself contains an unrelated error (Gemini's own re-derivation had a wrong `$/pt` constant on one check the same session) — audit a disagreement in both directions instead of assuming whichever answer already existed is correct.
- **Confound checklist for any new comparison-style backtest (two arms compared against each other).** Built 2026-07-21 per Opus Audit #4 after the same failure shape recurred 5+ times across ~5 sessions, always looking like a real win first, twice reaching `RESEARCH_CLAIM`/`OPEN_DECISION` before being retracted (most recently the same day: `volume_confirmed_candle_pattern_low_vol_trap`, selected the 6 largest-effect setup_types from a 48-setup sweep, reversed under held-out replication). Before recording or promoting any "config/condition A beats B" finding, check all four:
  1. **Do the two compared arms differ ONLY in the hypothesis variable**, or does one arm have a structural/algebraic edge (a later entry against the same fixed exit, a smaller remaining risk distance, anything mechanical)? If unsure, ask whether the "smarter" arm would still win with the intelligence stripped out and only the structural difference left.
  2. **Is the baseline computed by the exact same method/window as the thing being compared** — resimulated in the same pass, never read from a stored column computed under different historical conditions (the `backtest_scaleout_runner.mjs` baseline-mismatch incident, 2026-07-19).
  3. **Does the signal select a sub-population** (overshot / made-a-new-extreme / pattern-present / any filter)? If so, is there a same-selection-minus-the-signal-condition control bucket — the 3-way template in `scripts/pilot_cvd_divergence.mjs` (`SIGNAL` / `SAME_SELECTION_NO_SIGNAL` / `NEVER_SELECTED`) is the pattern to reuse, not reinvent.

If so, run `computeReplication()` (`server/services/rigorDiagnostics.js`) — a held-out/permutation check that pools the selected subset against everything NOT selected and reports whether the direction and magnitude survive. ## Documentation maintenance — keep this perpetually current

This file and [ARCHITECTURE.md](ARCHITECTURE.md) are the handoff point for the next session (human or Claude) — treat letting them go stale as a real cost, the same as introducing a bug. A `Stop` hook (`.claude/settings.json`) checks at the end of every session whether structural files changed without a matching doc update and prints a reminder — if you see that reminder, act on it before ending the turn rather than dismissing it.

Concretely, whenever a session does any of the following, update the relevant doc **in that same session**, not as a follow-up:
- Add/remove a route file, service file, or DB table → update [ARCHITECTURE.md](ARCHITECTURE.md)'s route/service/table tables, and if a table was added/dropped/altered, regenerate `server/schema.sql` (command is in ARCHITECTURE.md)
- Add/remove a dashboard component → update the frontend structure table in [ARCHITECTURE.md](ARCHITECTURE.md)
- Establish a new hard rule or convention (the user corrects an approach, or confirms a non-obvious one) → add it to the **Hard rules** or **Conventions** section above
- Fix something listed in [docs/KNOWN_ISSUES.md](docs/KNOWN_ISSUES.md) → remove that entry; discover a new one → add it
- The user confirms a fix/decision but it isn't fully implemented in the same session, proposes a follow-up that isn't confirmed yet, or you find a stat/display that's stale or disconnected from its source of truth → add it to [docs/OPEN_THREADS.md](docs/OPEN_THREADS.md) **before the session ends** — don't rely on conversation memory alone to carry pending work forward. This is on you to maintain proactively; the user has delegated it rather than asking for it each time.
- `docs/` also holds point-in-time specs (`MONTE_CARLO_SPEC*.md`, `BACKTESTING_PLAYBOOK.md`) and parked design docs (`*_parked.md`) — those describe proposals, not live state, and aren't required to track the running app. Don't confuse them with ARCHITECTURE.md.
- **Any change that supersedes existing code, data, or documentation must clean up what it replaces in the same session** — don't leave stale duplicate descriptions, dead constants/variables, orphaned scratch/temp files, or superseded DB rows sitting alongside the replacement. Concretely: rewriting a script's methodology → grep for every other doc that describes the old methodology (not just the primary one) and update all of them, and remove now-unused constants/params from the code itself; reverting a bad live change → delete the temp files used to make and revert it; a finding that invalidates an old proposal → replace/remove the old note, don't just append a new one next to it (OPEN_THREADS.md especially — resolved items get struck through with a "Resolved <date>" note per its own convention, not left dangling as if still open; see that file's own header — the older "delete when fixed" wording was changed 2026-07-14).
