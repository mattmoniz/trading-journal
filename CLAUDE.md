# CLAUDE.md

Trading journal: React frontend (Vite, port 3000) + Express backend (port 3002) + PostgreSQL (`trading_journal` db). See [ARCHITECTURE.md](ARCHITECTURE.md) for full route/service/table inventory — this file is conventions and rules, not structure.

**Start of session / after a context clear: read [docs/OPEN_THREADS.md](docs/OPEN_THREADS.md) first.** It tracks unfinished work, unconfirmed proposals, and stale-stats findings from prior sessions — the goal is to never lose a thread to a context reset.

## Dev workflow

- Start: `./start.sh` (kills stale processes, starts server + client, self-heals the `pre-commit` hook symlink) — Stop: `./stop.sh` or `fuser -k 3002/tcp`
- `git commit` runs a **pre-commit hook** (`scripts/git-hooks/pre-commit`, symlinked from `.git/hooks/pre-commit` — `.git/hooks/` isn't tracked, `./start.sh` re-creates the symlink if missing) that blocks new hardcoded trading-threshold anti-patterns in `acd.js`/`caseEngine.js` (same 4 patterns as the Stop hook, but commit-time and blocking instead of session-end and advisory). Deliberate exception: `ALLOW_HARDCODED=1 git commit ...`.
- Server only: `npm run server` (nodemon, port from `.env` `PORT=3002`) — Client only: `npm run client`
- DB: `server/schema.sql` is a full `pg_dump --schema-only` snapshot (122 tables/views, regenerated 2026-06-30 after a dead-table cleanup) — there's still no tracked migration history, so it drifts again the moment a table is added/altered live without regenerating. See the regen command in [ARCHITECTURE.md](ARCHITECTURE.md#schema-source-of-truth). When in doubt, query `information_schema.tables`/`information_schema.columns` against the live DB rather than trusting the file is current.

## Hard rules

- **No static thresholds.** Every threshold in this codebase must be derived from a rolling distribution (σ from a rolling mean/std), never a hardcoded number. This applies to entries, stops, targets, signal triggers — everything. If you're about to write a literal number as a cutoff, stop and compute it from historical data instead.
- **P&L must use the CumPL diff method**, not `SUM(pnl)` or `SUM(FlatToFlat)` — both overcount. See the SQL pattern in [ARCHITECTURE.md](ARCHITECTURE.md#pnl-calculation-cumpl-diff--critical-dont-regress-this). `/api/daily-logs` and `/api/stats/daily` both implement this — keep them in sync if you touch either.
- **Never fabricate a stat.** Any win-rate/hit-rate claim needs N≥20 in the sample before it's reported as decisive (see `engineReadHitRates.js` convention). Below that, say so explicitly rather than rounding to a confident-sounding number.
- **Never hand-type a WR%/N/$ literal into a live-rendered card, label, or description string.** Found 2026-07-13: 6 separate instances across `mine_session_bias.mjs`, `antigravityEdges.js` (IB re-test cards, gap-fill card, V-pattern card, `SETUP_CONTEXT` adjustment table), and `acd.js` (`levelMap.bestCtx`) — all presented a specific hand-typed number as if freshly computed, several silently drifted to the point of being *directionally wrong* (e.g. `acd.js` claimed IB_LOW was an "88% WR" edge; the real, live number was 66% WR at **negative** EV). Full writeup: [docs/OPEN_THREADS.md](docs/OPEN_THREADS.md). Either derive the text from a `row` field already fetched from `performance_audit` in the same function, or write a dedicated `scripts/backtest_<name>.mjs` that populates one — never hand-type the number, even as a placeholder "for now."
- **No lookahead in backtests/replays.** Case engine, day-type reassessment, and all backtest scripts must only use information that would have been available at that point in time. This is a frequent source of subtle bugs — when writing a new backtest script, explicitly check that no future bar/level data leaks into a decision made earlier in the session.
- **Do not guess on third-party tool behavior** (especially Sierra Chart specifics) — fetch documentation or ask before asserting how an external tool behaves.
- **Never write a file >400 lines in a single Write call.** Use Write for the first section, then `cat >>` via Bash to append the rest. This avoids the 32k output token limit that silently truncates large writes.
- **Use Gemini for mining/analysis, Claude for implementation.** When a task is combinatorial exploration or pattern-mining over `performance_audit`/trade data — "which pairs are best under condition X," "what does the data show about Y across N setup types," multi-scenario simulations — dispatch it to Gemini via the `scratch/claude_request.md` protocol rather than grinding through it directly. Gemini has read-only DB access and doesn't burn Claude's context on large query output; only the findings should come back into context, not raw rows. Claude's job is building the systems (scripts, endpoints, hooks) and interpreting/applying what Gemini finds — not re-deriving the mining work itself. Reserve doing it directly for small, deterministic, single-query aggregations (e.g. one bucketed backtest over one table) where dispatching would cost more round-trip time than it saves, and for anything Gemini has already gotten wrong twice on this task (see the 2-strikes rule below). This does not relax **Audit all Gemini output before acting on it** below — mining work still gets verified before anything is promoted to live.
- **Gemini gets 2 correction attempts, then Claude takes over.** When Gemini's output is wrong (wrong numbers, wrong methodology, SQL error loops — not a partial/incomplete response), send a correction prompt and re-invoke. If the 2nd attempt is also wrong, stop correcting and do the task directly instead of retrying a 3rd time. User rule: "after 2 incorrect attempts by Gemini, you can step in."
- **Audit all Gemini output before acting on it.** Gemini produces plausible-looking but sometimes wrong analysis. After reading `scratch/antigravity_response.md`, verify 3–5 key claims by re-querying the DB directly before promoting any finding to `performance_audit` or changing live parameters. Specific checks: (1) 100%/0% WR with N≥10 → always check `COUNT(DISTINCT log_date)` for single-session clustering; (2) grid output → compare "current params" cell to existing `performance_audit` baseline; (3) N counts → verify with a direct `COUNT(*)`; (4) any TRADE recommendation → re-run the WR/EV query yourself. User delegated this explicitly: "I want Claude to audit anything and everything Gemini does. It lies sometimes."
- **Check for frontend render errors before calling any frontend change done.** Run `npm run lint:frontend` (ESLint `no-undef` over `src/**/*.jsx`/`*.js` with browser+JSX globals in `eslint.config.js` — catches missing-import/undefined-variable `ReferenceError`s before they hit the browser) and `npm run build` (catches broken import/export paths and esbuild-level errors like duplicate object keys that lint won't). Also check `scratch/gemini_alerts.txt` / `scratch/server_errors.jsonl` for `[CLIENT_ERROR]` entries — `trading-journal-watcher.service` (`scratch/gemini_error_watcher.mjs`) logs live browser errors there, and a real one can sit unnoticed for days if nothing checks it. Added 2026-07-13 after a code-split refactor left 4 components used-but-unimported (`LivePlaybookCard`, `ApproachingLevelBanner`, plus 5 more in `BacktestView.jsx`) and a recurring `obj.fmtP(field)` bug (should be `fmtP(obj.field)` — `fmtP` is an imported function, not a method) sitting live undetected. If real browser/Playwright tooling isn't available in the environment, say so explicitly rather than claiming an interactive check was done — static checks (lint/build/dev-server-transform) confirm nothing throws on load, not that a specific interaction (hover, click) behaves correctly.

## Conventions

- **Benchmarking bundle size across commits (git worktrees):** never symlink `node_modules` between a worktree and the main repo — Vite's dependency-optimizer cache (`node_modules/.vite`) is shared through the symlink and can silently contaminate build output from a different commit's module graph, even after deleting `node_modules/.vite` between runs. Give each worktree its own real `npm install`. Also build each commit in its own fully separate Bash/tool call — chaining `cd worktreeA && npm run build` followed by a second build command in the *same* call risks the shell's cwd silently carrying over to the second build too. Found 2026-07-13: a self-audit of a lazy-loading change reported a "52% bundle regression" that was entirely a benchmarking artifact from these two bugs stacked together; an independent review with a clean `node_modules` install got the correct (and much better) numbers.
- Backtest scripts live in `scripts/`, named `backtest_<hypothesis>.js`, run manually via `node`, and typically write findings to the `performance_audit` table. They are not imported by the running app.
- Sierra Chart TAL data is stored as JSONB under `custom_fields->'sierra_data'` rather than typed columns — this lets new TAL columns appear without a migration and lets old Activity Log format rows coexist.
- Account filter state is lifted to `App.jsx` and shared between Calendar and Dashboard — don't duplicate it locally in a component.
- **Don't keep adding to `App.jsx`.** It was 20K+ lines before the 2026-07-13 code-split (`git log` commit `7c9b22a`) moved most view-layer code out into `src/views/`; it's now ~1.8K lines, but the split isn't an excuse to reverse it by piling new code back in. When a change needs new UI, extract it into its own file (`src/components/dashboard/` or `src/views/`) instead of inlining it. If a constant or helper needs to be shared across view files, put it in `src/constants/` or `src/utils/` — don't leave it as an unexported local `const`/`function` in App.jsx. That exact mistake (`SETUP_DISPLAY_LABELS`, `SETUP_RESOLUTION_TEXT`, `CAL_SETUP_SHORT_LABELS`, `LR_SLATE`, `getSetupConviction` all defined locally in App.jsx pre-split) caused several `ReferenceError`s in `ACDView.jsx`/`CalendarView.jsx` after the split, since they referenced App.jsx-local bindings across a file boundary. User directive, restated 2026-07-13.
- **Server-autonomous detection:** `server/index.js` runs a `setInterval` every 60s during 9:30–4 PM ET Mon–Fri calling `GET /api/acd/today`. This is intentional — it makes level fade detection independent of browser clients. Do not remove it. The INSERT in `acd.js` is `ON CONFLICT DO NOTHING` so concurrent client polls don't double-write.
- **Level fade detection gate:** `acd.js` line ~3838 checks `allRthBarsRow.rows.length >= 3` (not 60). IB-specific levels (`ibHighToday`/`ibLowToday`, `IB_MID_SCALP_FADE`, `OR_MID_AFTER_IB_FADE`) self-gate via `etMinNow >= 630` — do not restore the 60-bar gate.
- **sizeMultiplier is an IIFE** inside the `levelScalpSetup` object in `acd.js`. All sizing adjustments live there. When adding a new factor: (a) research backs it (N≥20), (b) add to the IIFE, (c) update `AlphaEngineOverview.jsx`, (d) document in OPEN_THREADS.
- **New setup type checklist (anti-hardcode gate) — also the checklist for auditing *existing* live setups, not just gating new ones.** Items 5-10 below were each found by retroactively checking an *already-live* setup, not by reviewing a new one before launch — if you're doing a broad audit pass over existing setup_types (see docs/OPEN_THREADS.md's "broader audit of all setup types" thread), these are exactly the categories of bug to check every one of them against: real stop/target simulation (5), half-wired integration (6), standalone-poller promotion gaps (7), Unified Signal Table status-mapping (8), fire-gate-vs-data-availability timing (9), and backfill-detection-window-vs-live-firing-window mismatch (10). Before any new `setup_type` goes live in `acd.js`, ALL of the following must be satisfied:
  1. Run `node scripts/backtest_setup_status.mjs` → generates/updates `SETUP_STATUS` row in `performance_audit`
  2. Run `node scripts/update_optimal_stops.mjs` → generates/updates `OPTIMAL_STOP` row with data-derived stop/target
  3. If N<20 resolved trades, do NOT fire live — insert as `status='SHADOW'` only until N≥20
  4. Never write a stop, target, or WR claim as a literal number in `acd.js` — always read from `liveStats._opt[type]` or `performance_audit`
  5. **Simulate the real stop/target as an actual bar-by-bar trade before ever calling a signal "validated."** A statistically stable *sign* on a raw point value (e.g. "price at bar+N") is necessary but not sufficient — it has no drawdown tolerance and is not a tradeable strategy. Found 2026-07-14: 3 of 4 minute-bar scanner signals passed day-clustering, time-of-day, and 3-way chronological stability checks, then turned negative EV (-$15.75, -$18.49, -$3.20/trade) the moment a real p75-MAE-stop/p50-MFE-target was simulated instead of the raw exit value. Only after this step should a signal be treated as a live candidate.
  6. **Verify integration, don't assume it.** New setup types are easy to half-wire: check `dropToTimeline()` is called from the actual insert path (not just the pattern copied from elsewhere), check `SETUP_DISPLAY_LABELS` (`src/constants/setupDisplay.js`) has an entry, check `isLongSetup()`/`inferDirection()` resolve correctly for the exact string being inserted. Found 2026-07-14: a new setup's live poller skipped `dropToTimeline()` entirely and had no display label — both silent, both would only surface once the setup was visible enough to matter.
  7. **If the setup lives outside the level-fade candidates array (its own poller — e.g. a bar-window statistical signal, not a level touch), it must replicate the dynamic SHADOW→ACTIVE promotion check manually.** The candidates-array insert path already does this correctly: `liveStats._suppressedSetups` is rebuilt from the latest `SETUP_STATUS` rows every trading day and checked fresh on every single fire (`server/routes/acd.js` ~line 4564). A standalone poller has no such built-in mechanism — if you hardcode `status='SHADOW'` at insert time with no live re-check, the setup sits in SHADOW **forever**, even after clearing N≥20 live trades with good EV, because nothing else in the pipeline will ever flip it. Found 2026-07-14 in `minuteBarSignalDetector.js`'s first version. Fixed with a `getLiveStatus()` function — queries real resolved `active_setups` trades for the type (N≥20 & EV>-$5 → `ACTIVE`, else `SHADOW`), called fresh on every fire — use it as the template for any future standalone poller.
  8. **If the calibration script writes a new `recommendation` value, register it in `/api/performance-audit/unified`'s status-mapping** (`server/routes/acd.js` ~line 6976) or the setup type is silently invisible in the Unified Signal Table (`BacktestView.jsx`'s "Unified Signal Table"). Found 2026-07-14: `SETUP_STATUS`'s actual vocabulary (`SUPPRESS`/`THIN_N`/`PROMOTE`/`DAY_TYPE_MANAGED`) matched none of the recognized strings there, hiding ~61 of 113 setup_types from the table.
  9. **If a setup's fire gate is earlier than the data it depends on for suppression, its suppression logic is a silent no-op.** Any setup exempted from the standard blended-EV `SUPPRESS` check (a `DAY_TYPE_CONDITIONAL`-style carve-out in `backtest_setup_status.mjs`, or a DOW/day-type check inline in `acd.js`) must have its fire-gate timing verified against when that dependency actually becomes available — check the actual gate condition (`etMin >= ...`), not just that a suppression check exists in the code. Found 2026-07-14: `IB_BULLISH`/`IB_BEARISH` fired off a deliberate 30-min IB window (`etMin>=600`, 10:00 ET) but their day-type suppression checks depend on `acd_daily_log.day_type`, which isn't classified until IB close at 10:30 ET — so the checks were guaranteed no-ops every time they fired, and `IB_BULLISH` ran live at -$27.81/trade EV (N=106) with zero effective guardrail. Fixed by moving the fire gate to `etMin>=630` (not the 30-min level *definition*, just when the alert is allowed to fire) and by giving `DAY_TYPE_CONDITIONAL` setups a real per-day-type floor in `backtest_setup_status.mjs` (SUPPRESS if every bucket with N≥20 is below the standard `-$5` bar) instead of unconditionally trusting the day-type carve-out. Full writeup: docs/OPEN_THREADS.md.
  10. **A backtest/backfill's detection population must match what the live poller actually fires on — window, touch-definition, and all.** If a historical calibration script restricts detection to a narrower window or stricter touch condition than the live code path uses, the resulting WR/EV describes a different, more selective strategy than what's actually live. Found 2026-07-14: `scripts/archive/backfill_level_fades.js` (source of every `resolution_method='BACKFILL'` row in `active_setups`, 72 setup_types) only scans for a level touch in a 10:30am-noon window, but live `acd.js` (`nearLevels`, ~line 4757) fires on the first RTH touch any time from ~9:34 AM — re-simulating `CAM_R4_FADE_SHORT` under live-matching "first touch anywhere in RTH" flipped it from +$51.72 EV (window-restricted) to **-$34.87 EV** (N=114), a real winner-to-loser flip, not noise. Only verified/fixed for 2 of the 72 affected setup_types so far (`scripts/repair_cam_r4_s3_window_mismatch.mjs`) — the rest are a known, flagged risk (docs/OPEN_THREADS.md), not blanket-fixed, because levels with a real formation time (IB/OR-dependent) can't safely be re-tested from session open without introducing lookahead. When building or re-verifying any backfill/calibration script, diff its detection window/conditions against the live poller's actual firing logic — don't assume they match just because they share level names.
  - The `Stop` hook (`.claude/hooks/check-docs-drift.sh`) scans for hardcoded anti-patterns and will warn if any of these are violated. The `SessionStart` hook checks for setup_types missing a fresh SETUP_STATUS row.
- **Trading-day dates: always derive from SQL `CURRENT_DATE`, never JS `new Date().toISOString()`.** The DB server runs in `America/New_York`; JS's `toISOString()` is UTC, and the two disagree once past 8PM ET — a full calendar day earlier in JS-UTC-land than the DB's own ET-based "today." This caused 3 separate same-day bugs on 2026-07-14 (`backtest_minute_bar_scan.mjs`, and pre-existing `backtest_setup_status.mjs`) where a script's own `run_date` silently drifted a day from its siblings', breaking every `MAX(run_date)`-based "latest run" join `performance_audit` consumers rely on (including `/api/performance-audit/unified`). Fetch it with `SELECT CURRENT_DATE::text as today` in every new backtest script — never `new Date().toISOString().slice(0,10)`.
- **Rigor diagnostics are standing, not one-off.** Day-clustering (top-5-dates % of N) + 3-way chronological sign-stability run on every weekly mining/calibration pass now, across **all 4** statistical pipelines in this codebase (`backtest_setup_status.mjs`, `mine_minutebar_conditions.mjs`, `patternScannerService.js`'s `mineLevelFades()`, `mine_tod_patterns.mjs`). These are informational — they do NOT feed SUPPRESS/PROMOTE or ACTIVE/DEGRADED logic — because "unstable" doesn't mean "losing," it can mean genuinely improving. Don't blanket-suppress on these flags; classify each one (degrading vs. improving vs. noisy-but-stable vs. too-thin-to-tell) before acting, the same way the 2026-07-14 audit did. Real result from the first full pass across all 4: level-fade patterns were the worst offender (**0 of 13 currently-`ACTIVE` patterns are clean** — all clustered, because that miner only uses a 90-day window and level touches aren't independent day-to-day), `mine_tod_patterns.mjs` was the best (6 of 7 clean) since its unit of analysis is already one-observation-per-day.
- **Share modules when the same logic would otherwise be reimplemented.** The rigor diagnostic above was independently hand-written **three separate times** on 2026-07-14 (one per script) before being centralized into `server/services/rigorDiagnostics.js` (`computeRigor()`) — the exact inconsistency this principle exists to prevent. Any script computing the same kind of check (day-clustering, chronological stability, or similar) must import the shared version, not write a 4th copy. `computeRigor` takes a generic `pnlFn` so callers without a real dollar EV (e.g. `mine_tod_patterns.mjs`'s pure hit-rate claims) can pass a +1/-1 hit/miss proxy instead — the stability math is identical either way.
- **`minePatterns()` (`patternScannerService.js`) is a known, unaddressed gap** — the 6 hand-coded "next-day tendency" hypotheses (session-type → next-day bias, gap-fill rate, etc.) have no persistence, no ACTIVE/DEGRADED lifecycle, and recompute fresh on every call, unlike the other 4 pipelines. Structurally different enough (no discovery table, no rigor check applicable in its current form) that it needs its own design pass rather than a bolt-on fix — not done as of 2026-07-14, flagged for a future session.
- **Unified suppression pipeline (the only suppression source):** All suppression of level fade setups flows through `scripts/backtest_setup_status.mjs` → `performance_audit` SETUP_STATUS/SETUP_STATUS_DOW → `liveStats._suppressedSetups` / `liveStats._dowSuppressToday`. Never add a hardcoded suppression list or day-of-week skip list to `acd.js` — the pipeline handles it automatically and re-evaluates weekly.
- **Conditional variant setup checklist** — when a single level name generates two setup types based on entry condition (e.g., `WPP_FADE_SHORT` vs `WPP_FADE_SHORT_GAP_UP`):
  1. Add the override to `resolveSetupType()` in `acd.js` (defined just above the `nearLevels` filter). This is the **single source of truth** — both the live path and early-touch backfill call it.
  2. Write a dedicated backtest script (`scripts/backtest_<variant>.mjs`) that persists SETUP_STATUS + OPTIMAL_STOP rows for the new type. Add it to `run_weekly_backtests.sh` under "Conditional-variant backtests".
  3. Add an entry to `CONDITIONAL_VARIANTS` in `server/config/setupTypes.js` with `baseType`, `direction`, `condition`, `backtestScript`. If the type name doesn't encode direction via a standard suffix, also add it to `CONTEXTUAL_DIRECTION_TYPES`.
  4. Update `AlphaEngineOverview.jsx` `suppressed` array — add entries for both the suppressed base type and the active variant, noting the condition.
  5. Add a note to `docs/OPEN_THREADS.md` to monitor variant at N=50.
  6. **Run `node scripts/test_invariants.mjs`** — this catches everything else automatically: OPTIMAL_STOP coverage, direction inference correctness, backtest script on disk, base type suppressed. If it passes, the pipeline is complete.
- **`antigravityEdges.js` Promise.all ordering footgun:** `getLiveEdgesContext()` fires all DB queries in a single `Promise.all` wave (20 entries). The destructured variable names are **positionally bound** — adding or removing a query shifts every entry below it to a wrong variable with no runtime error. Always update the destructuring list and the array body together, and check the index comments (0–19) when inserting. Cache-miss-only entries (indices 0–3) use `isCached ? Promise.resolve(null) : query(...)` — do not move them to a later position without updating the cache skip logic.

- **`acd.js` block-scoping footgun:** `liveStats` is declared with `let` inside the level-fade block (`if (currentPrice && allRthBarsRow.rows.length >= 3)` at line ~4065, inner `if (last5.length >= 3...)` at ~4108). Anything outside those blocks — including `const candidates`, the `for (const cand of candidates)` loop, `shadowCandidates`, and the INSERT body — is outside `liveStats`'s scope and will throw a ReferenceError if it references `liveStats` directly. The fix pattern is `getCached(todayET, 'levelFadeStats')` at the outer scope (already done at line ~5064). **When adding any new reference to `liveStats` in `acd.js`, check whether the call site is inside or outside the level-fade block.** Similarly, `ls()` and `lsMon()` are only valid inside the inner block — do not call them from the `candidates` array or below.**

## Documentation maintenance — keep this perpetually current

This file and [ARCHITECTURE.md](ARCHITECTURE.md) are the handoff point for the next session (human or Claude) — treat letting them go stale as a real cost, the same as introducing a bug. A `Stop` hook (`.claude/settings.json`) checks at the end of every session whether structural files changed without a matching doc update and prints a reminder — if you see that reminder, act on it before ending the turn rather than dismissing it.

Concretely, whenever a session does any of the following, update the relevant doc **in that same session**, not as a follow-up:
- Add/remove a route file, service file, or DB table → update [ARCHITECTURE.md](ARCHITECTURE.md)'s route/service/table tables, and if a table was added/dropped/altered, regenerate `server/schema.sql` (command is in ARCHITECTURE.md)
- Add/remove a dashboard component → update the frontend structure table in [ARCHITECTURE.md](ARCHITECTURE.md)
- Establish a new hard rule or convention (the user corrects an approach, or confirms a non-obvious one) → add it to the **Hard rules** or **Conventions** section above
- Fix something listed in [docs/KNOWN_ISSUES.md](docs/KNOWN_ISSUES.md) → remove that entry; discover a new one → add it
- The user confirms a fix/decision but it isn't fully implemented in the same session, proposes a follow-up that isn't confirmed yet, or you find a stat/display that's stale or disconnected from its source of truth → add it to [docs/OPEN_THREADS.md](docs/OPEN_THREADS.md) **before the session ends** — don't rely on conversation memory alone to carry pending work forward. This is on you to maintain proactively; the user has delegated it rather than asking for it each time.
- `docs/` also holds point-in-time specs (`MONTE_CARLO_SPEC*.md`, `BACKTESTING_PLAYBOOK.md`) and parked design docs (`*_parked.md`) — those describe proposals, not live state, and aren't required to track the running app. Don't confuse them with ARCHITECTURE.md.
- **Any change that supersedes existing code, data, or documentation must clean up what it replaces in the same session** — don't leave stale duplicate descriptions, dead constants/variables, orphaned scratch/temp files, or superseded DB rows sitting alongside the replacement. Concretely: rewriting a script's methodology → grep for every other doc that describes the old methodology (not just the primary one) and update all of them, and remove now-unused constants/params from the code itself; reverting a bad live change → delete the temp files used to make and revert it; a finding that invalidates an old proposal → replace/remove the old note, don't just append a new one next to it (OPEN_THREADS.md especially — resolved items get deleted per its own convention, not left dangling).
