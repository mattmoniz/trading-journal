## Ports & Dev Workflow

| Service | Port | Notes |
|---|---|---|
| Vite frontend | 3000 | `vite.config.js`; proxies `/api`, `/uploads`, `/socket.io` to 3002 |
| Express backend | 3002 | Set via `.env` `PORT=3002` (code default is 3001 — `.env` wins) |
| PostgreSQL | 5432 | db name `trading_journal` |

- Start everything: `./start.sh` (kills stale processes on 3000/3001/3002/5173, starts server + client via `concurrently`)
- Stop everything: `./stop.sh` or `fuser -k 3002/tcp`
- Server only: `npm run server` (nodemon) — Client only: `npm run client` (vite)
- DB schema bootstrap: `npm run db:setup` (runs `server/schema.sql` — only covers the original 5 core tables; everything else was added ad hoc directly against the DB, not via tracked migrations)

## Database

### Schema source of truth
`server/schema.sql` is a full `pg_dump --schema-only` snapshot of the live DB (regenerated 2026-08-04 after `active_setups.va_width_pctile_60d`/`va_overlap_streak`/`ib_range_pctile_60d` were added for the compression-metrics backfill — see the `active_setups` entry below; this regen also caught up several other tables/columns that had drifted since the last regen on 2026-07-27, since nothing in this codebase's workflow regenerates the dump automatically on every schema change). There is still no tracked migration history — tables beyond the original 5 (`daily_logs`, `trades`, `custom_field_definitions`, `setup_types`, and originally `trade_screenshots`, dropped 2026-07-16) were created ad hoc directly against the live DB — so `schema.sql` is a point-in-time dump, not hand-maintained DDL, and will drift again as soon as a table is added/altered without regenerating it. Regenerate with:

```bash
PGPASSWORD=$DB_PASSWORD pg_dump --schema-only --no-owner --no-privileges --no-comments \
  -h $DB_HOST -p $DB_PORT -U $DB_USER -d $DB_NAME \
  | sed '/^\\restrict /d; /^\\unrestrict /d' > server/schema.sql
```

`npm run db:setup` runs this file against an empty database — it is **not idempotent** (no `IF NOT EXISTS`), so it will error if run against a DB that already has these tables. To inspect current live schema directly instead of reading the dump:

```sql
SELECT table_name FROM information_schema.tables WHERE table_schema='public' ORDER BY table_name;
SELECT column_name, data_type FROM information_schema.columns WHERE table_name = '<table>' ORDER BY ordinal_position;
```

### 2026-07-13 `price_bars_primary` duplicate-minute-bar fix

Discovered while auditing a new minute-bar pattern scanner: `price_bars` (documented above as "1-min OHLCV bars") actually had sub-minute duplicate ticks for ~14.6% of RTH minutes in the NQ history (some single minutes had up to 25 rows — an ingestion issue, not a data-model choice; the worst offenders cluster in Jun–Aug 2025). The old `price_bars_primary` view passed these through as plain per-row `SELECT`s with no tiebreak among same-minute rows, so **any consumer that walked results positionally (`bars[i-N]` = "N minutes ago") got non-deterministic results** — proven by running the identical query twice back-to-back and getting different OHLCV values back for the same nominal minute.

Fixed at the view level (not per-consumer) since `price_bars` is documented as 1-minute data and nothing legitimately depends on sub-minute granularity through this view: `price_bars_primary` now `GROUP BY`s on `(symbol, contract, date_trunc('minute', ts))`, taking `open`=first tick/`close`=last tick (via `array_agg(...ORDER BY ts)[1]`, deterministic regardless of physical scan order), `high`=MAX, `low`=MIN, `volume`/`num_trades`/`bid_volume`/`ask_volume`=SUM. One view fix corrects every downstream consumer automatically — no code changes needed in `acd.js`, `caseEngine.js`, `acdService.js`, etc.

**Not yet done**: every live setup's stop/target calibration in `performance_audit` (from `backtest_unified.js`, `update_optimal_stops.mjs`, and the rest of the weekly backtest suite) was computed against the old, contaminated bar data and needs a full recompute against the fixed view. That's flagged in `docs/OPEN_THREADS.md`, not done as part of this fix — large enough to warrant its own session.

### 2026-07-27 `price_bars_primary` is a VIEW — an unbounded `ts >=` query is a real, severe performance bug

Found while running a full-population (~11,000 row) bar-6 exit-rule backtest: a per-trade lookup query (`SELECT ... FROM price_bars_primary WHERE symbol='NQ' AND ts >= $1 ORDER BY ts ASC LIMIT 10`) took **900ms–1.2s per call**, on pace for 2.5+ hours to finish 11,041 calls. `pg_indexes` returns **zero rows** for `price_bars_primary` — confirmed via `information_schema.tables` that it's a `VIEW` (`table_type='VIEW'`), not a plain table, so it structurally cannot have an index of its own; only the underlying `price_bars`/`price_bars_contract_calendar` tables can. `EXPLAIN ANALYZE` on the slow query showed a `GroupAggregate`/`Hash Join`/`Parallel Append` touching ~540,000 rows to return 10 — because the query had **no upper bound** on `ts`, the planner had to materialize the join+`GROUP BY date_trunc('minute', ts)` aggregation (the dedup fix from the 2026-07-13 entry above) across everything from that timestamp through the most recent data before it could sort and take the top 10.

**Fix**: add a tight upper bound alongside the lower one — `ts >= $1 AND ts < $1::timestamp + interval '6 hours'` (or whatever window the caller actually needs; this one only ever needs the first ~7 bars, well within a few hours). Verified directly: same query, same real `fired_at` value, dropped from ~900-1200ms to **62ms** — a 15-20x speedup, with the full 11,041-row run going from a 2.5+ hour projection to ~15 minutes.

**This is a general pattern risk, not a one-off bug in one script** — any code that queries `price_bars_primary` with `ts >= X` and no upper bound will hit the same wall, and this codebase has many scripts doing exactly that (a `grep -rn "FROM price_bars_primary" scripts/ server/` turns up dozens). Audited the same day (`price_bars_primary_unbounded_query_audit`, resolved) — the live/hot-path side (`server/routes`, `server/services`) was fully clean; the real risk was only in one-off, non-scheduled research scripts. When writing or auditing any new script that queries `price_bars_primary` with a lower-bound-only `ts` filter, still add an explicit upper bound sized to what the query actually needs — don't rely on `LIMIT` alone to keep it fast, since `LIMIT` only helps after the expensive aggregation, not before it.

### 2026-07-27 `price_bars_primary` materialized — the structural fix (`price_bars_primary_materialize_historical_bars`, resolved)

The tactical per-query-bound fix above helps callers that remember to add one, but every future caller still has to remember — a real structural fix removes the landmine instead of relying on discipline. `price_bars_primary` is now backed by a real, indexed **Postgres materialized view**, `price_bars_dedup_hist` (same dedup/front-month-selection logic as the original view, `WHERE pb.ts::date < CURRENT_DATE` — everything before today, which in practice is closed and rarely touched again), with a unique index `(symbol, contract, ts)` (required for `REFRESH ... CONCURRENTLY`) and a plain `(symbol, ts)` index for the common "just symbol + ts range" query shape. `price_bars_primary` itself is now a thin view: `SELECT * FROM price_bars_dedup_hist UNION ALL <original join, filtered to pb.ts > (MAX(ts) in price_bars_dedup_hist)>` — **zero code changes needed anywhere**, every one of the ~200 existing consumers still queries `price_bars_primary` by the same name and gets the same columns/types back.

The live branch's lower bound is derived from the materialized view's own current `MAX(ts)`, not a hardcoded "today" cutoff — self-adjusting regardless of exactly when the nightly refresh last ran (if a refresh is skipped or delayed, the live branch just covers more ground that day, never double-counts, and never drops data). **Refresh**: `scripts/refresh_price_bars_dedup_hist.mjs` (`REFRESH MATERIALIZED VIEW CONCURRENTLY`, ~8s), wired into `run_daily_calibration.sh` (runs nightly, 8:20 PM ET Mon-Fri) as the first step, before the calibration scripts that read bar data. Build/verification script: `scripts/materialize_price_bars_historical.mjs` — verifies the materialized view's fingerprint (row count + `SUM(volume)`/`SUM(high)`/`SUM(low)`) matches the original view's historical-only output exactly before ever touching `price_bars_primary`, then re-verifies the full (historical + live) output against a saved backup of the original view definition (`price_bars_primary_orig_backup`, kept as a live rollback path — `DROP VIEW price_bars_primary; CREATE VIEW price_bars_primary AS <the saved original SQL>` instantly reverts if anything ever looks wrong) — both checks done via a single combined SQL statement, not two separate queries, since this data is genuinely live/actively ingesting and two separate snapshot reads a moment apart will legitimately differ by whatever new bars arrived in between (confirmed directly: an early verification attempt flagged a "mismatch" that was actually just 1 real minute bar landing between two queries, not a bug).

**A real off-by-one bug was caught by this verification, not assumed correct**: the first working version used `pb.ts >= (SELECT MAX(ts) ...)` (inclusive) for the live branch's lower bound, which double-counted the materialized view's own last minute (once via `price_bars_dedup_hist`, once again via the live join since its `>=` bound included that exact same timestamp) — surfaced as `new` having exactly 1 more row than `orig`, consistently, across two separate runs (a systematic +1, not a random race). Fixed to `>` (exclusive). **Verified**: full-history fingerprint now matches the original view byte-for-byte; the exact query pattern that took 900ms-1.2s in the entry above (`ts >= $1` with no upper bound, on an old historical date) now takes **~80ms** (11-15x) even with zero explicit upper bound — the structural fix protects a caller that forgets to add one, which the tactical per-query fix above cannot. `test_invariants.mjs`, `data_sanity_audit.mjs`, and a live server restart + endpoint check all confirmed clean afterward (one unrelated pre-existing finding surfaced during verification — see `price_bars_recurring_2month_data_gaps_pattern` `OPEN_DECISION`, a genuine but unrelated ~61-day data gap pattern, confirmed present identically in both the old and new view so not caused by this change).

### P&L Calculation (CumPL Diff) — critical, don't regress this

Raw fill sums overcount P&L when positions are scaled. The correct approach uses `Cumulative Profit/Loss (C)` diffs at EP (flat-to-flat) boundaries:

```sql
WITH ep_fills AS (
  SELECT log_date, custom_fields->>'account' as account, exit_time,
    CASE WHEN custom_fields->'sierra_data'->>'Cumulative Profit/Loss (C)' ~ '^-?[0-9]+(\.[0-9]+)?$'
    THEN (custom_fields->'sierra_data'->>'Cumulative Profit/Loss (C)')::numeric ELSE NULL END as cum_pl
  FROM trades WHERE custom_fields->'sierra_data'->>'Exit DateTime' LIKE '% EP' AND exit_time IS NOT NULL
),
last_ep_per_day AS (
  SELECT DISTINCT ON (log_date, account) log_date, account, cum_pl
  FROM ep_fills ORDER BY log_date, account, exit_time DESC
),
daily_pnl_per_account AS (
  SELECT log_date,
    cum_pl - COALESCE(LAG(cum_pl) OVER (PARTITION BY account ORDER BY log_date), 0) as session_pnl
  FROM last_ep_per_day WHERE cum_pl IS NOT NULL
),
daily_cuml AS (
  SELECT log_date, SUM(session_pnl) as cum_daily_pnl
  FROM daily_pnl_per_account GROUP BY log_date
)
-- JOIN daily_cuml, use COALESCE(cum_daily_pnl, SUM(t.pnl), 0) as daily_pnl
```

Fallback to `SUM(t.pnl)` only for older Activity Log format data that lacks CumPL fields. Both `/api/daily-logs` and `/api/stats/daily` implement this pattern — keep them in sync if you touch one.

### TAL Markers & Dedup

- **BP** (`Entry DateTime` ends with ` BP`): position opened from flat — session start
- **EP** (`Exit DateTime` ends with ` EP`): position returned to flat — session end, authoritative P&L boundary
- Dedup key: `(entry_time, exit_time, symbol, direction, quantity, entry_price, exit_price, account)`. If the import file contains N rows matching a key and M already exist, only `N − M` are inserted — preserves legitimate repeated scale-ins without duplicating on re-import.

### Account filter (shared state)
`/api/accounts` returns accounts ordered by most recently active; the app defaults to `data[0]`. Selected account is lifted to the `App` component so Calendar and Dashboard stay in sync.

## `scripts/` — Ad-hoc Analysis & Backtests

~51 standalone Node scripts run manually (`node scripts/backtest_X.js`) against the live DB via `server/db.js`. They are **not imported by the running app** — each one tests a specific edge hypothesis and most write findings into `performance_audit`. Naming convention is `backtest_<hypothesis>.js`; one-time data-repair scripts use `repair_<what>.mjs` (see below). 87 superseded scripts moved to `scripts/archive/` (2026-07-09) — not maintained.

A few scripts ARE wired in as scheduled jobs from `server/index.js` (morning brief, weekly/monthly report, daily coaching, level computation) — check `index.js` cron registrations before assuming a script is dead.

Notable scripts that are scheduled or run after auto-import:
- `scripts/compute_levels.js` — computes all 68 MGI levels for a session date, writes to `level_prices`; supports single date or `--backfill [--from DATE]`; runs via three crons: Sunday 9:30 PM ET (for the upcoming Monday), Mon-Fri 8:00 AM ET (for today, pre-market), and Mon-Fri 11:00 AM ET (for today again). **The 11 AM pass exists because the two pre-market crons structurally cannot capture that day's own same-day-forming CURRENT-category levels** (`OR5/OR10/OR15/OR30_HIGH/LOW/MID`, `IB_HIGH/LOW/MID`) — those levels' own opening-range/IB bars don't exist yet before market open, so their `add()` guards always fail at 8 AM/Sunday-night. Found 2026-08-26: this had silently left `level_prices` frozen at 2026-08-12 values for these level names for two weeks (fixed via a one-time `--backfill --from` catch-up); does not affect live trading, which computes OR/IB from `acd_daily_log`/bars directly, never from this table.
